01

What is Amazon CloudFront?

🏠 ← Return to Learning Dashboard
Simple English

Amazon CloudFront is a Content Delivery Network (CDN) service from AWS. It stores copies of your website or app content in many locations around the world, so users get that content from a place near them instead of from your main server, which is often far away.

Hinglish

Amazon CloudFront AWS ka ek CDN (Content Delivery Network) service hai. Ye aapke website ya app ke content ki copies duniya bhar ki alag-alag jagah par store kar deta hai, taaki user ko content unke paas wali jagah se mile, na ki aapke main server se jo kaafi door ho sakta hai.

What problem does it solve?

Simple English

Without a CDN, every user request travels all the way to your original server, no matter how far the user is. This makes websites slow for users who are far from the server, and it also increases load on the server. CloudFront solves this by caching (storing) content closer to users.

Hinglish

CDN ke bina, har user ka request seedha aapke original server tak jaata hai, chahe user kitna bhi door ho. Isse door wale users ke liye website slow ho jaati hai, aur server par load bhi zyada padta hai. CloudFront is problem ko solve karta hai kyunki wo content ko user ke paas cache (store) kar deta hai.

Real-world example

Simple English

Suppose your server is in the US, but a user is browsing your website from India. Without CloudFront, every image, video, or file has to travel from the US to India, which takes time. With CloudFront, a copy of that content is already stored at an Edge Location in India, so the user gets it almost instantly.

Hinglish

Maan lo aapka server US mein hai, lekin ek user India se aapki website browse kar raha hai. CloudFront ke bina, har image, video, ya file US se India tak travel karegi, jisme time lagega. CloudFront ke saath, us content ki copy pehle se India ke Edge Location par store hoti hai, toh user ko wo turant mil jaata hai.

02

What is CDN?

Simple English

CDN stands for Content Delivery Network. It is a group of servers spread across many locations in the world. Instead of every user hitting one central server, users are served by the server closest to them, which makes content delivery much faster.

Hinglish

CDN ka full form hai Content Delivery Network. Ye duniya bhar mein failay hue servers ka ek group hai. Har user ek hi central server par jaane ke bajaye, apne sabse paas wale server se serve hota hai, jisse content delivery kaafi fast ho jaati hai.

Simple English

Without a CDN, the request always goes to one main server, so distant users face delay. With a CDN like CloudFront, the request first goes to the nearest edge location, and if the content is already cached there, it is returned immediately without contacting the main server at all.

Hinglish

CDN ke bina, request hamesha ek hi main server tak jaata hai, isliye door wale users ko delay hota hai. CloudFront jaise CDN ke saath, request pehle sabse paas wale edge location par jaata hai, aur agar content wahan pehle se cached hai, toh wo turant mil jaata hai, main server tak jaane ki zaroorat hi nahi padti.

03

Why do we use CloudFront?

Faster content delivery

Simple English

Content is served from a location near the user, so pages, images, and videos load much faster.

Hinglish

Content user ke paas wali jagah se serve hota hai, isliye pages, images, aur videos bahut fast load hote hain.

Lower latency

Simple English

Latency is the delay before data starts transferring. Since CloudFront serves from nearby edge locations, this delay becomes very small.

Hinglish

Latency matlab data transfer shuru hone se pehle ka delay. CloudFront paas wale edge locations se serve karta hai, isliye ye delay bahut kam ho jaata hai.

Caching

Simple English

CloudFront stores (caches) copies of your content at edge locations, so repeated requests do not need to go back to the origin server every time.

Hinglish

CloudFront aapke content ki copies edge locations par store (cache) kar deta hai, isliye baar baar request origin server tak jaane ki zaroorat nahi padti.

Global content delivery

Simple English

CloudFront has edge locations across the world, so your app can serve users in different countries with good speed, without deploying servers everywhere yourself.

Hinglish

CloudFront ke edge locations duniya bhar mein hain, isliye aapka app alag alag countries ke users ko achhi speed se serve kar sakta hai, bina khud har jagah server deploy kiye.

Reduced load on origin server

Simple English

Because most requests are served from the cache at edge locations, the origin server receives fewer requests, so it stays healthier under heavy traffic.

Hinglish

Kyunki zyada tar requests cache se edge locations par hi serve ho jaate hain, origin server ko kam requests milte hain, isliye heavy traffic mein bhi wo healthy rehta hai.

HTTPS / SSL

Simple English

CloudFront makes it easy to serve your content securely over HTTPS, including free certificates through AWS Certificate Manager.

Hinglish

CloudFront aapke content ko HTTPS ke through securely serve karna aasan bana deta hai, aur AWS Certificate Manager se free certificates bhi mil jaate hain.

Security

Simple English

CloudFront integrates with AWS security features like WAF (Web Application Firewall) and Origin Access Control to protect your content and your origin server.

Hinglish

CloudFront AWS ke security features jaise WAF (Web Application Firewall) aur Origin Access Control ke saath integrate hota hai, jisse aapka content aur origin server protect rehta hai.

DDoS protection

Simple English

CloudFront works with AWS Shield to absorb and mitigate large-scale traffic attacks, so your origin server is shielded from many kinds of DDoS attacks.

Hinglish

CloudFront AWS Shield ke saath milkar bade traffic attacks ko absorb aur mitigate karta hai, isliye aapka origin server kai tarah ke DDoS attacks se bacha rehta hai.

Better application performance

Simple English

Because of caching, lower latency, and fewer origin hits, the overall application feels faster and more reliable for end users.

Hinglish

Caching, kam latency, aur origin par kam hits ki wajah se, poora application end users ko zyada fast aur reliable feel hota hai.

How CloudFront Works

   User
    |
    v
 CloudFront
    |
    v
 Edge Location
    |
    v
   Cache

1. User sends a request

Simple English

The user's browser or app sends a request, for example to load an image or a webpage.

Hinglish

User ka browser ya app ek request bhejta hai, jaise kisi image ya webpage ko load karne ke liye.

2. Request reaches CloudFront

Simple English

This request is routed to CloudFront instead of going directly to your origin server.

Hinglish

Ye request seedha origin server ke bajaye CloudFront tak route hota hai.

3. CloudFront checks its cache

Simple English

CloudFront looks at the nearest edge location to see if it already has a valid copy of the requested content.

Hinglish

CloudFront sabse paas wale edge location par check karta hai ki requested content ki koi valid copy pehle se maujood hai ya nahi.

4. Cache Hit

Simple English

If the content is found and still valid (within TTL), it is called a Cache Hit, and CloudFront returns it immediately.

Hinglish

Agar content mil jaata hai aur abhi valid hai (TTL ke andar), toh ise Cache Hit kehte hain, aur CloudFront turant wo content return kar deta hai.

5. Cache Miss

Simple English

If the content is not found or has expired, it is called a Cache Miss.

Hinglish

Agar content nahi milta ya expire ho chuka hai, toh ise Cache Miss kehte hain.

6. CloudFront gets content from Origin

Simple English

On a cache miss, CloudFront sends a request to the Origin Server (like S3, EC2, or ALB) to fetch the latest content.

Hinglish

Cache miss hone par, CloudFront Origin Server (jaise S3, EC2, ya ALB) se latest content fetch karta hai.

7. CloudFront caches the content

Simple English

After getting the content from the origin, CloudFront stores a copy at the edge location so future requests can be served faster.

Hinglish

Origin se content lene ke baad, CloudFront uski ek copy edge location par store kar leta hai, taaki future requests aur fast serve ho sakein.

8. Content is returned to the user

Simple English

Finally, whether it was a cache hit or a cache miss, the content is delivered back to the user.

Hinglish

Aakhir mein, chahe cache hit ho ya cache miss, content user tak deliver kar diya jaata hai.

05

Important CloudFront Terms

Distribution

Simple English

A Distribution is the CloudFront configuration you create. It tells CloudFront which origin to use, how to cache content, and which domain to serve it on.

Hinglish

Distribution wo CloudFront configuration hai jo aap banate hain. Ye CloudFront ko batata hai ki kaunsa origin use karna hai, content kaise cache karna hai, aur kis domain par serve karna hai.

Example: d123abcxyz.cloudfront.net is a CloudFront distribution domain name.

Origin

Simple English

The Origin is the original source of your content, such as an S3 bucket, an EC2 server, or a Load Balancer. CloudFront fetches content from here when it is not already cached.

Hinglish

Origin aapke content ka original source hota hai, jaise S3 bucket, EC2 server, ya Load Balancer. CloudFront yahan se content fetch karta hai jab wo pehle se cached nahi hota.

Edge Location

Simple English

An Edge Location is a data center, part of AWS's global network, that stores cached copies of your content close to end users.

Hinglish

Edge Location ek data center hota hai, jo AWS ke global network ka hissa hai, aur end users ke paas aapke content ki cached copies store karta hai.

Regional Edge Cache

Simple English

A Regional Edge Cache sits between edge locations and the origin. It holds content longer than a normal edge location, so if an edge location does not have the content, the Regional Edge Cache can often provide it without going all the way to the origin.

Hinglish

Regional Edge Cache edge locations aur origin ke beech mein hota hai. Ye content ko normal edge location se zyada der tak hold karta hai, isliye agar edge location ke paas content nahi hai, toh Regional Edge Cache aksar origin tak jaaye bina hi wo de sakta hai.

Cache

Simple English

Cache means a temporary storage of content closer to the user, so it can be served quickly without repeatedly fetching it from the origin.

Hinglish

Cache ka matlab hai content ko user ke paas temporary store karna, taaki use baar baar origin se laaye bina jaldi serve kiya ja sake.

Cache Hit

Simple English

A Cache Hit happens when CloudFront finds the requested content already in its cache and can return it directly.

Hinglish

Cache Hit tab hota hai jab CloudFront ko requested content pehle se cache mein mil jaata hai aur wo use seedha return kar deta hai.

Cache Miss

Simple English

A Cache Miss happens when the content is not in the cache, so CloudFront has to fetch it from the origin first.

Hinglish

Cache Miss tab hota hai jab content cache mein nahi milta, isliye CloudFront ko pehle origin se wo content laana padta hai.

TTL (Time To Live)

Simple English

TTL is the amount of time content is allowed to stay in the cache before CloudFront checks the origin again for a fresh copy.

Hinglish

TTL wo time hota hai jab tak content cache mein rehne diya jaata hai, uske baad CloudFront origin se dobara fresh copy check karta hai.

Cache Behavior

Simple English

A Cache Behavior is a rule that tells CloudFront how to handle requests for a specific path pattern, like which origin to use and how long to cache it.

Hinglish

Cache Behavior ek rule hota hai jo CloudFront ko batata hai ki ek specific path pattern ke requests kaise handle karne hain, jaise kaunsa origin use karna hai aur kitni der cache karna hai.

Example: /images/* can have different caching rules than /api/*.

Viewer

Simple English

The Viewer is the end user or client (browser, mobile app) that sends the request to CloudFront and receives the response.

Hinglish

Viewer wo end user ya client (browser, mobile app) hota hai jo CloudFront ko request bhejta hai aur response receive karta hai.

Origin Request

Simple English

An Origin Request is the request CloudFront sends to the origin server when it needs fresh content, usually after a cache miss.

Hinglish

Origin Request wo request hai jo CloudFront origin server ko bhejta hai jab use fresh content chahiye hota hai, aam taur par cache miss ke baad.

What is an Origin?

Simple English

An Origin is the actual place where your content lives permanently. CloudFront does not create content itself; it just caches and delivers content that comes from an origin, such as an S3 bucket, an EC2 instance, an Application Load Balancer, an API Gateway, or any custom HTTP server.

Hinglish

Origin wo jagah hai jahan aapka content permanently rehta hai. CloudFront khud content nahi banata; wo sirf origin se aane wale content ko cache aur deliver karta hai, jaise S3 bucket, EC2 instance, Application Load Balancer, API Gateway, ya koi custom HTTP server.

   |
   +-- EC2                (single server)
   |
   +-- API Gateway         (serverless APIs)

Simple English

A Distribution is the main configuration unit in CloudFront. When you create one, AWS gives you a unique CloudFront domain name that acts as the entry point between your users and your origin.

Hinglish

Distribution CloudFront ka main configuration unit hota hai. Jab aap ek distribution banate ho, AWS aapko ek unique CloudFront domain name deta hai jo users aur origin ke beech entry point ka kaam karta hai.

Why do we create it?

Simple English

We create a distribution to tell CloudFront exactly which origin to pull content from, how to cache it, which domain names to accept, and what security settings to apply.

Hinglish

Hum distribution isliye banate hain taaki CloudFront ko exactly bataya ja sake ki kaunse origin se content lena hai, use kaise cache karna hai, kaunse domain names accept karne hain, aur kaunsi security settings lagani hain.

08

Edge Location

Simple English

An Edge Location is a small AWS data center placed in many cities around the world, much closer to end users than AWS Regions. CloudFront uses these locations to cache and serve your content quickly.

Hinglish

Edge Location ek chhota AWS data center hota hai jo duniya ki kai cities mein hota hai, aur AWS Regions se kaafi zyada users ke paas hota hai. CloudFront in locations ka use content cache aur fast serve karne ke liye karta hai.

Region vs Edge Location

Simple English

An AWS Region is a large geographic area where your main resources (like EC2 or S3) are hosted. There are far fewer Regions than Edge Locations. Edge Locations exist purely to cache and deliver content closer to users, not to run your main application.

Hinglish

AWS Region ek bada geographic area hota hai jahan aapke main resources (jaise EC2 ya S3) host hote hain. Regions, Edge Locations se kaafi kam hote hain. Edge Locations sirf content cache aur users ke paas deliver karne ke liye hote hain, aapki main application chalane ke liye nahi.

CloudFront Cache

Simple English

Caching means temporarily storing a copy of your content at the edge location. This is useful because it lets CloudFront answer repeated requests instantly, without contacting the origin server every single time.

Hinglish

Caching ka matlab hai content ki ek copy ko temporarily edge location par store karna. Ye isliye useful hai kyunki isse CloudFront baar baar aane wali requests ka jawab turant de sakta hai, har baar origin server se contact kiye bina.

Cache Miss flow

Simple English

On a cache hit, the response is very fast because it never leaves the edge location. On a cache miss, CloudFront has to make an extra trip to the origin, which is slower, but it stores that content so the next request becomes a cache hit.

Hinglish

Cache hit mein response bahut fast hota hai kyunki wo edge location se bahar hi nahi jaata. Cache miss mein CloudFront ko ek extra trip origin tak karni padti hai, jo thodi slow hoti hai, lekin wo content store kar leta hai taaki agli request cache hit ban jaaye.

10

TTL

Simple English

TTL stands for Time To Live. It defines how long CloudFront keeps a piece of content in its cache before it is considered old and needs to be refreshed from the origin.

Hinglish

TTL ka full form hai Time To Live. Ye batata hai ki CloudFront kisi content ko kitni der tak cache mein rakhega, uske baad wo purana maan liya jaata hai aur origin se refresh karna padta hai.

TTL TypeMeaning
Minimum TTLThe smallest amount of time content will stay cached, even if the origin says otherwise.
Maximum TTLThe largest amount of time content is allowed to stay cached.
Default TTLThe TTL CloudFront uses when the origin does not specify any caching headers.

Example: TTL = 3600 seconds

Simple English

If TTL is set to 3600 seconds (1 hour), CloudFront will keep serving the cached copy for 1 hour after it was first stored. During this hour, even if the file changes on the origin, users will still see the old cached version, until the TTL expires or an invalidation is done.

Hinglish

Agar TTL 3600 seconds (1 ghanta) set hai, toh CloudFront cached copy ko store hone ke 1 ghante tak serve karta rahega. Is 1 ghante mein, agar origin par file change bhi ho jaaye, users ko phir bhi purani cached version dikhegi, jab tak TTL expire na ho ya invalidation na ki jaaye.

11

Cache Behavior

Simple English

A Cache Behavior is a set of rules for a specific path pattern that tells CloudFront exactly how to treat requests matching that pattern, including which origin to use, which HTTP methods to allow, and what to include when deciding if two requests are 'the same' (headers, query strings, cookies).

Hinglish

Cache Behavior ek specific path pattern ke liye rules ka set hota hai jo CloudFront ko batata hai ki us pattern se match karne wali requests ko kaise treat karna hai, jaise kaunsa origin use karna hai, kaunse HTTP methods allow karne hain, aur do requests ko 'same' maanne ke liye kya include karna hai (headers, query strings, cookies).

/images/*   -> cache aggressively, long TTL, from S3
/api/*      -> do not cache (or cache very briefly), from ALB
/static/*   -> cache aggressively, long TTL, from S3
Simple English

Different paths often need different caching rules. Static files like images rarely change, so they can be cached for a long time. API responses often change per-user or per-request, so they usually need little or no caching.

Hinglish

Alag alag paths ko aksar alag caching rules chahiye hote hain. Images jaisi static files kam badalti hain, isliye unhe lambe samay tak cache kiya ja sakta hai. API responses aksar har user ya har request ke saath badalte hain, isliye unhe kam ya bilkul cache nahi karna padta.

Simple English

A very common pattern is to store static website files (like a React build) in an S3 bucket, and put CloudFront in front of it. CloudFront caches these files at edge locations, so the site loads fast for users everywhere, and S3 itself receives far less direct traffic.

Hinglish

Ek bahut common pattern ye hai ki static website files (jaise React ka build) S3 bucket mein store ki jaaye, aur CloudFront ko uske aage laga diya jaaye. CloudFront in files ko edge locations par cache karta hai, isliye site har jagah ke users ke liye fast load hoti hai, aur S3 ko khud kaafi kam direct traffic milta hai.

Origin Access Control (OAC)

Simple English

OAC (Origin Access Control) is used so that your S3 bucket can only be accessed through CloudFront, not directly from the public internet. This keeps your S3 bucket private and secure, while CloudFront still handles delivering the content.

Hinglish

OAC (Origin Access Control) is liye use hota hai taaki aapka S3 bucket sirf CloudFront ke through access ho sake, seedha public internet se nahi. Isse aapka S3 bucket private aur secure rehta hai, aur content deliver karne ka kaam CloudFront hi karta hai.

Simple English

Without OAC, someone could bypass CloudFront and hit the S3 bucket URL directly, skipping all your caching and security rules. With OAC set up along with a proper bucket policy, only CloudFront's requests are allowed, so S3 stays protected.

Hinglish

OAC ke bina, koi bhi CloudFront ko bypass karke seedha S3 bucket URL par ja sakta hai, jisse aapke caching aur security rules skip ho jaate hain. OAC aur ek sahi bucket policy set karne se, sirf CloudFront ki requests allow hoti hain, isliye S3 protected rehta hai.

Why place CloudFront before ALB?

Simple English

Even for dynamic applications behind a Load Balancer, putting CloudFront in front adds benefits: it can cache anything that is cacheable, terminate HTTPS closer to the user, and add a layer of protection before traffic even reaches your ALB.

Hinglish

Load Balancer ke peeche chalne wali dynamic applications ke liye bhi, CloudFront ko aage lagana faayde deta hai: jo bhi cacheable hai use cache kar sakta hai, HTTPS ko user ke paas hi terminate kar sakta hai, aur traffic ke ALB tak pahunchne se pehle hi ek protection layer add kar deta hai.

CloudFront Invalidation

Simple English

Invalidation means telling CloudFront to remove a cached file from its edge locations before its TTL naturally expires, so the next request fetches a fresh copy from the origin.

Hinglish

Invalidation ka matlab hai CloudFront ko batana ki wo kisi cached file ko edge locations se hata de, uske TTL naturally expire hone se pehle hi, taaki agli request origin se ek fresh copy laaye.

Why and when do we need it?

Simple English

We need invalidation when we update content (like deploying a new version of a website) but the old version is still cached and TTL has not expired yet. Without invalidation, users would keep seeing the old cached version until TTL runs out.

Hinglish

Invalidation ki zaroorat tab padti hai jab hum content update karte hain (jaise website ka naya version deploy karna) lekin purana version abhi bhi cached hai aur TTL abhi expire nahi hua. Invalidation ke bina, users tab tak purani cached version dekhte rahenge jab tak TTL khatam na ho jaaye.

Interview Questions

Short, natural answers you can speak out loud in an interview.

Q1. What is CloudFront?
EN

CloudFront is AWS's CDN service. It caches content at edge locations worldwide so users get content quickly from a nearby location instead of a distant origin server.

HI

CloudFront AWS ka CDN service hai. Ye content ko duniya bhar ke edge locations par cache karta hai taaki users ko content paas wali jagah se jaldi mile, door wale origin server se nahi.

Q2. What is CDN?
EN

CDN stands for Content Delivery Network, a group of geographically distributed servers that deliver content to users from the location nearest to them.

HI

CDN ka matlab hai Content Delivery Network, geographically alag alag jagah par phaile servers ka group jo users ko unke sabse paas wali location se content deliver karte hain.

Q3. Why do we use CloudFront?
EN

We use it for faster content delivery, lower latency, caching, global reach, reduced load on the origin, easy HTTPS, and built-in security like WAF and DDoS protection.

HI

Hum ise faster content delivery, kam latency, caching, global reach, origin par kam load, aasan HTTPS, aur WAF jaisi built-in security ke liye use karte hain.

Q4. What is an Edge Location?
EN

An Edge Location is a data center in AWS's global network that caches and delivers content close to end users.

HI

Edge Location AWS ke global network mein ek data center hota hai jo end users ke paas content cache aur deliver karta hai.

Q5. What is an Origin?
EN

An Origin is the original source of content, like an S3 bucket, EC2 instance, or ALB, from which CloudFront fetches content when it is not cached.

HI

Origin content ka original source hota hai, jaise S3 bucket, EC2 instance, ya ALB, jahan se CloudFront content fetch karta hai jab wo cached nahi hota.

Q6. What is a CloudFront Distribution?
EN

It's the configuration you create in CloudFront that defines the origin, caching rules, and domain used to serve your content.

HI

Ye wo configuration hai jo aap CloudFront mein banate ho, jo origin, caching rules, aur content serve karne wala domain define karta hai.

Q7. What is Cache Hit?
EN

A Cache Hit is when CloudFront finds the requested content already in its edge cache and returns it directly, without contacting the origin.

HI

Cache Hit tab hota hai jab CloudFront ko requested content pehle se edge cache mein mil jaata hai aur wo use seedha return kar deta hai, origin se contact kiye bina.

Q8. What is Cache Miss?
EN

A Cache Miss is when the content is not in the cache, so CloudFront has to fetch it from the origin first before returning it.

HI

Cache Miss tab hota hai jab content cache mein nahi hota, isliye CloudFront ko use return karne se pehle origin se fetch karna padta hai.

Q9. What is TTL?
EN

TTL, or Time To Live, is how long content stays valid in the cache before CloudFront checks the origin again.

HI

TTL, yaani Time To Live, batata hai content cache mein kitni der tak valid rahega, uske baad CloudFront origin se dobara check karta hai.

Q10. What is Cache Behavior?
EN

A Cache Behavior is a rule for a specific path pattern that decides which origin to use and how to cache requests matching that path.

HI

Cache Behavior ek specific path pattern ke liye rule hota hai jo decide karta hai ki kaunsa origin use karna hai aur us path se match hone wali requests ko kaise cache karna hai.

Q11. What is OAC?
EN

Origin Access Control lets only CloudFront access a private S3 origin, so the bucket cannot be reached directly from the public internet.

HI

Origin Access Control sirf CloudFront ko ek private S3 origin access karne deta hai, isliye bucket seedha public internet se access nahi ho sakta.

Q12. CloudFront vs S3?
EN

S3 is a storage service where files live; CloudFront is a CDN that caches and delivers those files quickly to users worldwide.

HI

S3 ek storage service hai jahan files rehti hain; CloudFront ek CDN hai jo un files ko fast cache aur deliver karta hai duniya bhar ke users ko.

Q13. CloudFront vs Route 53?
EN

Route 53 is DNS, it decides where a request should go; CloudFront is the CDN that delivers content once the request arrives.

HI

Route 53 DNS hai, ye decide karta hai request kahan jaani chahiye; CloudFront wo CDN hai jo request pahunchne ke baad content deliver karta hai.

Q14. CloudFront vs ALB?
EN

CloudFront is a global CDN for caching and delivery; ALB is a regional load balancer that distributes traffic across backend servers.

HI

CloudFront caching aur delivery ke liye ek global CDN hai; ALB ek regional load balancer hai jo traffic ko backend servers mein distribute karta hai.

Q15. What is CloudFront Invalidation?
EN

Invalidation removes cached content from edge locations before its TTL expires, forcing CloudFront to fetch a fresh copy on the next request.

HI

Invalidation cached content ko edge locations se TTL expire hone se pehle hata deta hai, jisse CloudFront agli request par fresh copy fetch karta hai.

Q16. How does CloudFront improve performance?
EN

By caching content near users, reducing latency, offloading traffic from the origin, and handling HTTPS efficiently at the edge.

HI

Content ko users ke paas cache karke, latency kam karke, origin se traffic offload karke, aur HTTPS ko edge par efficiently handle karke.

Q17. How do you use CloudFront with S3?
EN

You create an S3 bucket for your files, set it as the CloudFront origin, secure it with OAC and a bucket policy, then serve content through the CloudFront domain.

HI

Apni files ke liye ek S3 bucket banate ho, use CloudFront ka origin set karte ho, OAC aur bucket policy se secure karte ho, fir content CloudFront domain ke through serve karte ho.

Q18. How do you use CloudFront with ALB?
EN

You set the ALB as the CloudFront origin, so CloudFront caches what it can and adds HTTPS and security in front of your load-balanced backend.

HI

ALB ko CloudFront ka origin set karte ho, taaki CloudFront jo cache kar sake wo kare, aur load-balanced backend ke aage HTTPS aur security add kare.

Q19. How would you use CloudFront in a MERN application?
EN

CloudFront serves the React frontend fast from S3, and can also sit in front of API traffic that goes through ALB to ECS Fargate running Node.js/Express, before it reaches MongoDB.

HI

CloudFront React frontend ko S3 se fast serve karta hai, aur API traffic ke aage bhi reh sakta hai jo ALB se hote hue ECS Fargate mein chal rahe Node.js/Express tak jaata hai, MongoDB tak pahunchne se pehle.

Q20. How do you configure HTTPS with CloudFront?
EN

You request or import a certificate in AWS Certificate Manager, attach it to your CloudFront distribution, and set the viewer protocol policy to require or redirect to HTTPS.

HI

AWS Certificate Manager mein ek certificate request ya import karte ho, use apne CloudFront distribution se attach karte ho, aur viewer protocol policy ko HTTPS require ya redirect karne ke liye set karte ho.
