AWS DynamoDB

AWS DynamoDB — Beginner Study Notes

English + Hinglish • for learning, revision, AWS interview preparation and printing

1. AWS DynamoDB Introduction

AWS DynamoDB = Amazon DynamoDB

Definition Amazon DynamoDB is a fully managed NoSQL database service provided by AWS that provides fast and predictable performance with seamless scalability.
Hinglish DynamoDB AWS ka fully managed NoSQL database service hai. Isme hume database server install ya manage karne ki zarurat nahi hoti. AWS infrastructure ko manage karta hai aur hum mainly apne data aur application par focus karte hain.

What is DynamoDB?

A database service where you store data as items inside tables and read/write it using AWS APIs. You do not create or manage a database server.

Hinglish: DynamoDB mein hum tables banate hain aur unme items (records) store karte hain. Koi database server banana ya chalana nahi padta.

What is NoSQL?

NoSQL databases do not primarily use the traditional relational table structure of SQL databases. Details in section 4.

What does “fully managed” mean?

AWS takes care of servers, hardware, software patching, replication of data across facilities, and scaling infrastructure. You take care of your data model, access patterns, permissions, security and cost.

Hinglish: Fully managed ka matlab: server, hardware, patching, infrastructure AWS sambhalta hai. Data model, permissions, security aur cost hamari zimmedari hai.

Why do we use DynamoDB?

  • Fast, predictable performance for key-based lookups.
  • No server to install or patch.
  • Scales to large traffic.
  • Flexible schema (items can have different attributes).
  • Works well with AWS services (IAM, Lambda, CloudWatch).

Where is DynamoDB useful?

  • User profiles, shopping carts, orders history
  • Session data and temporary data (with TTL)
  • Gaming leaderboards / player data
  • IoT and event data
  • Serverless applications (API Gateway + Lambda + DynamoDB)

Hinglish: Jahan data ko key se fast access karna ho (jaise userId se profile) aur traffic zyada ho sakta ho, wahan DynamoDB achha lagta hai.

2. DynamoDB vs RDS

DynamoDB: NoSQL, key-value/document, serverless/fully managed experience, very fast access, automatic scaling options, flexible schema.

RDS: relational database, SQL, tables/rows/columns, MySQL/PostgreSQL/etc., relationships, SQL queries.

FeatureDynamoDBRDS
Database typeNoSQL (key-value / document)Relational (SQL)
Query styleAPI calls: GetItem, PutItem, Query, Scan (PartiQL is also available)SQL queries (SELECT, JOIN, ...)
SchemaFlexible; only the primary key is fixedFixed columns per table
ScalingDesigned for horizontal scaling; on-demand and provisioned optionsBigger instance (vertical), storage growth, read replicas
RelationshipsNo joins; you design data around access patternsForeign keys and JOINs
ConnectionAWS SDK/CLI over HTTPS + IAM permissionsEndpoint + port (e.g. 3306) + DB username/password
Typical use casesCarts, sessions, profiles, IoT, serverless appsFinancial data, reporting, apps needing joins and complex SQL
Hinglish DynamoDB mein SQL tables aur JOIN nahi hote; data key ke through access hota hai aur design access patterns ke hisaab se hota hai. RDS mein SQL, tables, rows, columns aur relationships hote hain. Dono alag problems ke liye bane hain — ek dusre se universally better nahi hai.

3. Real-World MERN-style Project Example

MERN normally means MongoDB, Express.js, React, Node.js. But a React + Node.js application can also use DynamoDB instead of MongoDB.

User | v React Frontend | v Node.js + Express Backend (on EC2) | v AWS DynamoDB | v Data

Suppose we build an e-commerce application: Frontend = React, Backend = Node.js + Express, Database = DynamoDB, AWS = EC2 runs the Node.js backend.

// User item
{
  "userId": "U101",
  "name": "Tarun",
  "email": "tarun@example.com"
}

// Product item
{
  "productId": "P101",
  "name": "Laptop",
  "price": 50000
}

Request flow

  1. User opens the React application.
  2. React sends an API request.
  3. Node.js/Express receives the request.
  4. Backend communicates with DynamoDB (using the AWS SDK).
  5. DynamoDB returns the requested data.
  6. Backend sends the response to React.
  7. React displays the result.

Hinglish: Flow wahi hai jo normal MERN app ka hota hai; bas Node.js backend MongoDB ke bajay AWS SDK se DynamoDB se baat karta hai.

4. What is NoSQL?

Definition NoSQL databases are databases that do not primarily use the traditional relational table structure of SQL databases.

Hinglish: NoSQL databases mein data mainly SQL ki fixed rows-columns wali relational tables ki tarah store nahi hota. (“NoSQL” ko aksar “Not only SQL” bhi kehte hain.)

DynamoDB supports key-value data and document data.

{
  "userId": "U101",
  "name": "Tarun",
  "age": 24,
  "skills": ["React", "Node.js", "AWS"]
}

Why NoSQL can be useful

  • Flexible data structure: items can have different attributes (lists, nested maps).
  • High scalability: built to spread data and traffic across many machines.
  • Fast access: quick lookups by key.
  • Large-scale applications: good when data and traffic are big.

Hinglish: Flexible structure, high scalability aur fast key-based access ki wajah se NoSQL badi applications mein use hota hai. Iska matlab ye nahi ki har project ke liye NoSQL hi best hai.

5. DynamoDB Table, Item and Attribute

Table A DynamoDB table is a collection of items.
Table | v Items | v Attributes
SQLDynamoDB
Database → Table → Rows → ColumnsTable → Items → Attributes
RowItem
ColumnAttribute

Item = one record/document in DynamoDB. Attribute = a field inside an item.

{
  "userId": "U101",
  "name": "Tarun",
  "email": "tarun@example.com"
}
  • Item: the complete object above.
  • Attributes: userId, name, email.

Hinglish: Table = items ka collection. Item = ek poora record (SQL ki row jaisa). Attribute = item ke andar ka ek field (SQL ke column jaisa). Fark ye hai ki alag items mein alag attributes ho sakte hain.

6. Primary Key, Partition Key and Sort Key

Every DynamoDB table must have a primary key. It uniquely identifies each item. There are two types:

  1. Simple primary key = Partition key only
  2. Composite primary key = Partition key + Sort key

Partition key

The partition key is the main key used to identify items and distribute them internally. Example: userId = U101.

Hinglish Partition key DynamoDB ko batata hai ki item ko kaise identify aur internally distribute karna hai.
Table: Users — Partition Key: userId
U101Tarun
U102Rahul
U103Riya

Composite primary key and Sort key

Sort key A sort key is the second part of a composite primary key and allows related items to be organized and queried together.

Partition key = userId, Sort key = orderId. The combination must be unique.

Table: UsersOrders
userId (PK)orderId (SK)productprice
U101O1001Laptop50000
U101O1002Mouse1000
U102O1003Keyboard2000

Why is this useful? Items with the same partition key are stored together and sorted by the sort key. So DynamoDB can efficiently fetch all orders of one user (userId = U101) with a Query, without checking the whole table.

Hinglish: Partition key se DynamoDB pata kar leta hai ki user ka data kahan hai. Sort key se us user ke orders ek order mein arranged rehte hain, isliye “U101 ke saare orders” jaisi query fast chalti hai.

7. How to Create a DynamoDB Table

  1. Login to the AWS Console.
  2. Search for DynamoDB.
  3. Open Amazon DynamoDB.
  4. Go to Tables.
  5. Click Create table.
  6. Enter the table name, for example Users.
  7. Partition key: userId
  8. Key type: String
  9. Sort key is optional. Add one only when you need a composite key (like orderId). For this first beginner example: Partition key = userId, no sort key.
  10. Keep the other settings simple/default for learning.
  11. Click Create table and wait until the status is Active.
Note DynamoDB configuration options can change over time, and the AWS Console may show different options depending on the current service interface. The main idea (table name + primary key) stays the same.

Hinglish: Console ki screens badalti rehti hain; important cheez table name aur primary key hai. Sort key optional hota hai, aur primary key baad mein change nahi hoti, isliye pehle se soch kar choose karo.

9. CRUD Operations

LetterMeaningDynamoDB operationHinglish
CCreatePutItemNaya item likhna/create karna
RReadGetItemKey se item padhna
UUpdateUpdateItemItem ke attributes badalna
DDeleteDeleteItemItem delete karna

PutItem (create)

PutItem creates/writes an item. If an item with the same primary key already exists, it is replaced (unless you add a condition).

aws dynamodb put-item \
  --table-name Users \
  --item '{
    "userId": {"S": "U101"},
    "name": {"S": "Tarun"},
    "email": {"S": "tarun@example.com"}
  }'

S = String. (Other common types: N = Number, BOOL = Boolean, L = List, M = Map.)

Why is the CLI JSON different? DynamoDB’s low-level API represents attribute types explicitly ({"S": "Tarun"}), so the CLI syntax differs from normal JSON. Normal JSON like "name": "Tarun" is what you use with the Document Client in code (section 15).

Hinglish: Low-level API ko type batana padta hai (S, N, ...). Isliye CLI mein {"S": "Tarun"} likhte hain. PutItem same key par purana item replace kar deta hai, dhyan rakhna.

GetItem (read)

aws dynamodb get-item \
  --table-name Users \
  --key '{
    "userId": {"S": "U101"}
  }'
  • --table-name Users — which table.
  • --key — the full primary key of the item you want (here only userId).

Hinglish: GetItem ko exact primary key chahiye; ye ek hi item wapas deta hai aur bahut fast hota hai.

UpdateItem

aws dynamodb update-item \
  --table-name Users \
  --key '{"userId":{"S":"U101"}}' \
  --update-expression "SET #n = :name" \
  --expression-attribute-names '{"#n":"name"}' \
  --expression-attribute-values '{":name":{"S":"Tarun Rajput"}}'
  • update-expression — what to change: SET #n = :name means “set attribute #n to value :name”.
  • expression-attribute-names — a nickname for an attribute name. #n stands for name. This is needed because name is a DynamoDB reserved word.
  • expression-attribute-values — the actual value. :name stands for "Tarun Rajput".

Hinglish: # se shuru hone wale placeholders attribute ke naam ke liye hote hain, aur : se shuru hone wale placeholders value ke liye. Isse reserved words ki problem nahi aati aur query safe rehti hai.

DeleteItem

aws dynamodb delete-item \
  --table-name Users \
  --key '{
    "userId": {"S": "U101"}
  }'

Deletes the item with that primary key. Hinglish: Ye us key wala item hata deta hai. Delete se pehle sure ho lo, warna backup/PITR se hi recover hoga.

10. Query vs Scan

QueryScan
How it worksUses key conditions (partition key, optionally sort key)Examines items across the whole table/index
EfficiencyGenerally more efficient for targeted accessCan consume more resources, especially on big tables
Typical useGet all orders for user U101Check the entire table to find users where age = 24
In applicationsPreferred for normal access patternsUsually not preferred for large-scale application access patterns
# Query: all orders of user U101 (table with userId + orderId)
aws dynamodb query \
  --table-name UsersOrders \
  --key-condition-expression "userId = :u" \
  --expression-attribute-values '{":u":{"S":"U101"}}'
Hinglish Query = seedha us partition key wale items nikalna (jaise “U101 ke saare orders”). Scan = poori table check karna (jaise “kis user ki age 24 hai?”). Scan chhoti tables ya kabhi-kabhi ke admin kaam ke liye theek hai, lekin badi tables par bar bar Scan chalane se cost aur time dono badhte hain. Isliye Query ke hisaab se table design karo.

Note: a filter on a Scan (like age = 24) is applied after items are read, so you are still charged for reading the items examined.

11. DynamoDB Indexes (GSI and LSI)

An index gives you another way to look up items besides the table’s primary key. Hinglish: Index ek extra “rasta” hai jisse hum primary key ke alawa kisi aur attribute se bhi efficiently search kar sakte hain.

GSI (Global Secondary Index)LSI (Local Secondary Index)
Partition keyCan be different from the base tableSame as the base table
Sort keyCan be different (optional)Different sort key
UseAlternative access patternsAnother sort order within the same partition key
When to createCan be added laterMust be created when the table is created

Simple example (LSI): table UsersOrders has userId + orderId. An LSI with sort key orderDate lets you list one user’s orders sorted by date.

Real project with GSI

Users table: partition key = userId. Suppose we also want to find a user by email (for login).

Base table Users Primary key : userId GSI email-index GSI partition key : email

Now userId lookups use the table, and email lookups use the GSI — two efficient access patterns.

Design tip Design indexes based on your application’s actual query patterns. Every index adds storage and write cost, so do not create unnecessary indexes.

Hinglish: Jitne queries chahiye utne hi indexes banao. Bina zarurat index banane se cost badhti hai.

12. Capacity Modes, RCU and WCU

ModeMeaningHinglish
On-demandPay based on request usage; DynamoDB manages capacity automatically.Jitni requests, utna payment. Capacity planning ki tension nahi.
ProvisionedYou specify read/write capacity settings and manage capacity planning, with scaling options (auto scaling) available.Hum khud read/write capacity set karte hain; traffic predictable ho to suitable.

RCU and WCU

  • RCU = Read Capacity Unit
  • WCU = Write Capacity Unit

Conceptually: a read operation consumes read capacity, and a write operation consumes write capacity. Actual consumption depends on item size and the operation characteristics (for example consistency type, or whether it is a Query or a Scan). Bigger items and bigger scans use more capacity.

Hinglish: Read karne par RCU kharch hota hai, write karne par WCU. Item jitna bada, ya operation jitna heavy (jaise Scan), capacity utni zyada use hoti hai. Exact calculation ke liye AWS ka current documentation dekho.

13. DynamoDB Scaling and the Serverless Concept

DynamoDB is designed for horizontal scalability:

  • Handles large amounts of traffic
  • Automatically manages infrastructure
  • Supports scaling options (on-demand, or provisioned with auto scaling)
  • Can handle very high request volumes when tables are designed well
Hinglish Traffic badhne par DynamoDB ko traditional server ki tarah manually CPU/RAM increase karne ki zarurat nahi hoti. DynamoDB service scaling ko manage karne ke liye designed hai.

Serverless concept

DynamoDB is commonly used as a serverless database.

14. Access DynamoDB from Node.js (AWS SDK v3)

npm install @aws-sdk/client-dynamodb
const {
  DynamoDBClient,
  PutItemCommand
} = require("@aws-sdk/client-dynamodb");

const client = new DynamoDBClient({
  region: process.env.AWS_REGION
});
  • require("@aws-sdk/client-dynamodb") — SDK package import karta hai.
  • DynamoDBClient — DynamoDB se baat karne wala client object.
  • PutItemCommand — “item likho” wali command ka class.
  • region: process.env.AWS_REGION — kaunse AWS region (jaise eu-north-1) ke DynamoDB se baat karni hai; environment variable se aata hai.

Now write an item:

const command = new PutItemCommand({
  TableName: "Users",
  Item: {
    userId: { S: "U101" },
    name: { S: "Tarun" },
    email: { S: "tarun@example.com" }
  }
});

await client.send(command);
  • TableName — kis table mein likhna hai.
  • Item — item ka data; har value ke saath type (S = String) likhna padta hai.
  • client.send(command) — command ko AWS ko bhejta hai. await ka matlab result aane tak ruko.

Note: await works inside an async function (or top-level in ES modules). No access keys are written in this code: the SDK finds credentials automatically (see section 17).

15. DynamoDB Document Client (Easier Way)

npm install @aws-sdk/client-dynamodb @aws-sdk/lib-dynamodb
const { DynamoDBClient } = require("@aws-sdk/client-dynamodb");
const {
  DynamoDBDocumentClient,
  PutCommand,
  GetCommand
} = require("@aws-sdk/lib-dynamodb");

const client = new DynamoDBClient({ region: process.env.AWS_REGION });
const docClient = DynamoDBDocumentClient.from(client);

async function demo() {
  // Create / write
  await docClient.send(new PutCommand({
    TableName: "Users",
    Item: { userId: "U101", name: "Tarun", age: 24 }
  }));

  // Read
  const result = await docClient.send(new GetCommand({
    TableName: "Users",
    Key: { userId: "U101" }
  }));

  console.log(result.Item);
}

demo();
Why Document Client is easier With the Document Client, developers work with normal JavaScript values ("Tarun", 24) instead of manually specifying DynamoDB attribute types ({ S: "Tarun" }, { N: "24" }).

Hinglish: Document Client mein normal JS objects use karte hain, type (S/N) likhne ki tension nahi. Zyada tar Node.js projects mein ye asaan padta hai.

16. Node.js + Express + DynamoDB API

React | v Express API | v DynamoDB
MethodRouteDynamoDB operation
POST/api/usersPutCommand
GET/api/users/:idGetCommand
PUT/api/users/:idUpdateCommand
DELETE/api/users/:idDeleteCommand
const express = require("express");
const { randomUUID } = require("crypto");
const { DynamoDBClient } = require("@aws-sdk/client-dynamodb");
const {
  DynamoDBDocumentClient, PutCommand, GetCommand, UpdateCommand, DeleteCommand
} = require("@aws-sdk/lib-dynamodb");

const app = express();
app.use(express.json());

const docClient = DynamoDBDocumentClient.from(
  new DynamoDBClient({ region: process.env.AWS_REGION })
);
const TABLE = "Users";

// POST /api/users
app.post("/api/users", async (req, res) => {
  const { name, email } = req.body;
  if (!name || !email) {
    return res.status(400).json({ error: "name and email are required" });
  }
  const user = { userId: randomUUID(), name, email };
  await docClient.send(new PutCommand({ TableName: TABLE, Item: user }));
  res.status(201).json(user);
});

// GET /api/users/:id
app.get("/api/users/:id", async (req, res) => {
  const out = await docClient.send(new GetCommand({
    TableName: TABLE, Key: { userId: req.params.id }
  }));
  if (!out.Item) return res.status(404).json({ error: "Not found" });
  res.json(out.Item);
});

// PUT /api/users/:id  (update name)
app.put("/api/users/:id", async (req, res) => {
  const out = await docClient.send(new UpdateCommand({
    TableName: TABLE,
    Key: { userId: req.params.id },
    UpdateExpression: "SET #n = :name",
    ExpressionAttributeNames: { "#n": "name" },
    ExpressionAttributeValues: { ":name": req.body.name },
    ReturnValues: "ALL_NEW"
  }));
  res.json(out.Attributes);
});

// DELETE /api/users/:id
app.delete("/api/users/:id", async (req, res) => {
  await docClient.send(new DeleteCommand({
    TableName: TABLE, Key: { userId: req.params.id }
  }));
  res.status(204).end();
});

app.listen(3000, () => console.log("API running on port 3000"));

Simplified for learning: real apps also need error handling (try/catch), authentication and stricter validation. Note that this update would create the item if the id does not exist; add a condition expression if you want to prevent that.

What happens on POST /api/users?

Request body:
{
  "name": "Tarun",
  "email": "tarun@example.com"
}
  1. Backend validates the request (name and email present).
  2. Backend generates a userId (a unique id).
  3. Backend writes the item to DynamoDB (PutCommand).
  4. Backend returns a response with the created user.

Hinglish: Pehle request check hoti hai, phir unique userId banti hai, phir DynamoDB mein item save hota hai, aur last mein response React ko jata hai.

17. Environment Variables and AWS Credentials

AWS_REGION=
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
Do NOT hard-code credentials Never write access keys in source code, Dockerfiles or notes pushed to GitHub. Keep any .env file out of Git (.gitignore).
  • Local development: configure credentials with the AWS CLI credential/configuration mechanism (aws configure). The SDK reads them automatically, so your code needs only AWS_REGION (or a configured default region).

Hinglish: Access keys code mein kabhi mat likho. Local machine par aws configure use karo, aur EC2 par IAM Role lagao, taaki long-term keys server par rakhni hi na padein.

18. EC2 + DynamoDB and the IAM Role

Internet | v EC2 | v Node.js / Express | v DynamoDB

EC2 runs the backend, the backend uses the AWS SDK, and DynamoDB stores the data.

Why does EC2 need an IAM Role?

DynamoDB is protected by IAM. Your app must have permission to call DynamoDB operations. The clean way is:

EC2 | v IAM Role (attached to the instance) | v DynamoDB permissions

Example permission concept (actions):

dynamodb:GetItem
dynamodb:PutItem
dynamodb:UpdateItem
dynamodb:DeleteItem
dynamodb:Query

Example policy idea (limited to one table; replace region, account and table name):

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "dynamodb:GetItem", "dynamodb:PutItem",
      "dynamodb:UpdateItem", "dynamodb:DeleteItem",
      "dynamodb:Query"
    ],
    "Resource": "arn:aws:dynamodb:eu-north-1:<ACCOUNT_ID>:table/Users"
  }]
}
Least privilege Give only the actions and only the tables the app needs. Do not attach AdministratorAccess just to use DynamoDB.

Hinglish: EC2 ko DynamoDB use karne ki permission IAM Role se milti hai. Role mein sirf zaroori actions aur sirf zaroori table do — ye least privilege hai.

19. Does DynamoDB Need Port 3306?

NO. DynamoDB is not MySQL. There is no MySQL-style port 3306 that you open in a Security Group for normal DynamoDB API access. The application normally communicates with DynamoDB through AWS service APIs over HTTPS.
RDS MySQLDynamoDB
Port = 3306AWS API over HTTPS
Connect with DB username/passwordConnect with AWS credentials / IAM role
Control network access with Security GroupControl access with IAM policies
Hinglish RDS MySQL mein hum 3306 port aur security group rule use karte hain. DynamoDB mein aisa nahi hota: app AWS SDK ke through HTTPS API call karti hai, aur permission IAM se control hoti hai. Isliye DynamoDB ke liye 3306 kholne ki koi zarurat nahi.

20. Access DynamoDB from Outside AWS, Windows and Endpoint

DynamoDB is an AWS managed service accessed through AWS APIs. A developer’s local computer can use:

  • AWS CLI
  • AWS SDK
  • AWS Console

Authentication/authorization is done using AWS credentials (or another appropriate identity mechanism), and access depends on IAM permissions.

aws dynamodb list-tables --region eu-north-1

aws dynamodb scan --table-name Users --region eu-north-1

Use Scan only on small learning tables. Unlike a public RDS database, you do not normally expose DynamoDB by opening port 3306 to the internet.

Hinglish: Bahar se access ke liye bas AWS CLI/SDK/Console aur sahi IAM permission chahiye. Koi port kholne ki zarurat nahi.

Local Windows access

  1. Install AWS CLI, then check it: 
    aws --version
  2. Configure credentials: 
    aws configure
    Enter: Access Key ID, Secret Access Key, Default region (for example eu-north-1) and Output format (for example json).
  3. Test: 
    aws dynamodb list-tables --region eu-north-1
Handle keys carefully Long-term access keys should be handled carefully and never committed to GitHub. Use least-privilege IAM users/roles and rotate or delete keys you no longer need.

DynamoDB endpoint

DynamoDB does not work like RDS, where you usually get a database-specific hostname (endpoint) for your instance. Instead, the AWS SDK/CLI uses the AWS regional DynamoDB service endpoint for the region you select (for example eu-north-1), and it does this automatically. There is no separate endpoint per table.

RDS : Application -> RDS endpoint (host:3306) -> Database DynamoDB : Application -> AWS SDK / API (region) -> DynamoDB

Hinglish: RDS mein hum ek alag endpoint (hostname) se connect karte hain. DynamoDB mein bas region choose karte hain; SDK khud sahi regional service endpoint use kar leta hai.

21. DynamoDB Security

  • IAM: controls who can do what in AWS.
  • IAM Policies: JSON rules that allow/deny actions on resources (e.g. dynamodb:GetItem on the Users table).
  • IAM Roles: temporary permissions for EC2, Lambda, etc., without long-term keys.
  • Encryption: encryption at rest is managed by AWS by default, with options for customer-managed KMS keys. Data in transit uses HTTPS.
  • Least privilege: only the needed actions on only the needed tables.
  • AWS credentials: keep secret, never hard-code, prefer roles.
  • CloudTrail: records API activity for auditing who did what.
  • VPC endpoints (where appropriate): let resources inside a VPC reach DynamoDB privately without going through the public internet.

Hinglish: DynamoDB ki security mostly IAM se hoti hai: kaun access kar sakta hai, kaunse actions kar sakta hai. Encryption default hota hai, aur CloudTrail se audit hota hai. Private network se access chahiye to VPC endpoint use kar sakte ho.

22. DynamoDB Backup

  • Point-in-time recovery (PITR): when enabled, lets you restore a table to a chosen point within the recovery window.
  • On-demand backups: a backup you create manually at a moment in time.
  • Restore: creates a new table from a backup or PITR point.

Example: If important data is accidentally deleted, backup/recovery features can help recover data depending on the configured recovery options (for example, PITR must have been enabled beforehand).

Hinglish: PITR on rakho to kisi purane time par table restore kar sakte ho. On-demand backup hum khud lete hain. Restore hamesha nayi table banata hai.

23. DynamoDB TTL (Time To Live)

TTL = Time To Live. TTL allows items to be automatically removed after their expiration time.

{
  "otp": "123456",
  "expiresAt": 1750000000   // Unix time in seconds
}

You choose one attribute (here expiresAt) as the TTL attribute, holding a Unix epoch time in seconds. After that time, DynamoDB deletes the item in the background.

Useful for: OTPs, temporary sessions, temporary cache-like data, expiring records.

Note TTL deletion is a background process and is not guaranteed to happen at the exact second of expiry. If your app must never use expired data, also check the expiry time in your code.

Hinglish: TTL se purana data apne aap delete ho jata hai. Delete thodi der baad hota hai, isliye app mein bhi expiry check rakho.

24. DynamoDB Streams

DynamoDB Streams capture changes to items (create, update, delete) in order.

User updated | v DynamoDB | v DynamoDB Stream | v Lambda | v Send notification / process event

Hinglish: Jab table mein koi item add/update/delete hota hai, Stream us change ka record rakhta hai. Lambda us record ko padhkar kaam kar sakta hai, jaise notification bhejna ya kisi aur system ko update karna.

28. Real E-commerce Example and Design Thinking

Table: Orders • Partition key: userId • Sort key: orderId

userId (PK)orderId (SK)productpricestatus
U101O1001Laptop50000Delivered
U101O1002Mouse1000Shipped

To get all orders for U101, run a Query with partition key U101.

aws dynamodb query \
  --table-name Orders \
  --key-condition-expression "userId = :u" \
  --expression-attribute-values '{":u":{"S":"U101"}}'

Why is this efficient? All items with the same partition key are stored together, so DynamoDB goes straight to that user’s items instead of reading the whole table.

Design DynamoDB tables based on access patterns

In traditional SQL, developers often start by designing normalized tables. In DynamoDB, first ask: “What queries does my application need?”

Requirement: “Get all orders of a user.” Design: Partition key = userId, Sort key = orderId.

Hinglish SQL mein hum pehle tables design karte hain, phir queries likhte hain. DynamoDB mein ulta hota hai: pehle sochte hain ki app ko kaunse queries chahiye (access patterns), phir unke hisaab se partition key aur sort key choose karte hain.

29. Common DynamoDB Mistakes

  1. Using Scan for everything — expensive and slow on big tables; prefer Query with good keys.
  2. Poor partition key design — e.g. a key where most requests hit the same value (a “hot” partition).
  3. Giving excessive IAM permissions — use least privilege; avoid AdministratorAccess.
  4. Hard-coding AWS credentials — use roles / credential configuration.
  5. Ignoring item size — large items cost more and there is an item size limit.
  6. Creating unnecessary indexes — each index adds cost.
  7. Not thinking about access patterns — design starts from queries.
  8. Ignoring cost — check pricing, capacity mode, backups, streams.
  9. Using DynamoDB like a relational SQL database — it has no joins; design differently.
  10. Not planning for high-traffic access patterns — think about key distribution and capacity early.

Hinglish: Sabse badi galti: DynamoDB ko MySQL ki tarah use karna. Access patterns pehle socho, Scan kam use karo, aur permissions tight rakho.

30. Cost, Monitoring and Throttling

Cost

DynamoDB pricing can depend on:

  • Read/write usage
  • Storage
  • On-demand or provisioned capacity
  • Backups
  • Streams
  • Other enabled features (indexes, global tables, etc.)
Cost warning DynamoDB is not always free. AWS Free Tier availability and limits can change, so verify the current AWS pricing and Free Tier terms, and watch your billing dashboard.

Hinglish: Cost read/write, storage, backups, streams sab par depend karti hai. Free tier ke rules badalte rehte hain, isliye current AWS pricing page check karo.

Monitoring

Amazon CloudWatch can monitor DynamoDB. Common metrics:

MetricSimple meaning
Read capacity (consumed)How much read capacity your app is using.
Write capacity (consumed)How much write capacity your app is using.
Throttled requestsRequests rejected/delayed because capacity was exceeded.
Successful request latencyHow long successful requests take.
Consumed capacityTotal capacity used; helps plan cost and limits.

Throttling

Definition Throttling happens when requests exceed the available capacity for the relevant operation/partition.

Application design, capacity mode, partition-key distribution and traffic patterns all matter. A good key spreads requests evenly; a “hot” key can cause throttling even if total traffic looks small. SDKs automatically retry throttled requests, but repeated throttling means you should review your design or capacity settings.

Hinglish: Jab requests available capacity se zyada ho jaati hain to DynamoDB kuch requests ko throttle kar deta hai. Isse bachne ke liye partition key achhi choose karo aur capacity mode sahi rakho.

31. DynamoDB Interview Questions & Answers

Q1. What is DynamoDB?
A fully managed NoSQL database service from AWS with fast, predictable performance and easy scaling.
Q2. Is DynamoDB SQL or NoSQL?
NoSQL (key-value and document). It is not a relational database.
Q3. What is a DynamoDB table?
A collection of items.
Q4. What is an item?
One record in a table, like a row in SQL.
Q5. What is an attribute?
A field inside an item, like a column value in SQL.
Q6. What is a partition key?
The main key used to identify items and distribute them internally, e.g. userId.
Q7. What is a sort key?
The second part of a composite key; it organizes items within the same partition key so they can be queried together.
Q8. What is a composite primary key?
Partition key + sort key, e.g. userId + orderId. The combination must be unique.
Q9. Difference between Query and Scan?
Query uses key conditions and is generally efficient for targeted access. Scan examines items across the table/index and can be costly on large tables.
Q10. What is a GSI?
Global Secondary Index: an index with a different partition key (and optional sort key) for alternative access patterns; can be added later.
Q11. What is an LSI?
Local Secondary Index: same partition key as the table but a different sort key; must be created when the table is created.
Q12. What is DynamoDB TTL?
Time To Live: automatically removes items after an expiry time stored in a TTL attribute (Unix seconds).
Q13. What is DynamoDB Streams?
A feature that captures item changes so other services like Lambda can react to them.
Q14. What is RCU?
Read Capacity Unit: measures read capacity consumed; depends on item size and read type.
Q15. What is WCU?
Write Capacity Unit: measures write capacity consumed; depends on item size.
Q16. What is on-demand capacity?
Pay per request; DynamoDB manages capacity automatically.
Q17. What is provisioned capacity?
You set read/write capacity and plan it, with auto scaling options available.
Q18. How does EC2 access DynamoDB?
The app uses the AWS SDK over HTTPS, with permissions from an IAM role attached to the EC2 instance.
Q19. Does DynamoDB require port 3306?
No. That is MySQL. DynamoDB is accessed through AWS APIs over HTTPS.
Q20. How can a local computer access DynamoDB?
With AWS CLI, SDK or Console, using AWS credentials that have IAM permission.
Q21. How is DynamoDB different from RDS?
DynamoDB is NoSQL, key-based, no joins, accessed via API and IAM. RDS is relational SQL with tables, joins, endpoint and port.
Q22. How is DynamoDB different from MongoDB?
DynamoDB is an AWS-managed key-value/document service integrated with IAM; MongoDB is a document database with its own ecosystem (Atlas is its managed service). They are different products, each with strengths.
Q23. How do you secure DynamoDB?
IAM least-privilege policies and roles, no hard-coded credentials, encryption (default, optionally KMS), CloudTrail auditing, VPC endpoints where appropriate.
Q24. How do you connect Node.js with DynamoDB?
Install AWS SDK v3 (@aws-sdk/client-dynamodb, or lib-dynamodb for the Document Client), create a client with the region, and send commands like PutCommand/GetCommand.
Q25. Why use IAM roles instead of hard-coded AWS credentials on EC2?
Roles give temporary, automatically rotated credentials, so no long-term keys are stored on the server or leaked in code, and permissions can be limited.
