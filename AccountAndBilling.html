⚠️ Real-World Pricing & Free Tier Disclaimer

AWS pricing, tier limits, and eligible instance types evolve over time and vary slightly across geographic Regions. Always confirm current rates on the official AWS Pricing and Free Tier pages before making business decisions. These study notes focus on core concepts, architecture, and practical governance.

THEORY 1. What is an AWS Account?

"An AWS Account is a secure, isolated container that holds all your AWS cloud resources, users, security credentials, and financial billing records."

Think of an AWS Account like your private safe-deposit locker inside Amazon's global data center building. Everything you build on AWS — virtual servers (EC2), object storage buckets (S3), relational databases (RDS) — lives inside this single account container, and all monthly charges link directly to it.

Key Elements Inside an AWS Account:

  • AWS Account ID: A unique 12-digit number (e.g., 123456789012) that permanently identifies your account.
  • Root User: The master administrative identity created at initial signup with full, unrestricted access.
  • IAM Users & Roles: Individual sub-identities and temporary permission sets created for engineers and microservices.
  • AWS Resources: The actual compute, networking, and database workloads you deploy.
  • Billing & Cost Management: The tracking engine that calculates consumption and generates invoices.

Every operational and security boundary traces back to this hierarchy. Without an account container, no AWS service can be provisioned or metered.

THEORY 3. The Root User

The Root User is the super-administrator identity created automatically when you first sign up for AWS with an email address and password. It possesses total, irrevocable control over every resource, setting, and financial detail in the account.

Why You Must Never Use the Root User for Daily Tasks:

  • Infinite Power: Root access cannot be restricted by IAM policies. A single accidental click can terminate your entire production database or delete your VPC.
  • Catastrophic Breach Risk: If Root credentials are stolen, an attacker can spin up thousands of expensive crypto-mining servers or permanently delete your backups.
🔒 Essential Root User Security Checklist:
  • Enable Multi-Factor Authentication (MFA): Require a hardware security key (YubiKey) or authenticator app (Google Authenticator) on every login.
  • Lock Away Root Credentials: Use a long (20+ character) unique password and store it in an enterprise password vault.
  • Never Generate Root Access Keys: Do not create programmatic CLI access keys for the Root User.
  • Use IAM for Daily Work: Create dedicated IAM users or federated SSO logins with least-privilege permissions.

THEORY 4. IAM Users & The Principle of Least Privilege

An IAM (Identity and Access Management) User is an identity that you create inside your AWS account for a specific team member, developer, or automated application with strictly scoped permissions.

Core Components of an IAM User:

  • Username & Password: Used to sign in to the AWS Management Console via a custom account URL.
  • Access Keys (Access Key ID + Secret Access Key): Cryptographic credentials used to interact with AWS via CLI, SDKs, or APIs.
  • IAM Policies: JSON documents attached to users or groups that define exact actions allowed or denied (e.g., allow S3 read-only, deny EC2 deletion).

Root User vs IAM User Comparison:

Attribute Root User IAM User

THEORY 5 & 6. AWS Account ID, Alias, Regions & Availability Zones

5. Account ID vs Account Alias

Your Account ID is a permanent 12-digit number (e.g., 559988112233). An Account Alias is a human-friendly name (e.g., acme-corp-prod) that replaces the 12-digit number in the console sign-in URL:

Standard Sign-in URL: https://559988112233.signin.aws.amazon.com/console
Custom Alias Sign-in URL: https://acme-corp-prod.signin.aws.amazon.com/console

6. Global Regions, AZs & Financial Impact

AWS operates across dozens of physical Regions worldwide, each housing multiple isolated Availability Zones (AZs). Pricing varies between Regions due to local real estate, electricity, and telecommunication costs. Deploying resources in Stockholm (eu-north-1) or N. Virginia (us-east-1) may carry different hourly rates than São Paulo (sa-east-1).

THEORY 7 & 8. AWS Billing Fundamentals & Billing Dashboard

AWS Billing operates on a consumption-based Pay-as-you-go model. You pay only for the exact compute seconds, gigabytes stored, or data transmitted, with zero mandatory upfront commitments.

8. The Billing & Cost Management Dashboard

The Billing Dashboard is your financial control center, displaying:

  • Current Month-to-Date Balance: Real-time accrued expenditure for the active billing cycle.
  • Month-End Cost Forecast: Machine-learning projected spending based on current run-rate.
  • Spend by Service & Region: Visual breakdown highlighting which services drive costs.

How to Open the Billing Dashboard:

  1. Sign in to the AWS Management Console.
  2. Click your account name/ID in the top-right navigation bar.
  3. Select Billing and Cost Management.

THEORY 9 & 10. AWS Free Tier & Cloud Pricing Models

9. The 3 Types of AWS Free Tier Offers

Free Tier Model How it Works Common Service Examples
12-Months Free Available for the first 12 months following account activation. 750 hrs/mo t2.micro / t3.micro EC2, 5 GB S3 standard storage, 750 hrs/mo RDS db.t3.micro.
Always Free Never expires; available to all AWS accounts indefinitely up to monthly limits. 1,000,000 AWS Lambda requests/month, 25 GB Amazon DynamoDB storage, 10 custom CloudWatch metrics.
Short-Term Trials Time-bound trial periods activated on first use of a specific service. Amazon Redshift (2-month free trial), Amazon Inspector (15-day trial).

10. The 5 Pillars of AWS Pricing

  • 1. Compute: Billed per millisecond/hour while instances run (EC2, ECS, Lambda).
  • 2. Storage: Billed per GB-month for data retained on disks (EBS, S3, EFS).
  • 3. Data Transfer OUT: Billed per GB for data exiting AWS to the public internet (inbound data is free).
  • 4. API Requests: Billed per million operations (S3 PUT/GET, DynamoDB read/write units).
  • 5. Dedicated Static IPs & Gateways: Hourly charges for provisioned gateways (NAT Gateway) or unattached Elastic IPs.

THEORY 15, 16 & 17. PAYMENTS, INVOICES & COST ALLOCATION TAGS

15. Payment Methods & Verification

AWS requires a valid credit/debit card upon signup for identity verification and overage billing. If a monthly transaction fails (due to expiry, international transaction blocks, or insufficient balance), AWS attempts retries before placing the account in restricted status.

16. Itemized Invoices

At the close of each billing cycle (1st of every month), AWS finalizes an official tax invoice itemizing charges by service, consumption tier, and local regulatory taxes (GST/VAT). You can view and download invoices in PDF and CSV format under the Bills / Invoices tab.

17. Cost Allocation Tags

Tags are custom key-value pairs assigned to resources (e.g., Project = MERN-App, Environment = Production). Once activated in the Cost Allocation Tags console, you can filter and visualize costs per business project in Cost Explorer:

THEORY 18 & 19. COST OPTIMIZATION STRATEGIES & TOP COST DRIVERS

18. 10 Golden Rules of AWS Cost Optimization

  • 1. Terminate Idle EC2 Instances: A running server consumes money every second, even if CPU usage is 0%.
  • 2. Delete Unattached EBS Volumes: When you terminate an EC2 instance, verify whether attached EBS storage volumes were orphaned.
  • 3. Release Disassociated Elastic IPs: AWS charges an hourly penalty for public IPv4 addresses not actively mapped to running instances.
  • 4. Clean Up Forgotten S3 Buckets & Snapshots: Stale backups and raw log files accumulate storage fees indefinitely.
  • 5. Monitor NAT Gateways: NAT Gateways charge ~$0.045/hour (~$32/month) plus data processing. Use Gateway Endpoints for S3/DynamoDB instead!
  • 6. Delete Empty Load Balancers: Application Load Balancers incur hourly base charges regardless of whether requests are received.
  • 7. Right-Size Workloads: Do not run a t3.xlarge when a t3.micro handles the memory load comfortably.
  • 8. Use S3 Lifecycle Policies: Automatically transition older objects to S3 Infrequent Access or Glacier deep archive.
  • 9. Leverage AWS Savings Plans & Reserved Instances: Commit to 1 or 3-year steady-state workloads for up to 72% discounts.
  • 10. Automate Shutdown Schedules: Stop staging/dev servers during nights and weekends using AWS Instance Scheduler or Lambda.

21. Essential Financial Security Controls

  • Never Hardcode API Keys: Never commit AWS Access Keys to public GitHub repositories. Automated bots scan commits within seconds and launch unauthorized crypto-mining servers.
  • Activate IAM User Access to Billing: By default, IAM users cannot view billing. The Root user must explicitly activate "IAM User and Role Access to Billing Information" in Account Settings.
  • Set Dual Alert Thresholds: Configure budgets for both Actual and Forecasted spend to catch run-rate spikes before month-end.

PRACTICAL 22 & 23. PRACTICAL LABS: AUDIT COSTS & FIND RUNNING RESOURCES

22. Step-by-Step: Identify Top Cost-Driving Services

  1. Open Cost Explorer from the Billing console left menu.
  2. Set Date range to Current month or Last 30 days.
  3. Set Granularity to Daily or Monthly.
  4. Click the Group by dropdown and select Service.
  5. Review the stacked bar chart. Identify the highest bar (e.g., EC2-Other or RDS) to pinpoint where your cloud budget is being consumed.

23. Step-by-Step: Hunting & Terminating Orphaned Resources

  1. EC2 Instances: Open EC2 Console → Instances → filter by Instance state = running. Stop/terminate unused servers.
  2. EBS Volumes: In EC2 Console → Volumes → filter by State = available (unattached disks). Select → Actions → Delete volume.
  3. Elastic IPs: In EC2 Console → Elastic IPs → check for entries with no Associated instance ID. Select → Actions → Release Elastic IP addresses.
  4. NAT Gateways: Open VPC Console → NAT Gateways → select test gateway → Actions → Delete NAT Gateway.
  5. Load Balancers: In EC2 Console → Load Balancers → select test ALB → Actions → Delete load balancer.

INTERVIEW 26. TOP 25+ AWS BILLING & ACCOUNT INTERVIEW QUESTIONS & ANSWERS

Q1. What is an AWS Account, and how does it act as an isolation boundary?

An AWS Account is the foundational security, administrative, and financial container in the AWS cloud. Every resource created belongs strictly to one account. By default, resources in one account cannot see, access, or communicate with resources in another account unless explicit cross-account IAM roles, VPC Peering, or AWS Resource Access Manager (RAM) shares are configured.

Key takeaway: Account boundaries provide 100% blast-radius containment for enterprise security and cost segregation.
Q2. What is the AWS Root User, and why should you NEVER use it for daily administrative work?

The Root User is the master identity created when the AWS account is first registered using an email address and password. It possesses absolute, unrestricted privileges across all AWS services, resources, and billing operations. Using it for daily tasks presents catastrophic risks: if root credentials leak or a human mistake occurs, entire production infrastructures can be deleted with zero recovery.

Key takeaway: Secure Root with hardware/virtual MFA, lock away its credentials, and perform 100% of daily engineering through scoped IAM users or roles.
Q3. What is the Principle of Least Privilege in IAM, and why is it vital for cost governance?

The Principle of Least Privilege states that users, roles, applications, or services should be granted only the absolute minimum permissions strictly necessary to perform their assigned job functions. From a cost governance perspective, this prevents unauthorized developers or test scripts from spinning up expensive GPU compute instances, enterprise RDS clusters, or high-throughput NAT Gateways.

Key takeaway: Always start with zero permissions, scope actions to specific resource ARNs, and restrict instance types using IAM policy conditions.
Q4. What is the Pay-As-You-Go pricing model, and how does AWS calculate resource billing?

Pay-as-you-go means you pay strictly for the actual cloud capacity you consume per second, minute, or hour, with zero upfront capital investment (CapEx) and zero long-term commitments. Compute is billed per second/minute of running state, storage is billed per GB-month, and outbound internet traffic is billed per GB. When a resource is stopped or deleted, ongoing compute charges immediately halt.

Key takeaway: Transforms heavy upfront capital expenditures into flexible, pay-for-what-you-use operating expenses (OpEx).
Q5. What is the exact difference between AWS Budgets and AWS Cost Explorer?

Cost Explorer is a reactive and diagnostic reporting tool used for visual graphing, root-cause cost breakdown, historical spending analysis, and future trend forecasting. AWS Budgets is a proactive governance tool that allows you to set custom monthly spending or usage limits (e.g., $100/month) and triggers automated email/SNS alerts or automated actions (e.g., attaching SCPs) when actual or forecasted costs cross your defined thresholds.

Key takeaway: Cost Explorer tells you where money was spent; AWS Budgets alerts you before you overspend.
Q6. What are the three distinct categories of the AWS Free Tier?

1) 12-Months Free: Available for the first 12 months after account creation (e.g., 750 hours/month of t2.micro/t3.micro EC2, 5 GB S3 Standard storage, 750 hours RDS Single-AZ).
2) Always Free: Never expires, available to all accounts indefinitely (e.g., 1 Million AWS Lambda requests/month, 25 GB DynamoDB NoSQL storage, 10 custom CloudWatch alarms).
3) Short-Term Trials: Time-limited trials that activate when a specific service is first used (e.g., Amazon GuardDuty 30-day trial, Redshift 2-month trial).

Key takeaway: Free tier limits are calculated per calendar month; any consumption exceeding the allocated limits is billed at standard On-Demand rates.
Q7. How does AWS charge for Data Transfer (Inbound vs Outbound vs Inter-Region)?

Inbound Data Transfer (uploading data from the internet into AWS) is always 100% Free. Outbound Data Transfer (downloading/serving data from AWS out to the public internet) is charged per GB (first 100 GB/month is free globally across all services, then ~$0.09/GB). Data transfer between AWS Regions is billed at ~$0.02/GB, and data transfer across different Availability Zones (AZs) in the same region incurs ~$0.01/GB in each direction.

Key takeaway: Serving heavy file or video downloads directly from EC2 is expensive; caching static assets via Amazon CloudFront dramatically lowers egress costs.
Q8. Why does an unallocated or unattached Elastic IP (EIP) cost money?

Public IPv4 addresses are scarce global internet resources. To prevent developers from allocating and hoarding public IPv4 addresses without actively utilizing them, AWS charges an hourly fee (~$0.005/hour) whenever an allocated Elastic IP is not mapped to an active, running EC2 instance or Network Interface (ENI).

Key takeaway: Always release unattached Elastic IPs immediately in the VPC Console to eliminate unnecessary recurring idle fees.
Q9. What are Cost Allocation Tags, and what must be done before they appear in billing reports?

Cost Allocation Tags are key-value metadata labels (e.g., Environment: Production, Project: MERN-Store, CostCenter: Engineering) attached to AWS resources. Tags do NOT appear in billing dashboards or Cost Explorer automatically. An administrator must navigate to Billing Console → Cost Allocation Tags and explicitly Activate the desired user-defined or AWS-generated tags. Once activated, AWS indexes the tagged costs within 24 hours.

Key takeaway: Tagging is the essential foundation for showback and chargeback accounting across corporate departments.
Q10. What happens if an AWS monthly invoice payment fails or the registered card expires?

When an automatic card payment fails, AWS sends immediate email notifications to the account root and alternate billing contacts. AWS retries payment attempts periodically over several days. If payment remains unpaid for 30–60 days, AWS enters a grace period and will eventually restrict new resource creation, stop running EC2 instances, and ultimately suspend the entire account until the outstanding invoice is resolved.

Key takeaway: Always configure Alternate Billing Contacts and maintain a backup payment method on file.
Q11. What is the fundamental architectural difference between an IAM User and an IAM Role?

An IAM User represents a permanent identity created for a person or external system with long-term credentials (password for Console, Access Key ID & Secret Access Key for CLI/SDK). An IAM Role has no long-term passwords or keys; it is an identity assumed dynamically by AWS services (like EC2, Lambda, ECS) or federated users to obtain temporary, self-expiring security tokens via AWS STS (Security Token Service).

Key takeaway: Never embed permanent IAM user access keys in application code; always assign IAM roles to compute workloads.
Q12. What are the top practical best practices to avoid unexpected AWS bills?

1) Create dual AWS Budgets with alerts at 50%, 80%, and 100% of actual budget, plus 100% of forecasted budget.
2) Enable CloudWatch Billing Alarms in the us-east-1 (N. Virginia) global region.
3) Enforce MFA across Root and IAM user accounts.
4) Regularly audit and delete unattached EBS volumes, unattached Elastic IPs, and idle NAT Gateways.
5) Enable AWS Cost Anomaly Detection for automated ML-powered spike alerts.
6) Immediately terminate sandbox and lab instances after practice sessions.

Key takeaway: Automated multi-tier budget alerts combined with routine resource cleanup habits prevent 99% of accidental cloud bills.
Q13. How do you pinpoint which AWS service, region, or operation is driving up costs in Cost Explorer?

Open AWS Cost Explorer, set time granularity to "Daily", and adjust the Group By dimension: Group by Service to identify the top offending service (e.g., EC2 vs RDS); Group by Region to see geographic distribution; and Group by Usage Type or API Operation to isolate the exact micro-charge (e.g., NatGateway-Hours vs BoxUsage:t3.xlarge vs TimedStorage-ByteHrs).

Key takeaway: Grouping by "Usage Type" reveals the exact line-item component causing unexpected spending increases.
Q14. Why does an idle NAT Gateway incur recurring costs even when passing zero network traffic?

A NAT Gateway is a fully managed, highly available networking appliance deployed across a specific Availability Zone. AWS charges a flat hourly base provisioning fee (~$0.045/hour = ~$32.40/month per NAT Gateway) simply for keeping the infrastructure running, regardless of whether traffic passes through it, plus ~$0.045 per GB of data processed.

Key takeaway: In a 3-AZ VPC with 3 NAT Gateways, baseline idle cost is ~$100/month. Always delete test NAT Gateways after completing lab exercises.
Q15. How do you grant an IAM user permission to view the AWS Billing & Cost Management Console?

Enabling billing access requires two mandatory steps:
1) The Root User must sign in, open Account Settings, scroll to IAM User and Role Access to Billing Information, click Edit, check Activate IAM Access, and click Update.
2) An administrator must then attach an IAM policy containing billing permissions (e.g., BillingReadOnlyAccess or AWSBillingConductorFullAccess) to the IAM User or Group.

Key takeaway: Without Step 1 (the Root account activation toggle), attaching billing IAM policies will result in an "Access Denied" error.
Q16. What is an AWS Account Alias, and why is it recommended for production setups?

An Account Alias is a custom, human-readable name that replaces the random 12-digit AWS Account ID in your console login URL (e.g., https://my-company-prod.signin.aws.amazon.com/console instead of https://123456789012.signin.aws.amazon.com/console). It simplifies team access and prevents engineers from confusing Development, Staging, and Production accounts.

Key takeaway: Account Aliases must be globally unique across all AWS accounts worldwide.
Q17. What is the difference between On-Demand Instances, Reserved Instances (RIs), and Savings Plans?

On-Demand: Maximum flexibility, pay per second, zero commitment, highest unit price.
Reserved Instances (RI): Commitment to a specific instance type, OS, and region for 1 or 3 years in exchange for up to 72% discount.
Compute Savings Plans: Commitment to a consistent hourly spend (e.g., $10/hour) for 1 or 3 years; automatically applies up to 66% discounts across EC2 instances, AWS Fargate containers, and AWS Lambda functions regardless of family, region, or OS.

Key takeaway: Compute Savings Plans provide the greatest flexibility across modern containerized and serverless architectures.
Q18. What is the AWS Pricing Calculator, and when should it be used?

The AWS Pricing Calculator (calculator.aws) is a free web modeling tool that enables cloud architects and engineers to estimate total monthly and annual infrastructure costs before launching resources. It allows you to configure instances, storage types, egress bandwidth, database clusters, and backup retention to export formal architectural cost estimates (PDF/CSV) for managerial approval.

Key takeaway: Always calculate upfront cost models prior to provisioning production workloads to prevent architectural budget overruns.
Q19. What is AWS Consolidated Billing in AWS Organizations, and what financial advantages does it provide?

Consolidated Billing aggregates the billing records and payments from multiple AWS member accounts into a single master management account. Financial benefits include: 1) One unified monthly invoice and payment method. 2) Volume tier discounts: storage and data transfer across all accounts are combined to reach cheaper volume pricing tiers faster. 3) Shared Savings: unused Reserved Instance or Savings Plan hours in one account automatically discount eligible usage in other accounts.

Key takeaway: Centralizes corporate financial governance while maximizing volume tier discounts.
Q20. What is AWS Cost Anomaly Detection, and how does machine learning prevent runaway bills?

AWS Cost Anomaly Detection is a free, machine-learning-driven service that continuously monitors your account's historical spending trends to detect unexpected cost spikes or abnormal provisioning patterns. When an anomaly occurs (e.g., a misconfigured script repeatedly launching high-end EC2 instances), it calculates the root cause (account, service, region) and immediately dispatches an alert via email or Slack (via Amazon SNS).

Key takeaway: Catches runaway loops or compromised API keys before bills escalate into thousands of dollars.
Q21. What is AWS Compute Optimizer, and how does it prevent resource over-provisioning?

AWS Compute Optimizer utilizes machine learning algorithms to evaluate historical CloudWatch utilization data (CPU utilization, memory usage, network throughput, disk I/O) over a 14-day window. It provides actionable right-sizing recommendations for EC2 instances, EBS volumes, Auto Scaling Groups, and Lambda functions, identifying oversized resources that can be downsized to cheaper instance families without compromising performance.

Key takeaway: Eliminates waste from over-provisioned infrastructure while ensuring adequate application headroom.
Q22. How do Amazon S3 Lifecycle Rules optimize long-term storage expenditures?

S3 Lifecycle Rules automatically migrate objects between storage classes based on object age without changing file access URLs: moving data from S3 Standard ($0.023/GB) → S3 Standard-IA ($0.0125/GB) after 30 days → S3 Glacier Flexible ($0.0036/GB) after 90 days → S3 Glacier Deep Archive ($0.00099/GB) after 180 days, or permanently deleting old versions.

Key takeaway: Archiving compliance logs into Glacier Deep Archive reduces storage costs by up to 95% compared to Standard S3.
Q23. What are Service Control Policies (SCPs) in AWS Organizations, and how do they enforce hard cost guardrails?

SCPs are central guardrail policies applied at the AWS Organization, OU (Organizational Unit), or account level. Unlike IAM policies, SCPs define the maximum permissible boundaries for an account. An administrator can attach an SCP that explicitly denies provisioning of expensive instance types (e.g., denying ec2:RunInstances for non-free-tier instance families) or blocks unauthorized expensive regions entirely across all sub-accounts.

Key takeaway: Even the Root User of a member account cannot override or bypass an Organization SCP guardrail.
Q24. What is the difference between AWS Service Quotas (Hard Limits) and Billing Alarms?

Billing Alarms: Purely observational and informational notifications that alert you when monetary spending thresholds are crossed; they do not stop or prevent workloads from running.
Service Quotas: Physical infrastructure capacity caps imposed by AWS per region (e.g., maximum 32 vCPUs for running On-Demand standard instances). When a quota limit is reached, AWS actively blocks further provisioning API calls until a quota increase is submitted and approved.

Key takeaway: Alarms provide visibility into cost; quotas enforce physical circuit breakers against runaway provisioning.
Q25. How do you properly close an AWS Account to ensure zero lingering charges?

1) Sign in as the Root User.
2) Manually terminate and delete all active resources across ALL regions (terminate EC2 instances, delete EBS volumes/snapshots, release Elastic IPs, delete NAT Gateways, empty and delete S3 buckets, delete RDS databases).
3) Open Account Settings → scroll to the bottom → select Close Account → check all confirmation acknowledgments and click Close Account.
AWS provides a 90-day post-closure period before permanent deletion, during which no active resources generate charges.

Key takeaway: Only the Root User can close an account; always clean up provisioned resources prior to closing to ensure a clean final invoice.
