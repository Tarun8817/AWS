AWS CloudFormation — IaC Notes
AWS CLOUDformation

Infrastructure as Code (IaC)

Create, Deploy, Update and Manage AWS Infrastructure Using Code

⚠ Cost warning: Every practical lab in this document creates real AWS resources (EC2, S3, etc.) that can incur charges depending on your account, region and configuration. Always delete stacks you no longer need, and check the AWS Billing Dashboard. AWS Console labels/screens can also change over time — the flow described here stays the same even if button names shift slightly.

1. Introduction

Theory
Simple definition AWS CloudFormation is an AWS service that allows us to create and manage AWS infrastructure using code instead of manually creating resources one by one.
TermSimple meaning
AWSAmazon Web Services — the cloud provider offering services like EC2, S3, RDS.
CloudFormationAn AWS service that reads a text file describing infrastructure and creates it for you.
InfrastructureThe AWS resources your application needs — servers, storage, databases, networking.
Infrastructure as Code (IaC)Describing infrastructure in a file (code) instead of clicking through a console.
TemplateThe YAML/JSON file that describes what resources to create.
StackA deployed instance of a template — the actual group of resources CloudFormation manages together.
ResourceA single AWS thing created by the template, e.g. one S3 bucket or one EC2 instance.

The problem with creating resources manually

Without CloudFormation, a developer manually creates each piece by clicking through the Console: EC2, Security Group, S3, RDS, IAM Role, Load Balancer — one at a time, remembering every setting. This is slow, easy to get wrong, hard to repeat exactly, and hard to track changes to.

Without CloudFormation: Developer manually creates one-by-one: EC2 -> Security Group -> S3 -> RDS -> IAM Role -> Load Balancer With CloudFormation: CloudFormation Template | v CloudFormation Stack | v AWS Resources (all created together, from one file)

CloudFormation solves this by letting you write down what you want once, and it figures out how to create it, in the right order, repeatably.

2. What is Infrastructure as Code (IaC)?

Theory
Traditional approachIaC approach
AWS Console → manually create each resource by clickingCode (template) → AWS → Infrastructure is created automatically

Advantages of IaC

  • Automation — resources are created without manual clicking.
  • Repeatability — the same template produces the same infrastructure every time.
  • Version control — templates can be stored in Git, so changes are tracked.
  • Consistency — dev, staging and prod can be built from the same base template.
  • Faster deployment — a whole environment can be created in one step.
  • Easy rollback — CloudFormation can undo a failed change automatically.
  • Less human error — no missed checkbox or wrong dropdown value.
  • Easy replication — spin up an identical environment in another region/account.
Real-world example A team needs an identical staging environment for testing before every release. With IaC, they reuse the same CloudFormation template with a different parameter (e.g. Environment: staging) instead of manually rebuilding everything from memory.

3. CloudFormation Architecture

Theory
CloudFormation Template | v CloudFormation Stack | v +-----------------------------------------+ | EC2 | S3 | RDS | IAM | VPC | +-----------------------------------------+
  • Template — the YAML/JSON file you write, describing every resource.
  • Stack — created when you deploy a template; CloudFormation tracks every resource that belongs to this stack as one unit.
  • Resources — the actual AWS services (EC2, S3, RDS, IAM roles, VPC, etc.) that get created, updated or deleted together as part of the stack.

Because the stack tracks everything as one group, updating the template and re-deploying updates all the related resources together, and deleting the stack removes them together (subject to DeletionPolicy).

4. Important CloudFormation Terms

Theory

1. Template

The YAML/JSON file describing your infrastructure. Why: it's the source of truth for what should exist. Example: a file s3-bucket.yaml describing one S3 bucket.

2. Stack

A deployed instance of a template, tracked as one unit. Why: lets you create/update/delete a whole group of resources together. Example: stack my-s3-stack.

3. Resource

A single AWS item created by the template (e.g. AWS::S3::Bucket). Why: the actual building block of your infrastructure. Example: one EC2 instance.

4. Parameter

An input value supplied when you deploy the stack. Why: makes templates reusable across environments. Example: InstanceType = t3.micro.

5. Mapping

A fixed lookup table inside the template (e.g. region → value). Why: avoids hardcoding region-specific values in multiple places. Example: mapping AMI IDs per region.

6. Condition

A rule that decides whether a resource is created. Why: lets one template behave differently per environment. Example: only create a resource when Environment = prod.

7. Output

A value returned after the stack is created (e.g. a URL or bucket name). Why: lets you retrieve useful info without digging through the Console. Example: the public IP of an EC2 instance.

8. Metadata

Extra descriptive information attached to the template or a resource (not used to create resources directly). Why: useful for tools/Console hints. Example: grouping parameters into sections in the Console UI.

9. Intrinsic Functions

Built-in functions like !Ref, !GetAtt, !Sub used inside templates. Why: let resources reference each other and build dynamic values. Example: !Ref MyBucket.

10. Change Set

A preview of what will change before you actually apply an update. Why: avoid surprises on a live stack. Example: see that updating a template will replace an EC2 instance.

11. Drift Detection

A check for differences between the template and the actual resource state. Why: catches manual changes made outside CloudFormation. Example: someone edited a Security Group rule by hand.

12. Stack Policy

A JSON policy that restricts what update actions can be performed on specific resources in a stack. Why: protects critical resources (like a production database) from accidental replacement. Example: deny replacing an RDS instance during updates.

13. Nested Stack

A stack created and managed as a resource inside another (parent) stack. Why: breaks large infrastructure into reusable, organized pieces. Example: a Network Stack nested inside a Main Stack.

14. StackSet

One template deployed as stacks across multiple AWS accounts and/or regions. Why: centrally manage infrastructure for an organization. Example: deploying the same security baseline to 10 accounts.

5. CloudFormation Template Structure

Theory

A template is normally organized into these top-level sections:

AWSTemplateFormatVersion: Description: Parameters: Mappings: Conditions: Resources: Outputs:
SectionPurposeRequired?
AWSTemplateFormatVersionThe template format version (a fixed string).Optional but common
DescriptionA short text description of the template.Optional
ParametersInputs you supply at deploy time.Optional
MappingsFixed lookup tables.Optional
ConditionsRules controlling whether resources are created.Optional
ResourcesThe actual AWS resources to create.Required
OutputsValues returned after deployment.Optional

A basic template

yaml
AWSTemplateFormatVersion: '2010-09-09'

Description: Basic CloudFormation Example

Resources:
  MyBucket:
    Type: AWS::S3::Bucket

Outputs:
  BucketName:
    Value: !Ref MyBucket
  • AWSTemplateFormatVersion: '2010-09-09' — the fixed version string CloudFormation expects.
  • Description — a human-readable note about what this template does.
  • Resources.MyBucket — MyBucket is the logical ID (a name you choose for use inside this template); Type: AWS::S3::Bucket says it's an S3 bucket.
  • Outputs.BucketName.Value: !Ref MyBucket — after creation, show the actual bucket name/reference as an output called BucketName.

6. YAML Basics for CloudFormation

Theory

CloudFormation templates are usually written in YAML (JSON also works, but YAML is more beginner-friendly).

ConceptMeaning
IndentationSpaces (not tabs) show which items belong inside which section. Consistent 2-space indentation is common.
Key/valueKey: value — a colon and a space separate the key from its value.
ListsLines starting with - under a key represent a list.
ObjectsA key with no value on the same line, followed by indented key/value pairs, is a nested object.
StringsUsually written plainly; quotes ('...' or "...") are used when the value could be misread (like '2010-09-09').
CommentsStart with # and are ignored by CloudFormation.
yaml
# A resource is a key, indented under Resources
Resources:
  MyBucket:
    Type: AWS::S3::Bucket
Why indentation matters YAML uses indentation instead of brackets to show structure. If Type: is indented at the wrong level, CloudFormation may read it as belonging to the wrong resource (or fail with a parsing error).

Common YAML mistakes

  • Mixing tabs and spaces (YAML does not allow tabs for indentation).
  • Inconsistent indentation between sibling lines.
  • Missing the space after a colon (Type:AWS::S3::Bucket is invalid; it needs Type: AWS::S3::Bucket).
  • Forgetting the - when writing a list item.
  • Using a reserved character (like :) inside an unquoted string.

7. CloudFormation Resource

Theory
yaml
Resources:
  MyBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: my-example-bucket
PartMeaning
Logical ID (MyBucket)A name you choose to refer to this resource inside this template (used with !Ref, !GetAtt, DependsOn). It is not the actual AWS resource name.
Type (AWS::S3::Bucket)Tells CloudFormation which AWS resource to create.
PropertiesThe settings for that resource (varies by resource type).

Logical IDs are used only within the template to link resources together — e.g. an EC2 instance's Properties can reference a Security Group's logical ID to attach it.

8. Practical Lab 1 — Create an S3 Bucket Using CloudFormation

Practical

Goal: create an S3 bucket using a CloudFormation stack via the AWS Console.

CloudFormation | v S3 Bucket

Template: s3-bucket.yaml

yaml
AWSTemplateFormatVersion: '2010-09-09'

Description: Create an S3 bucket using CloudFormation

Resources:
  MyS3Bucket:
    Type: AWS::S3::Bucket

Outputs:
  BucketName:
    Description: Name of the S3 bucket
    Value: !Ref MyS3Bucket

Since MyS3Bucket has no BucketName property, AWS will auto-generate a unique bucket name. !Ref MyS3Bucket for an S3 bucket returns that bucket's name.

  1. Open the AWS Management Console.
  2. Search for CloudFormation.
  3. Open CloudFormation.
  4. Click Create stack.
  5. Choose With new resources (standard).
  6. Choose Upload a template file.
  7. Create the file s3-bucket.yaml locally with the code above, and select it to upload.
  8. Click Next.
  9. Enter the stack name: my-s3-stack
  10. Continue through the remaining options (leave defaults for this beginner lab).
  11. Review the summary shown by CloudFormation.
  12. If AWS asks you to acknowledge IAM capability (this happens when a template can create IAM resources), check the acknowledgement box. This template doesn't create IAM resources, so it may not appear here — but it will for later labs.
  13. Click Submit / Create stack.

What happens after clicking Create?

CloudFormation starts creating resources in the order it determines from the template, and shows a live Events tab with each step.

StatusMeaning
CREATE_IN_PROGRESSCloudFormation is currently creating the stack/resource.
CREATE_COMPLETEThe stack/resource was created successfully.
CREATE_FAILEDSomething went wrong creating this resource.
ROLLBACK_IN_PROGRESSA failure occurred, so CloudFormation is undoing what it created.
ROLLBACK_COMPLETEThe rollback finished; the stack is back to a clean (deleted) state and usually must be deleted before retrying.
  1. Open the Resources tab of the stack.
  2. Click the S3 bucket resource link to open it in the S3 console.
  3. Verify that the bucket exists and is empty.

9. Practical Lab 2 — Create an EC2 Instance Using CloudFormation

Practical

Prerequisites

  • VPC — the network your instance launches into (the default VPC works for learning).
  • Subnet — a slice of the VPC; usually chosen automatically if not specified for a default VPC.
  • Security Group — controls inbound/outbound traffic (built in Lab 3).
  • Key Pair — used for SSH access; must already exist in your account/region.
  • AMI — the image (OS) the instance boots from.
  • Instance Type — the instance size, e.g. t3.micro.
yaml
Parameters:
  InstanceType:
    Type: String
    Default: t3.micro

  KeyName:
    Type: AWS::EC2::KeyPair::KeyName

  AMIId:
    Type: AWS::EC2::Image::Id

Resources:
  MyEC2:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !Ref AMIId
      InstanceType: !Ref InstanceType
      KeyName: !Ref KeyName
  • Parameters.InstanceType — a string input with a sensible default (t3.micro).
  • Parameters.KeyName — a special parameter type that lets the Console show a dropdown of your existing key pairs.
  • Parameters.AMIId — a special parameter type for AMI IDs, also shown as a picker in the Console.
  • Resources.MyEC2.Properties.ImageId/InstanceType/KeyName — each uses !Ref to pull in the value supplied for that parameter at deploy time.
AMI IDs are region-specific Never hard-code an AMI ID into a template you plan to reuse across regions. An AMI ID that works in one region (e.g. ap-south-1) will not exist in another region (e.g. eu-north-1). That's why this template takes the AMI ID as a parameter instead of hardcoding it.

How to find the AMI ID

  1. Open the EC2 Console in the same region you plan to deploy in.
  2. Click Launch instance (you don't have to finish this — just browse).
  3. Under Application and OS Images, pick an OS (e.g. Amazon Linux) and note the AMI ID shown.
  4. Copy that AMI ID to use as the parameter value when deploying your stack.

How to find Key Pair / VPC / Subnet / Security Group

  • Key Pair: EC2 Console → Key Pairs (create one first if you don't have any; download the .pem/.ppk file and keep it safe).
  • VPC: VPC Console → Your VPCs (the default VPC is fine for this lab).
  • Subnet: VPC Console → Subnets (pick one inside the VPC you're using).
  • Security Group: built in the next lab, or EC2 Console → Security Groups to see existing ones.

Deploy, verify, and clean up

  1. Follow the same Create stack flow as Lab 1, uploading this template.
  2. Fill in the parameters (Instance Type, Key Pair, AMI ID) on the parameters screen.
  3. Submit and watch the Events tab until status is CREATE_COMPLETE.
  4. Open Resources → click the EC2 instance link to confirm it's running in the EC2 Console.
  5. To remove it, delete the stack (not just the instance) from the CloudFormation Console — this terminates the EC2 instance along with any other resources in the stack.

10. Practical Lab 3 — EC2 + Security Group

Practical

This template creates a Security Group allowing SSH (22) and HTTP (80), then an EC2 instance using that Security Group.

yaml
Resources:
  MySecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Allow SSH and HTTP
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 22
          ToPort: 22
          CidrIp: 0.0.0.0/0

        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: 0.0.0.0/0

  MyEC2:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !Ref AMIId
      InstanceType: !Ref InstanceType
      KeyName: !Ref KeyName
      SecurityGroupIds:
        - !Ref MySecurityGroup

AWS::EC2::SecurityGroup acts as a virtual firewall. Each entry under SecurityGroupIngress is one allowed inbound rule (protocol, port range, and allowed source CIDR).

Security risk: SSH from 0.0.0.0/0 CidrIp: 0.0.0.0/0 on port 22 means anyone on the internet can attempt to SSH into this instance. This is acceptable only for quick, temporary learning. For real projects, restrict SSH to your own IP, e.g. CidrIp: YOUR.PUBLIC.IP.ADDRESS/32, or access via a bastion host/VPN instead.

11. Practical Lab 4 — EC2 Web Server Using UserData

Practical

This template creates a Security Group, an EC2 instance, installs Apache automatically, starts it, and serves a simple HTML page — all without logging in manually.

yaml
MyEC2:
  Type: AWS::EC2::Instance
  Properties:
    ImageId: !Ref AMIId
    InstanceType: !Ref InstanceType
    KeyName: !Ref KeyName
    SecurityGroupIds:
      - !Ref MySecurityGroup
    UserData:
      Fn::Base64: !Sub |
        #!/bin/bash
        dnf update -y
        dnf install -y httpd
        systemctl start httpd
        systemctl enable httpd

        echo "<h1>Hello from CloudFormation</h1>" > /var/www/html/index.html
PartMeaning
UserDataA script that runs automatically the first time the instance boots.
Fn::Base64CloudFormation must pass UserData to EC2 as Base64; this function encodes it for you.
!Sub |Lets you write a multi-line script and optionally substitute ${Parameter} values into it.
dnf update -y / dnf install -y httpdUpdates packages and installs the Apache web server (httpd) on Amazon Linux.
systemctl start httpdStarts the Apache service immediately.
systemctl enable httpdMakes Apache start automatically on every reboot.
echo "..." > /var/www/html/index.htmlWrites a simple HTML page that Apache will serve as the homepage.

Accessing the site: once the instance is running and the Security Group allows port 80, open a browser and go to http://PUBLIC-IP (replace with the instance's actual public IP, available in the EC2 Console or via an Output — see Outputs).

12. Practical Lab 5 — Create S3 + EC2 Together

Practical

A single template can describe several resources at once. CloudFormation figures out the right creation order based on how resources reference each other.

CloudFormation | +---- S3 | +---- Security Group | +---- EC2 (uses Security Group)

Here, MyEC2 references MySecurityGroup via SecurityGroupIds: [!Ref MySecurityGroup]. CloudFormation detects this reference and automatically creates the Security Group before the EC2 instance, even though the S3 bucket has no dependency and could be created at any point.

Combine the S3 bucket resource from Lab 1, the Security Group from Lab 3, and the EC2 instance from Lab 4 into one Resources: section to try this yourself.

13. Parameters

Theory

Parameters let the same template be reused with different inputs (e.g. different environments), instead of duplicating templates.

yaml
Parameters:
  Environment:
    Type: String
    Default: dev
    AllowedValues:
      - dev
      - test
      - prod
  • Type: String — the kind of value expected (other types include Number, AWS::EC2::KeyPair::KeyName, AWS::EC2::Image::Id, etc.).
  • Default: dev — used if the deployer doesn't provide a value.
  • AllowedValues — restricts input to a fixed list, preventing typos like Prodd.

Other useful parameters for a real project: InstanceType, KeyName, AMIId (as shown in Lab 2).

14–16. Intrinsic Functions: !Ref, !GetAtt, !Sub

Theory

14. !Ref

!Ref returns a resource's "primary" identifying value, or a parameter's value.

yaml
Outputs:
  BucketName:
    Value: !Ref MyBucket
  • For an S3 bucket, !Ref returns the bucket name.
  • For an EC2 instance, !Ref returns the instance ID.
  • For a Parameter, !Ref returns whatever value was supplied for that parameter.

15. !GetAtt

!GetAtt returns a specific attribute of a resource — something more specific than what plain !Ref gives you.

yaml
Outputs:
  InstancePublicIP:
    Value: !GetAtt MyEC2.PublicIp
!Ref vs !GetAtt !Ref MyEC2 gives the instance ID. !GetAtt MyEC2.PublicIp gives the public IP address specifically — an attribute that !Ref alone can't give you. Use !GetAtt whenever you need something more specific than the resource's primary identifier.

16. !Sub

!Sub substitutes ${...} placeholders inside a string with parameter or resource values.

yaml
UserData:
  Fn::Base64: !Sub |
    echo "Environment: ${Environment}"

Here ${Environment} is replaced with the actual value of the Environment parameter when the template is deployed — useful for building dynamic scripts or strings like URLs.

17. Outputs

Theory

Outputs return useful information after a stack is created, visible in the Console's Outputs tab (or via CLI).

yaml
Outputs:
  InstanceId:
    Value: !Ref MyEC2

  PublicIP:
    Value: !GetAtt MyEC2.PublicIp

  BucketName:
    Value: !Ref MyS3Bucket

  WebsiteURL:
    Description: Website URL
    Value: !Sub "http://${MyEC2.PublicIp}"

Common outputs: EC2 Instance ID, Public IP, S3 Bucket Name, and a ready-to-click Website URL built with !Sub.

18. DependsOn

Theory

CloudFormation automatically detects most dependencies when one resource references another (e.g. via !Ref). DependsOn is for the rare cases where a dependency exists but isn't visible through a reference.

yaml
MyEC2:
  Type: AWS::EC2::Instance
  DependsOn: MyS3Bucket
  Properties:
    ImageId: !Ref AMIId
    ...

Use DependsOn when a resource must exist first for a reason CloudFormation can't infer (e.g. an application expects a bucket to already exist when it boots, even though nothing in the template's properties references it directly).

19. Conditions

Theory

Conditions let a template create (or configure) resources differently depending on parameter values.

yaml
Conditions:
  IsProduction:
    Fn::Equals:
      - !Ref Environment
      - prod

Resources:
  MyEC2:
    Type: AWS::EC2::Instance
    Condition: IsProduction
    Properties:
      ...

Here, MyEC2 is only created when the Environment parameter equals prod. This lets one template safely serve multiple environments with different resources.

20. Mappings

Theory

Mappings are fixed lookup tables, commonly used to pick a value based on region.

yaml
Mappings:
  RegionMap:
    us-east-1:
      AMI: ami-xxxxxxxx
    eu-north-1:
      AMI: ami-yyyyyyyy

Resources:
  MyEC2:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !FindInMap [RegionMap, !Ref "AWS::Region", AMI]
Why hardcoding region-specific values is risky An AMI ID, endpoint, or other value that's correct in one region will often be wrong (or non-existent) in another. Hardcoding it means the template silently breaks when deployed elsewhere. A Mapping keeps all region-specific values in one clearly labeled place.

21. CloudFormation Change Sets

Practical

A Change Set is a preview of what would happen if you applied an update, without actually applying it yet.

Existing Stack | v Modify Template | v Create Change Set | v Review Changes | v Execute Change Set
  1. Open the stack in the CloudFormation Console.
  2. Click Update.
  3. Upload the modified template.
  4. Choose Create change set instead of applying immediately.
  5. Review the listed changes — CloudFormation shows which resources will be Modified, Added, Removed, or Replaced.
  6. If everything looks correct, click Execute change set to apply it.

22. Update a CloudFormation Stack

Practical

Example: change the EC2 instance type from t3.micro to t3.small.

  1. Open CloudFormation.
  2. Select the stack.
  3. Click Update.
  4. Upload the new template (or edit parameters, e.g. change InstanceType to t3.small).
  5. Review the changes shown.
  6. Optionally create a Change Set first if you want a preview (see section 21).
  7. Click Execute / Update stack.
  8. Monitor the Events tab as it applies.

During an update, you may see statuses like UPDATE_IN_PROGRESS and UPDATE_COMPLETE. Some property changes (like instance type) can be updated in place; others may require replacing the resource entirely — the Change Set preview tells you which.

23. Stack Rollback

Theory
CloudFormation tries to create/update resources | v Something fails | v CloudFormation rolls back | v Previous state is restored / partially-created resources are cleaned up
StatusMeaning
UPDATE_ROLLBACK_IN_PROGRESSAn update failed and CloudFormation is undoing it, restoring the previous configuration.
UPDATE_ROLLBACK_COMPLETEThe rollback from a failed update finished; the stack is back to its last working state.
ROLLBACK_COMPLETEA brand-new stack's creation failed and was rolled back; the stack must usually be deleted before you can try again.

What to do when deployment fails

  1. Open the Events tab and find the first *_FAILED event (later events are usually just the rollback cascade).
  2. Read the Status reason column for the actual error message.
  3. Fix the template or parameter causing the issue.
  4. If the stack is in ROLLBACK_COMPLETE, delete it and create a new stack with the corrected template.

24. Delete a CloudFormation Stack

Practical
  1. Open CloudFormation.
  2. Select the stack.
  3. Click Delete.
  4. Confirm the deletion.
  5. Monitor the Events tab until it disappears from the stack list (deletion complete).

Resources managed by the stack are generally deleted along with the stack, unless a resource has been configured otherwise (see DeletionPolicy below).

25. DeletionPolicy

Theory
ValueBehavior
Delete (default for most resources)The resource is deleted when the stack (or the resource from the template) is removed.
RetainThe resource is kept in AWS even after the stack is deleted.
SnapshotA final snapshot is taken before deletion (supported for certain resource types like RDS instances and EBS volumes).
yaml
MyDatabase:
  Type: AWS::RDS::DBInstance
  DeletionPolicy: Snapshot
  Properties:
    ...
Why databases and important data may need Retain/Snapshot Deleting a stack that includes an RDS database or an S3 bucket with important files, using the default Delete policy, can permanently destroy real data. Set DeletionPolicy: Retain or DeletionPolicy: Snapshot (where supported) on resources holding data you can't afford to lose.

26. Drift Detection

Theory

Example: CloudFormation created an EC2 Security Group. Later, someone manually edits that Security Group directly from the AWS Console (adds/removes a rule).

CloudFormation template saysActual resource is
Original configuration (what was deployed)Changed configuration (edited by hand afterward)
Template ≠ Actual Infrastructure Once a manual change happens outside CloudFormation, the template no longer matches reality. Drift Detection finds this mismatch.
  1. Open the Stack.
  2. Open Stack actions.
  3. Click Detect drift.
  4. Wait, then check the drift status shown on the stack.
  5. Click through to view drift details to see exactly which properties differ.

27–28. Nested Stacks and StackSets

Theory

27. Nested Stacks

Main Stack | +--- Network Stack | +--- Database Stack | +--- Application Stack

A nested stack is a stack created as a resource inside a parent stack. It's useful for breaking large infrastructure into smaller, reusable, independently-maintained templates (e.g. a shared Network Stack reused by several applications).

28. StackSets

One CloudFormation template | v Multiple AWS accounts | v Multiple AWS regions

A StackSet deploys the same template as separate stacks across many accounts and/or regions from one place — useful for organization-wide baselines like security guardrails, logging setups, or standard tagging policies.

30. Practical CLI Deployment

Practical
  1. Install the AWS CLI for your operating system.
  2. Configure credentials:
    bash
    aws configure
    Enter: Access Key ID, Secret Access Key, Region, and Output format (e.g. json).
    Never commit AWS access keys to GitHub Keep credentials out of source code, config files pushed to Git, and screenshots. Use least-privilege IAM users, and rotate keys you no longer need.
  3. Verify your identity:
    bash
    aws sts get-caller-identity
  4. Deploy the stack:
    bash
    aws cloudformation create-stack \
  --stack-name my-s3-stack \
  --template-body file://s3-bucket.yaml
  5. Check the stack status:
    bash
    aws cloudformation describe-stacks \
  --stack-name my-s3-stack
  6. Check events (useful when something goes wrong):
    bash
    aws cloudformation describe-stack-events \
  --stack-name my-s3-stack
  7. Delete the stack when finished:
    bash
    aws cloudformation delete-stack \
  --stack-name my-s3-stack
Windows PowerShell note The commands above work the same in PowerShell. For multi-line commands, PowerShell uses a backtick (`) instead of a backslash (\) as the line-continuation character:
powershell
aws cloudformation create-stack `
  --stack-name my-s3-stack `
  --template-body file://s3-bucket.yaml

32. Complete MERN CloudFormation Project (Simplified)

Practical

Frontend: React • Backend: Node.js + Express • Database: RDS MySQL/PostgreSQL • File Storage: S3 • Infrastructure: CloudFormation

Developer | v CloudFormation Template | v VPC | v Security Groups | v EC2 | v Backend (Node.js/Express) | v RDS | v S3
yaml
AWSTemplateFormatVersion: '2010-09-09'
Description: Simplified MERN-style backend infrastructure

Parameters:
  KeyName:
    Type: AWS::EC2::KeyPair::KeyName
  AMIId:
    Type: AWS::EC2::Image::Id
  DBPassword:
    Type: String
    NoEcho: true

Resources:
  AppSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Allow HTTP and SSH to app server
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: 0.0.0.0/0
        - IpProtocol: tcp
          FromPort: 22
          ToPort: 22
          CidrIp: YOUR.IP.ADDRESS/32

  AppServer:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !Ref AMIId
      InstanceType: t3.micro
      KeyName: !Ref KeyName
      SecurityGroupIds:
        - !Ref AppSecurityGroup

  AppDatabase:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot
    Properties:
      Engine: mysql
      DBInstanceClass: db.t3.micro
      AllocatedStorage: "20"
      MasterUsername: admin
      MasterUserPassword: !Ref DBPassword

  AppBucket:
    Type: AWS::S3::Bucket

Outputs:
  AppServerPublicIP:
    Value: !GetAtt AppServer.PublicIp
  DatabaseEndpoint:
    Value: !GetAtt AppDatabase.Endpoint.Address
  BucketName:
    Value: !Ref AppBucket

NoEcho: true on DBPassword hides the value in the Console and CLI output. Replace YOUR.IP.ADDRESS/32 with your actual public IP before deploying. This is intentionally simplified — a production setup would typically add a VPC with private subnets, an RDS Proxy, and a load balancer.

35. Common Errors

Important

1. YAML indentation error

Why: inconsistent spacing or tabs. Check: the error message usually points to a line number. Fix: re-indent consistently with spaces only.

2. Invalid AMI ID

Why: typo, or the AMI ID doesn't exist. Check: the Events tab error message. Fix: copy the AMI ID fresh from the EC2 Console.

3. AMI not available in region

Why: AMI IDs are region-specific (see section 9). Fix: find the correct AMI ID for the region you're deploying to, or use a Mapping.

4. Key pair does not exist

Why: the key pair name doesn't exist in this account/region. Fix: create a key pair first, or select an existing one from the parameter dropdown.

5. Security group error

Why: invalid port range, protocol, or referencing a security group from a different VPC. Fix: check the properties match a valid rule and the same VPC.

6. IAM permission denied

Why: the user/role deploying the stack lacks permission to create one of the resources. Fix: grant the needed IAM permissions (least privilege, not full admin).

7. CREATE_FAILED

Why: any resource-level failure during creation. Check: the Status reason next to the failed resource in Events. Fix: depends on the specific reason shown.

8. ROLLBACK_COMPLETE

Why: initial stack creation failed and was rolled back. Fix: delete the stack, fix the template, and create it again.

9. UPDATE_ROLLBACK_FAILED

Why: CloudFormation couldn't even undo a failed update (e.g. a resource was manually modified). Fix: use "Continue update rollback," skipping the problem resource if needed.

10. Resource already exists

Why: a resource with the exact requested name already exists outside this stack. Fix: choose a different name, or import the existing resource instead.

11. Bucket name already exists

Why: S3 bucket names must be globally unique across all AWS accounts. Fix: choose a more unique name, or omit BucketName to let AWS auto-generate one.

12. Invalid property

Why: a property name is misspelled or doesn't apply to that resource type. Fix: check the AWS resource type reference for the correct property names.

13. Invalid template

Why: broken YAML/JSON syntax. Fix: validate the file's structure (correct indentation, matching brackets/quotes).

14. Dependency failure

Why: a resource depended on another resource that failed to create. Fix: fix the root failure first — dependent resources will then succeed on retry.

36. Best Practices

Important
  • Use Parameters instead of hardcoding values that change per environment.
  • Use Outputs to surface important information (IPs, URLs, names).
  • Avoid hardcoding region-specific values (AMI IDs, etc.) — use Parameters or Mappings.
  • Store templates in version control (e.g. Git).
  • Use meaningful logical IDs (e.g. AppSecurityGroup, not SG1).
  • Use tags on resources for cost tracking and organization.
  • Use least-privilege IAM for whoever/whatever deploys the stack.
  • Use Change Sets before applying updates to important stacks.
  • Test templates on a small/dev stack before touching production.
  • Keep environments (dev/staging/prod) separated (separate stacks/parameters).
  • Protect production resources with Stack Policies and careful DeletionPolicy choices.
  • Never commit AWS credentials to any repository.
  • Avoid opening SSH (port 22) to the entire internet (0.0.0.0/0).
  • Keep large templates modular (nested stacks) rather than one giant file.

37. Complete Practical Lab — “CloudFormation Web Server”

Practical
CloudFormation | v Security Group | v EC2 | v Apache | v HTML Website | v Public IP
yaml
AWSTemplateFormatVersion: '2010-09-09'
Description: CloudFormation Web Server lab

Parameters:
  InstanceType:
    Type: String
    Default: t3.micro
  KeyName:
    Type: AWS::EC2::KeyPair::KeyName
  AMIId:
    Type: AWS::EC2::Image::Id

Resources:
  WebServerSG:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Allow HTTP and SSH
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: 0.0.0.0/0
        - IpProtocol: tcp
          FromPort: 22
          ToPort: 22
          CidrIp: 0.0.0.0/0

  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !Ref AMIId
      InstanceType: !Ref InstanceType
      KeyName: !Ref KeyName
      SecurityGroupIds:
        - !Ref WebServerSG
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash
          dnf update -y
          dnf install -y httpd
          systemctl start httpd
          systemctl enable httpd
          echo "<h1>Hello from CloudFormation</h1>" > /var/www/html/index.html

Outputs:
  WebsiteURL:
    Description: Open this in your browser
    Value: !Sub "http://${WebServer.PublicIp}"
  1. Create a new file named web-server.yaml.
  2. Copy the YAML code above into it.
  3. Open the AWS Console.
  4. Open CloudFormation.
  5. Click Create Stack → With new resources (standard).
  6. Choose Upload a template file and select web-server.yaml.
  7. Enter a stack name, e.g. cfn-web-server-lab.
  8. Configure the parameters (InstanceType, KeyName, AMIId).
  9. Review the summary.
  10. Click Submit.
  11. Monitor the Events tab until status is CREATE_COMPLETE.
  12. Open the Resources tab and confirm the Security Group and EC2 instance were created.
  13. Open the Outputs tab and copy the WebsiteURL value.
  14. Open a new browser tab.
  15. Paste the URL and confirm you see “Hello from CloudFormation.”
  16. To modify the website, edit the echo "..." line in the template (e.g. change the heading text).
  17. Go back to the stack, click Update, and upload the modified template.
  18. After the update completes, refresh the browser tab and verify the new content. (Note: UserData typically only runs on first boot — a plain template update alone may not re-run it. For learning purposes, verifying the stack update completed successfully is the main goal here.)
  19. When finished, select the stack and click Delete.
  20. Verify the stack disappears from the list and the EC2 instance is terminated in the EC2 Console.

39. Interview Questions & Answers

Interview
Q1. What is AWS CloudFormation?
An AWS service that creates and manages infrastructure from code (templates) instead of manual console clicks.
Q2. What is IaC?
Infrastructure as Code — describing infrastructure in a file so it can be created, versioned and repeated automatically.
Q3. What is a CloudFormation template?
The YAML/JSON file that defines what AWS resources to create and how.
Q4. What is a CloudFormation stack?
A deployed instance of a template; the group of resources CloudFormation manages together as one unit.
Q5. What is a resource?
A single AWS item defined in the template, e.g. an EC2 instance or S3 bucket.
Q6. What is a parameter?
An input value supplied at deploy time, making templates reusable across environments.
Q7. What is an output?
A value returned after stack creation, such as a resource's public IP or name.
Q8. What is !Ref?
An intrinsic function that returns a resource's primary identifier or a parameter's value.
Q9. What is !GetAtt?
An intrinsic function that returns a specific attribute of a resource, e.g. an EC2 instance's public IP.
Q10. What is !Sub?
An intrinsic function that substitutes ${...} placeholders in a string with parameter/resource values.
Q11. What is DependsOn?
An explicit way to tell CloudFormation one resource must be created before another, when the dependency isn't inferred automatically.
Q12. What is a Change Set?
A preview of what an update would change before actually applying it.
Q13. What is Drift Detection?
A check comparing the template's expected configuration against the actual, possibly manually-changed, resource state.
Q14. What is DeletionPolicy?
A setting controlling what happens to a resource when it's removed from the stack: Delete, Retain, or Snapshot.
Q15. What is a StackSet?
A way to deploy one template as stacks across multiple AWS accounts and regions.
Q16. What is a Nested Stack?
A stack created as a resource inside another (parent) stack, used to organize large templates.
Q17. What happens if stack creation fails?
CloudFormation rolls back and removes whatever it had already created, ending in ROLLBACK_COMPLETE.
Q18. What is rollback?
Automatically undoing changes to return to the last known good state after a failure.
Q19. CloudFormation vs Terraform?
CloudFormation is AWS-native (YAML/JSON, AWS-managed state); Terraform is multi-cloud (HCL, its own state file). Neither is universally better.
Q20. CloudFormation vs manual deployment?
Manual deployment is quick for one-off resources but hard to repeat/track; CloudFormation is repeatable, trackable and easier to clean up.
Q21. Why use Parameters?
To make one template reusable across environments/accounts without hardcoding values.
Q22. Why use Outputs?
To easily retrieve important information (URLs, IPs, names) after deployment, without manually digging through the Console.
Q23. How do you update a stack?
Open the stack, choose Update, provide the new template/parameters, review the changes, and execute the update.
Q24. How do you delete a stack?
Select the stack in the Console (or use the CLI delete-stack command) and confirm deletion; resources are removed per their DeletionPolicy.
Q25. How do you troubleshoot CREATE_FAILED?
Check the Events tab for the Status reason on the failed resource, fix the underlying issue (permissions, invalid value, etc.), then retry.

41. Final Real-World Flow

Theory
Developer | v CloudFormation YAML | v GitHub | v CloudFormation Stack | v +--------------------------------+ | VPC | EC2 | ALB | RDS | S3 | +--------------------------------+ | v Application

In practice: a developer writes the CloudFormation YAML template describing the required infrastructure, and stores it in GitHub for version control and team review. When deployed, this template becomes a CloudFormation Stack, which creates the actual VPC, EC2, ALB, RDS and S3 resources the application needs, tracked and managed together. The running Application sits on top of this infrastructure. Any future change goes back through the same cycle: edit the template, review via a Change Set, and update the stack — keeping infrastructure changes as trackable and repeatable as application code changes.
