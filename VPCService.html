THEORY 1. INTRODUCTION — What is AWS VPC?

"AWS VPC (Virtual Private Cloud) is a logically isolated virtual network in AWS where we can launch and control AWS resources such as EC2 instances, RDS databases, and load balancers."

If you are new to networking, think of AWS as a huge physical building. An AWS VPC is like renting your own private, locked office floor inside that building. Only people you invite can enter, and you control all the doors, hallways, and security cameras!

Deconstructing the Key Networking Terms

  • AWS (Amazon Web Services): The worldwide cloud platform offering compute, storage, databases, and networking on-demand.
  • Network: Two or more computers linked together to share files, data, and communication.
  • Virtual Network: A software-defined network. Instead of physical cables, switches, and routers, AWS creates virtual software versions of them.
  • Private Network: A protected network space that is not directly accessible to anyone on the open public internet unless you explicitly allow it.
  • VPC (Virtual Private Cloud): Your own custom, isolated slice of the AWS cloud that belongs strictly to your AWS account.

Why is VPC Required?

When you build real-world software, security and isolation are non-negotiable. VPC gives you 100% control over:

  • IP Address Ranges: You pick your own custom private IP scheme (e.g., 10.0.0.0/16).
  • Subnet Creation: You can divide your network into public and private areas.
  • Route Tables: You define exactly where network packets can travel.
  • Security Firewalls: Multi-layered security using Security Groups and Network ACLs.
⚠️ What Would Happen Without Networking Isolation?
  • Direct Internet Exposure: Every server, database, cache, and microservice would have a public IP and be exposed to global hackers and botnets.
  • No Internal Security Boundaries: If one web server got compromised, attackers could effortlessly jump straight to your confidential customer database.
  • IP Address Chaos: No control over private IP ranges, causing routing conflicts with on-premises datacenters and company VPNs.

THEORY 2. WHY DO WE NEED A VPC? (Real-World MERN Stack Example)

Let's understand why VPC is critical using a standard MERN (MongoDB / MySQL, Express, React, Node.js) application.

In a production application, you have 3 distinct layers:

  1. Frontend (React / Next.js): Needs to be reached by users on the public internet.
  2. Backend API (Node.js / Express): Processes business logic and talks to the database.
  3. Database (MongoDB / Amazon RDS / PostgreSQL): Stores highly sensitive user credentials, credit card info, and private customer records.
The Golden Security Rule: We NEVER want our database server to have a public IP or be reachable from the public internet!

How VPC Solves This Problem:

+-------------------------------------------------------------------------+ | PUBLIC INTERNET | | (End-Users Browsing) | +-------------------------------------------------------------------------+ │ ▼ +-------------------------------------------------------------------------+ | Application Load Balancer (ALB) | | (Accepts HTTPS on Port 443) | +-------------------------------------------------------------------------+ │ ▼ +-------------------------------------------------------------------------+ | PUBLIC SUBNET (Frontend / ALB) | | Has route to Internet Gateway (Accessible from Internet) | +-------------------------------------------------------------------------+ │ (Internal Private Traffic Only) ▼ +-------------------------------------------------------------------------+ | PRIVATE SUBNET 1 (Backend EC2) | | Node.js Express API — No Public IP — Internet can't touch it | +-------------------------------------------------------------------------+ │ (Database Port Only e.g., 5432/27017) ▼ +-------------------------------------------------------------------------+ | PRIVATE SUBNET 2 (RDS Database) | | Database Server — Completely isolated inside private network | +-------------------------------------------------------------------------+

Why This Architecture is Extremely Secure:

  • Zero Direct Database Attacks: Automated scanners on the internet cannot even ping your database because it has no public IP address and no route to the internet.
  • Controlled Entry Points: The only doorway into your network is the Load Balancer, which inspects SSL certificates and filters malicious requests.
  • Strict Tier Separation: Backend servers only accept traffic coming from the Load Balancer, and the Database only accepts traffic coming from the Backend servers.

Core Components Explained at a Glance:

  • AWS Region: The physical geographic area (e.g., Stockholm eu-north-1, N. Virginia us-east-1) where your VPC lives.
  • VPC (Virtual Private Cloud): Your private network boundary (e.g., 10.0.0.0/16) spanning all Availability Zones in that Region.

  • Private Subnet: A subdivision with no direct path to the Internet Gateway. Perfect for databases and backend microservices.

THEORY 4. 19 IMPORTANT VPC COMPONENTS (Master Reference)

Let's explain every single VPC component in crystal-clear language with practical real-world usage:

Component What it is Why it is used Practical Example
1. VPC A logically isolated virtual network dedicated to your AWS account. Provides complete isolation and control over your cloud infrastructure. Hosting your company's entire production web platform inside 10.0.0.0/16.
2. CIDR Block Classless Inter-Domain Routing — a notation representing a block of IP addresses. Defines how many IP addresses your VPC or subnet can have. 10.0.0.0/16 gives 65,536 IP addresses for your VPC.
3. Subnet A smaller section/sub-range of IP addresses inside a VPC, tied to 1 Availability Zone. Organizes resources into isolated segments based on security and routing needs. Creating 10.0.1.0/24 in AZ-a for frontend servers.
4. Public Subnet A subnet whose route table has a direct route (0.0.0.0/0) to an Internet Gateway. To host public-facing servers like Web Servers, Bastion Hosts, and ALBs. Web server running Apache/Nginx accessible by users worldwide.
5. Private Subnet A subnet that has NO direct route to an Internet Gateway. To keep critical systems hidden from public internet attacks. PostgreSQL/MySQL RDS database holding customer records.
6. Availability Zone (AZ) One or more physical, isolated data centers with redundant power and networking. Ensures High Availability (HA). If one AZ fails, your app runs in another. Launching EC2 instances across eu-north-1a and eu-north-1b.
7. Route Table A set of routing rules that determine where network packets are directed. Acts as the traffic police/GPS of your network. Rule: Send all unknown traffic 0.0.0.0/0 to Internet Gateway igw-12345.
8. Internet Gateway (IGW) A horizontally scaled, redundant AWS gateway that connects your VPC to the internet. Allows two-way communication between VPC public resources and the internet. Users visiting your public e-commerce website via browser.
9. NAT Gateway Network Address Translation service placed in a public subnet. Allows private instances to reach the internet (for updates/patches) without allowing internet users in. Private EC2 running sudo dnf update to download security patches.
10. Security Group (SG) A virtual stateful firewall attached directly to an EC2 instance / ENI. Controls inbound (incoming) and outbound (outgoing) traffic at instance level. Allow Inbound Port 80 (HTTP) and Port 22 (SSH only from your home IP).
11. Network ACL (NACL) A stateless firewall that operates at the subnet boundary level. Provides a second layer of defense with explicit ALLOW and DENY rules. Explicitly BLOCK/DENY a specific malicious hacker IP address (e.g. 198.51.100.4/32).
12. Elastic IP (EIP) A static, persistent public IPv4 address allocated to your AWS account. Maintains a constant public IP even if an instance is stopped and restarted. Required static IP attached to a NAT Gateway for outbound internet NATing.
13. VPC Peering A direct private network connection between two VPCs. Enables EC2 instances in different VPCs to communicate using private IPs. Connecting VPC-A (Development) with VPC-B (Shared Services) privately.
14. VPC Endpoint Private connection between your VPC and supported AWS services (e.g., S3, DynamoDB). Allows private instances to access S3 directly without needing a NAT Gateway. Private backend EC2 saving backup files to S3 bucket via Gateway Endpoint.
15. DHCP Option Sets Dynamic Host Configuration Protocol standards configured for your VPC. Configures domain name servers (DNS), domain name, and NTP servers for instances. Setting custom company DNS domain (e.g., corp.mycompany.internal).
16. Network Interface (ENI) A virtual network card attached to an EC2 instance. Holds private IP, MAC address, public IP association, and Security Groups. Attaching a secondary network card to an EC2 instance for management traffic.
17. Default VPC A ready-to-use VPC pre-created by AWS in every region. Allows beginners to immediately launch EC2 instances without configuring networking. Quick testing, running tutorials, or spinning up sandbox instances.
18. Default Route Table The automatically generated route table created when a VPC is born. Contains the default local routing rule for intra-VPC communication. Enables all subnets in the VPC to communicate with each other locally.
19. Main Route Table The specific route table that implicitly controls any subnet without an explicit association. Acts as a fallback safety route table for unassigned subnets. Keeping the Main Route Table private as a security best practice.

THEORY 5. AWS REGION AND AVAILABILITY ZONE

Understanding the hierarchy of AWS infrastructure is fundamental to building high-availability networks.

AWS GLOBAL INFRASTRUCTURE │ ▼ AWS REGION (e.g., eu-north-1) (Geographic Area: Stockholm) │ ┌───────────────────────────┼───────────────────────────┐ ▼ ▼ ▼ AZ: eu-north-1a AZ: eu-north-1b AZ: eu-north-1c (Data Center Cluster 1) (Data Center Cluster 2) (Data Center Cluster 3) │ │ │ ▼ ▼ ▼ Subnet-1 (10.0.1.0/24) Subnet-2 (10.0.2.0/24) Subnet-3 (10.0.3.0/24)

Key Concepts Explained:

  • AWS Region: A separate physical geographical location in the world (e.g., eu-north-1 Stockholm, us-east-1 N. Virginia, ap-south-1 Mumbai). A VPC spans an entire Region.
  • Availability Zone (AZ): One or more isolated data centers within a region, connected with ultra-low latency fiber networking. Each AZ is physically isolated from floods, fires, and power outages affecting other AZs.
  • Subnet Rule: A Subnet can ONLY live in exactly ONE Availability Zone. A subnet cannot span across multiple AZs!
High Availability (HA) Principle: If you put two Web Servers in eu-north-1a and one data center catches fire, your site goes down. But if you launch Web Server 1 in eu-north-1a and Web Server 2 in eu-north-1b behind a Load Balancer, your website continues running with zero downtime!
Note on AZ Names: Exact AZ names (like eu-north-1a) are mapped dynamically per AWS account by AWS for load distribution. Always check the AZs available in your specific console!

THEORY 6. CIDR BLOCK (Classless Inter-Domain Routing)

CIDR (pronounced "see-der") is simply a standardized way of writing an IP address followed by a slash (/) and a number to specify a range of IP addresses.

Let's understand 10.0.0.0/16 in super simple terms:

  • An IPv4 address has 32 bits in total (4 numbers separated by dots, each 0 to 255).
  • The number after the slash (/16) tells you how many bits are LOCKED (fixed network prefix).
  • The remaining bits (32 - 16 = 16 bits) are FREE for your devices to use.
  • 2^16 = 65,536 total IP addresses!

Common CIDR Sizes in AWS VPC:

CIDR Block Slash Prefix Total Available IPs Typical Use in AWS
10.0.0.0/16 /16 (16 locked bits) 65,536 IPs Standard recommended size for a whole VPC
10.0.1.0/24 /24 (24 locked bits) 256 IPs (251 usable by you) Standard size for a Subnet
10.0.2.0/24 /24 (24 locked bits) 256 IPs (251 usable by you) Standard size for a Subnet
10.0.1.50/32 /32 (32 locked bits) Exactly 1 IP Specific single host / Security Group rule
0.0.0.0/0 /0 (0 locked bits) All IPs in the World "The entire Internet" / default route
🚨 The 5 Reserved IPs in Every AWS Subnet!

In every AWS subnet you create, AWS automatically reserves 5 IP addresses for internal routing and management. If you create a /24 subnet (256 IPs), you get 256 - 5 = 251 usable IPs:

  • 10.0.1.0: Network address (standard network identifier).
  • 10.0.1.1: Reserved by AWS for the VPC Local Router.
  • 10.0.1.2: Reserved by AWS for Amazon DNS server.
  • 10.0.1.3: Reserved by AWS for future internal use.
  • 10.0.1.255: Network broadcast address (AWS does not support broadcast).

THEORY 7. CIDR PRACTICAL EXAMPLE — Subnet Slicing

How do subnet CIDR blocks fit inside a VPC CIDR block? Think of the VPC CIDR as a large whole pizza, and subnets as individual slices!

┌─────────────────────────────────────────────────────────────────────────┐ │ VPC CIDR: 10.0.0.0/16 │ │ (Total IPs: 10.0.0.0 to 10.0.255.255) │ │ │ │ ┌───────────────────────────────┐ ┌───────────────────────────────┐ │ │ │ PUBLIC SUBNET │ │ PRIVATE SUBNET │ │ │ │ CIDR: 10.0.1.0/24 │ │ CIDR: 10.0.2.0/24 │ │ │ │ Range: 10.0.1.0 - 10.0.1.255 │ │ Range: 10.0.2.0 - 10.0.2.255 │ │ │ │ (Web Servers, ALB) │ │ (Databases, Backend APIs) │ │ │ └───────────────────────────────┘ └───────────────────────────────┘ │ │ │ │ ┌───────────────────────────────┐ ┌───────────────────────────────┐ │ │ │ SPARE SUBNET AZ-B │ │ SPARE SUBNET AZ-B │ │ │ │ CIDR: 10.0.3.0/24 │ │ CIDR: 10.0.4.0/24 │ │ │ │ Range: 10.0.3.0 - 10.0.3.255 │ │ Range: 10.0.4.0 - 10.0.4.255 │ │ │ └───────────────────────────────┘ └───────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────────┘
CRITICAL RULE: Subnet CIDRs Must NEVER Overlap!

If you create a subnet with 10.0.1.0/24, you CANNOT create another subnet starting at 10.0.1.0. The next subnet must start at 10.0.2.0/24, 10.0.3.0/24, etc. If IP ranges overlap, the router will not know where to deliver your packets!

THEORY 8. PUBLIC VS PRIVATE SUBNET (Comparison)

What really makes a subnet "Public" vs "Private"?

⚡ CRITICAL EXAM / INTERVIEW POINT: Simply typing the word "public" in the Subnet Name tag does NOT make it public! A subnet is ONLY public if its associated Route Table has a route to an Internet Gateway (0.0.0.0/0 → igw-xxxx)!
Feature Public Subnet Private Subnet
Internet Route Has route 0.0.0.0/0 → Internet Gateway NO direct route to Internet Gateway (uses NAT GW or none)
Direct Inbound from Internet ✅ Yes (if Security Group allows) ❌ No (Completely blocked from internet)
Direct Outbound to Internet ✅ Yes (via Internet Gateway) ⚠️ Only via NAT Gateway (outbound only)
Public IP Addresses Instances get Public IPv4 or Elastic IP Instances have Private IP only (no public IP)
Typical Resources ALB, Web Servers, Bastion/Jump Host, NAT Gateway RDS Databases, Redis/Memcached, Backend Node/Java APIs
Security Exposure Medium/High (front-line defence) Highest security (completely isolated)

THEORY 9. INTERNET GATEWAY (IGW)

An Internet Gateway (IGW) is a highly available, VPC-level component that allows communication between your VPC and the outside internet. It performs Network Address Translation (NAT) for instances that have public IPv4 addresses.

Traffic Flow through Internet Gateway:

┌─────────────────┐ ┌─────────────────┐ ┌────────────────────────┐ ┌──────────────┐ │ User on Web │ ────► │ Internet Gateway│ ────► │ Public Route Table │ ────► │ Public EC2 │ │ (Browser Req) │ ◄──── │ (my-igw) │ ◄──── │ (0.0.0.0/0 -> igw-xxx) │ ◄──── │ (Web Server) │ └─────────────────┘ └─────────────────┘ └────────────────────────┘ └──────────────┘

Why Internet Gateway is Amazing:

  • Fully Managed & Scalable: You don't manage any servers; AWS scales bandwidth automatically with zero maintenance.
  • 1:1 VPC Attachment: Exactly ONE Internet Gateway can be attached to a VPC at any time.
  • Free of Charge: There is no hourly fee for the Internet Gateway itself (you only pay standard AWS data transfer rates).

THEORY 10. ROUTE TABLE

"A route table contains a set of rules (called routes) that determine where network traffic from your subnet or gateway is directed."

How Route Table Rules Work:

Every route has two parts: Destination (where the packet wants to go) and Target (the gateway, interface, or router that will handle it).

Example Public Route Table:

Destination (Where traffic wants to go) Target (Who sends it) Explanation
10.0.0.0/16 local Local Route: Any traffic meant for another server inside this VPC stays inside the VPC. (Default rule, cannot be deleted).
0.0.0.0/0 igw-0123456789abcdef0 Default Internet Route: Any traffic for an IP address outside the VPC is sent straight to the Internet Gateway!

Example Private Route Table:

Destination Target Explanation
10.0.0.0/16 local Intra-VPC communication between subnets.
0.0.0.0/0 nat-0123456789abcdef0 Outbound internet requests (e.g. software downloads) are routed through the NAT Gateway.

THEORY 11. NAT GATEWAY (Network Address Translation)

A NAT Gateway allows instances in a Private Subnet to initiate outbound connections to the internet (e.g., to download OS updates, npm packages, security patches) while preventing anyone on the internet from initiating inbound connections to those private instances!

How Outbound NAT Traffic Flows:

┌──────────────────┐ ┌──────────────────────┐ ┌────────────────────┐ ┌──────────────┐ │ Private EC2 / │ ────► │ Private Route Table │ ────► │ NAT Gateway │ ────► │ Internet │ │ Backend Server │ │ (0.0.0.0/0 -> nat-xx)│ │ (In Public Subnet) │ │ (OS Updates) │ └──────────────────┘ └──────────────────────┘ └────────────────────┘ └──────────────┘ │ Attached Elastic IP: 52.18.99.12 (Internet only sees this Elastic IP!)

4 Mandatory Requirements for a NAT Gateway:

  1. Must be placed inside a PUBLIC Subnet: It needs a direct path to the Internet Gateway.
  2. Must have an Elastic IP (Static Public IP) attached: So it can represent private servers on the internet.
  3. Private Route Table must point to it: Route 0.0.0.0/0 → nat-gateway-id.
  4. Subnet Association: The private route table must be associated with the private subnet.

Internet Gateway vs NAT Gateway Comparison:

Feature Internet Gateway (IGW) NAT Gateway
Communication Direction Two-Way (Inbound & Outbound) One-Way (Outbound only initiated by private instance)
Target Subnet Attached to VPC, used by Public Subnets Placed in Public Subnet, used by Private Subnets
Elastic IP Required? No Yes (Mandatory for public NAT gateway)
Cost Free (No hourly charge) Paid (~$0.045/hour + data transfer charges)

THEORY 12. SECURITY GROUP (Virtual Firewall)

A Security Group (SG) is a virtual, stateful firewall that controls inbound and outbound network traffic at the EC2 instance / ENI level.
[ INBOUND RULES ] Internet (0.0.0.0/0) ── Port 80 (HTTP) ──► [ ALLOWED ] ──► ┌────────────────┐ Internet (0.0.0.0/0) ── Port 443 (HTTPS) ─► [ ALLOWED ] ──► │ EC2 INSTANCE │ Hacker IP ── Port 22 (SSH) ──► [ BLOCKED ] │ (Web Server) │ My Home IP (1.2.3.4) ── Port 22 (SSH) ──► [ ALLOWED ] ──► └────────────────┘ │ [ OUTBOUND RULES ] ▼ All Traffic (0.0.0.0/0) ────────► [ ALLOWED ] (Default)

Key Characteristics of Security Groups:

  • Stateful: If you allow inbound traffic on port 80, the return response traffic is automatically allowed out, regardless of outbound rules!
  • Default Deny: By default, all inbound traffic is blocked until you explicitly add an ALLOW rule. (There are no DENY rules in SGs; anything not allowed is denied).
  • Security Group Referencing: You can set the source of a Security Group rule to be another Security Group ID (e.g., allow database port 5432 ONLY from sg-backend).

THEORY 13. NETWORK ACL (NACL — Subnet Firewall)

A Network Access Control List (NACL) is an optional layer of security for your VPC that acts as a stateless firewall at the Subnet boundary level.

Security Group vs Network ACL (Master Comparison):

Feature Security Group Network ACL (NACL)
Level of Operation Instance / ENI Level Subnet Level
State Stateful (Return traffic is automatically allowed) Stateless (Return traffic MUST be explicitly allowed)
Rule Types ALLOW rules only ALLOW and DENY rules
Rule Evaluation All rules evaluated before deciding Processed in numerical order (lowest number first, e.g. 100 before 200)
Default Custom State Denies all inbound, allows all outbound Custom NACL denies all inbound & outbound by default

THEORY 14. ELASTIC IP (EIP)

An Elastic IP address (EIP) is a static, persistent public IPv4 address allocated to your AWS account that does not change when an instance is stopped and restarted.
  • Why Used: Regular EC2 public IPs change whenever you Stop and Start an instance. Elastic IPs stay permanent until you explicitly release them.
  • NAT Gateway Requirement: Every public NAT Gateway requires exactly one Elastic IP.
  • Cost Note: AWS charges a small fee (~$0.005/hour) for all public IPv4 addresses, and also if an Elastic IP is allocated but not attached to a running instance. Always release unattached Elastic IPs!

THEORY 15 & 16. DEFAULT VPC VS CUSTOM VPC

15. What is a Default VPC?

When you open a brand new AWS account, AWS automatically creates a Default VPC in every region with a default CIDR (usually 172.31.0.0/16), one default public subnet in every Availability Zone, an Internet Gateway attached, and default route table configured.

16. Comparison: Default VPC vs Custom VPC

Criteria Default VPC Custom VPC
Creation Pre-created automatically by AWS Created manually by you from scratch
CIDR Block Fixed (typically 172.31.0.0/16) Fully customizable (e.g., 10.0.0.0/16)
Subnets All subnets are Public by default You decide how many public and private subnets
Internet Gateway Pre-attached Created and attached manually
Production Suitability ❌ Not recommended for production ✅ Industry standard for production architectures
Best For Fast learning, experimentation, quick testing Real-world enterprise & secure applications

PRACTICAL 17. PRACTICAL 1 — Create a Custom VPC

Step-by-Step AWS Management Console Guide

  1. Log in to the AWS Management Console.
  2. In the top search bar, type VPC and select the VPC service.
  3. Ensure you are in your desired Region (e.g., Stockholm eu-north-1, N. Virginia us-east-1).
  4. Click the orange Create VPC button.
  5. Under Resources to create, select VPC only (this teaches you each component individually).
  6. Fill in the details:
    • Name tag: my-custom-vpc
    • IPv4 CIDR block: Select IPv4 CIDR manual input
    • IPv4 CIDR: 10.0.0.0/16
    • Tenancy: Default
  7. Click Create VPC at the bottom.
  8. Verification: Look at your newly created VPC. Note down the generated VPC ID (e.g., vpc-0a1b2c3d4e5f6g7h8), State: Available, and CIDR: 10.0.0.0/16.
What Happened Behind the Scenes: AWS carved out an isolated software network containing 65,536 private IP addresses and automatically created a Default Route Table, Network ACL, and DHCP options set for this VPC.

PRACTICAL 18. PRACTICAL 2 — Create Public & Private Subnets

Creating Subnet 1: Public Subnet

  1. In the VPC Dashboard left sidebar, click Subnets.
  2. Click Create subnet.
  3. VPC ID: Select your my-custom-vpc.
  4. Subnet name: public-subnet-1a
  5. Availability Zone: Choose the first AZ (e.g., eu-north-1a).
  6. IPv4 CIDR block: 10.0.1.0/24
  7. Click Create subnet.

Creating Subnet 2: Private Subnet

  1. Click Create subnet again.
  2. VPC ID: Select my-custom-vpc.
  3. Subnet name: private-subnet-1a
  4. Availability Zone: Choose the same or another AZ (e.g., eu-north-1a).

Instead of typing IP addresses into Security Groups, you can reference Security Group IDs as the source! This ensures zero unauthorized access even if internal IPs change.

[ Internet Users ] │ Port 80/443 (Source: 0.0.0.0/0) ▼ ┌──────────────────────────────────────┐ │ ALB Security Group: sg-alb │ └──────────────────────────────────────┘ │ Port 5000 / 3000 (Source: sg-alb) <-- Only ALB allowed! ▼ ┌──────────────────────────────────────┐ │ Backend Security Group: sg-backend │ └──────────────────────────────────────┘ │ Port 27017 / 5432 (Source: sg-backend) <-- Only Backend allowed! ▼ ┌──────────────────────────────────────┐ │ Database Security Group: sg-db │ └──────────────────────────────────────┘
Security Group Inbound Type & Port Allowed Source Security Reason
sg-alb HTTP (80) & HTTPS (443) 0.0.0.0/0 (Anywhere) Public users must be able to load the web application.
sg-backend Custom TCP (Port 5000) sg-alb (ALB SG ID) Nobody can bypass the load balancer to hit the backend directly.
sg-db PostgreSQL (5432) / Mongo (27017) sg-backend (Backend SG ID) Only the backend servers can execute database queries.

THEORY 29 & 30. VPC PEERING & VPC ENDPOINTS

29. VPC Peering

VPC Peering is a direct network connection between two VPCs that enables you to route traffic between them using private IPv4 or IPv6 addresses.
┌─────────────────────────┐ ┌─────────────────────────┐ │ VPC A (10.0.0.0/16) │ ◄─── [ VPC PEERING ] ──► │ VPC B (20.0.0.0/16) │ │ Production VPC │ (Private Fiber) │ Shared Analytics VPC │ └─────────────────────────┘ └─────────────────────────┘
  • No Overlapping CIDRs: VPC A (10.0.0.0/16) and VPC B (20.0.0.0/16) must have completely distinct IP ranges.
  • No Transitive Peering: If A is peered with B, and B is peered with C, A CANNOT talk to C through B. (You must create a direct peering between A and C, or use AWS Transit Gateway).
  • Route Table Updates Required: You must add a route in VPC A pointing to VPC B's CIDR via the peering connection ID (pcx-xxxx).

30. VPC Endpoints (PrivateLink & Gateway Endpoints)

How do private EC2 instances upload logs to Amazon S3 without going over the public internet or paying for a NAT Gateway?

A VPC Endpoint enables private connections between your VPC and supported AWS services without requiring an Internet Gateway, NAT device, VPN, or AWS Direct Connect.
  • Gateway Endpoints (Free): Used for Amazon S3 and Amazon DynamoDB. You add a route in your route table targeting the endpoint ID (vpce-xxxx).
  • Interface Endpoints (Paid PrivateLink): Uses an Elastic Network Interface (ENI) with a private IP inside your subnet to connect to services like SQS, SNS, Secrets Manager, etc.

THEORY 31, 32, 33 & 34. FLOW LOGS, DNS, ENI & ROUTING SCENARIOS

31. VPC Flow Logs

VPC Flow Logs captures metadata about IP traffic going to and from network interfaces in your VPC. Logs can be published to Amazon CloudWatch Logs or Amazon S3.

Sample Flow Log Entry:
2 123456789010 eni-abc123de 198.51.100.15 10.0.1.25 443 51234 6 10 8400 1620000000 1620000060 ACCEPT OK
Shows timestamp, source IP, destination IP, port 443, and whether it was ACCEPT (allowed by SG/NACL) or REJECT (blocked).

32. VPC DNS Settings

  • DNS Resolution (enableDnsSupport): When enabled, AWS resolves DNS hostnames through the Amazon-provided DNS server (at VPC CIDR + 2, e.g. 10.0.0.2).
  • DNS Hostnames (enableDnsHostnames): When enabled, instances launched in the VPC get public DNS hostnames (e.g. ec2-xx-xx-xx.compute.amazonaws.com).

33. Elastic Network Interface (ENI)

An ENI is a virtual network interface card (NIC) that includes: a primary private IPv4, one or more secondary private IPs, an Elastic IP association, MAC address, and Security Groups.

38. Top 15 VPC Errors, Root Causes & Fixes

Error / Symptom Possible Root Cause How to Fix
1. EC2 has no Internet access Missing 0.0.0.0/0 → igw-xxxx route in Route Table. Add default route 0.0.0.0/0 targeting the Internet Gateway in your Route Table.
2. Website does not load (Browser timeout) Security Group is blocking Inbound HTTP (Port 80) or HTTPS (443). Add Inbound rule to Security Group: Type: HTTP, Port: 80, Source: 0.0.0.0/0.
3. SSH connection timed out Security Group Port 22 not open to your current Public IP address. Update Security Group Inbound rule for SSH (Port 22) with your current public IP (or 0.0.0.0/0 for testing).

5. NAT Gateway status is Pending or Failing Placed in a Private Subnet or missing Elastic IP. Recreate NAT Gateway inside the Public Subnet and attach an Elastic IP.
6. Subnet using wrong route table Subnet not explicitly associated with custom route table (defaults to Main RT). Go to Route Tables → Subnet Associations → Explicitly associate your subnet.
7. Internet Gateway not working IGW was created but never Attached to the VPC. Select IGW → Actions → Attach to VPC → Select your custom VPC.
8. EC2 instance has NO Public IP "Auto-assign public IPv4" was disabled in subnet settings during launch. Enable auto-assign on subnet or allocate and associate an Elastic IP to the EC2 instance.
9. Network ACL blocking traffic Custom NACL denying ephemeral ports (1024-65535) or missing outbound allow. Ensure NACL Inbound and Outbound rules allow necessary ports and Ephemeral Return Ports.

11. EC2 Instance Connect fails Security Group blocks AWS EC2 Instance Connect service IP ranges for Port 22. Allow port 22 in Security Group from EC2 Instance Connect IP block for your region.
12. RDS database unreachable from backend RDS Security Group not allowing port (5432/3306) from Backend Security Group. Edit RDS Security Group to allow Inbound DB port from sg-backend.
13. DNS hostnames not resolving enableDnsHostnames or enableDnsSupport is set to false. Edit VPC settings and check both Enable DNS resolution and Enable DNS hostnames.
14. Out of available IP addresses Subnet CIDR too small (e.g. /28 = only 11 usable IPs exhausted). Create a larger subnet (e.g. /24) or attach a secondary CIDR block to the VPC.
15. VPC Peering traffic not flowing Route tables in both VPCs not updated with peering connection route. Add routes in BOTH VPC route tables pointing to the other VPC's CIDR via pcx-xxxx.

THEORY 40 & 41. VPC BEST PRACTICES & DEFENSE-IN-DEPTH SECURITY

40. 14 Essential VPC Best Practices

  • 1. Plan CIDR Sizes Carefully: Use standard RFC 1918 private ranges (10.0.0.0/16 is industry standard).
  • 2. Prevent CIDR Overlaps: Ensure your AWS VPC CIDRs never clash with corporate VPNs or other peered VPCs.
  • 3. Multi-AZ by Default: Always create subnets across at least 2 Availability Zones for high availability.
  • 4. Keep Databases in Private Subnets: Never give an RDS database a public IP or put it in a public subnet.
  • 5. Principle of Least Privilege: Only open exact ports needed (e.g. 443 for HTTPS, never open 0-65535).
  • 6. Restrict SSH Access: Never allow SSH (Port 22) from 0.0.0.0/0 in production; use AWS SSM Session Manager instead.
  • 7. Chain Security Groups: Reference Security Group IDs rather than hardcoded IP addresses.
  • 8. Use VPC Endpoints for S3 & DynamoDB: Keeps AWS service traffic on private AWS backbone and saves NAT Gateway costs.
  • 9. Monitor with VPC Flow Logs: Enable flow logs for compliance, incident investigation, and network troubleshooting.
  • 10. Keep Main Route Table Private: Leave the default main route table strictly private so new subnets are never accidentally made public.
  • 11. Cost Governance: Delete unused NAT Gateways and release unattached Elastic IPs promptly.
  • 12. Use Descriptive Tags: Tag every resource with Environment=Production, Project=MERN, Owner=TeamDevOps.
  • 13. Avoid Unnecessary Public IPs: Only public-facing Load Balancers and NAT Gateways need public IPs.
  • 14. Document Architecture: Maintain clear architectural network topology diagrams for your team.

INTERVIEW 45. TOP 30+ AWS VPC INTERVIEW QUESTIONS & ANSWERS

Q1. What is an AWS VPC?

A logically isolated virtual network dedicated to your AWS account where you launch and manage AWS resources with full control over IP addressing, subnets, and routing.

Q2. Why do we need a custom VPC?

To establish isolated, secure multi-tier architectures (e.g. keeping databases completely private from the public internet) and customize IP ranges to avoid enterprise routing conflicts.

Q3. What is CIDR?

Classless Inter-Domain Routing. A notation (e.g. 10.0.0.0/16) specifying an IP address and its network mask prefix to define an IP address range.

Q4. What is a Subnet?

A sub-range of IP addresses inside a VPC that resides inside a single Availability Zone, used to group resources by routing and security needs.

Q5. How many IP addresses does AWS reserve in every subnet?

Exactly 5 IP addresses (the first 4 and the last 1: network address, router, DNS, future use, and broadcast).

Q6. What makes a Subnet "Public"?

Its associated Route Table has a default route pointing to an Internet Gateway (0.0.0.0/0 → igw-xxxx) and instances have public IPs. Naming it "public" alone does not make it public.

Q7. What is a Private Subnet?

A subnet whose route table has NO route to an Internet Gateway, keeping resources completely unreachable from the public internet.

Q8. What is an Internet Gateway (IGW)?

A managed, redundant VPC-level component that enables two-way communication between instances in public subnets and the internet.

Q9. How many Internet Gateways can you attach to a single VPC?

Exactly ONE Internet Gateway per VPC at any time.

Q10. What is a NAT Gateway?

A managed service in a public subnet allowing private instances to initiate outbound connections to the internet without allowing inbound internet connections in.

Q11. Where must a NAT Gateway be deployed?

In a Public Subnet, because it requires direct internet routing via an Internet Gateway and an Elastic IP.

Q12. What is a Route Table?

A set of destination-target rules that directs network traffic originating from subnets inside a VPC.

Q13. What is a Security Group?

A stateful virtual firewall operating at the EC2 instance / ENI level that filters inbound and outbound traffic.

Q14. What does "Stateful Firewall" mean?

If inbound traffic is allowed, the corresponding outbound response traffic is automatically allowed out, regardless of outbound rules.

Q15. What is a Network ACL (NACL)?

A stateless firewall operating at the subnet boundary level that supports both ALLOW and DENY rules evaluated in numerical order.

Q16. What is the difference between Security Group and NACL?

Security Groups operate at the instance level (stateful, allow rules only). NACLs operate at the subnet level (stateless, allow and deny rules).

Q17. What is an Elastic IP (EIP)?

A persistent, static public IPv4 address that does not change when an instance stops and starts.

Q18. What is VPC Peering?

A 1-to-1 private network connection between two VPCs allowing them to communicate via private IPs without traversing the public internet.

Q19. Is VPC Peering transitive?

No. If VPC A is peered with B, and B with C, A cannot reach C through B without a direct peering connection or AWS Transit Gateway.

Q20. What is a VPC Endpoint?

A private connection enabling EC2 instances in private subnets to talk to AWS services (like S3 and DynamoDB) without using a NAT Gateway or public internet.

Q21. What are the two types of VPC Endpoints?

Gateway Endpoints (free, for S3 & DynamoDB) and Interface Endpoints (powered by AWS PrivateLink with an ENI).

Q22. What is VPC Flow Logs?

A feature that captures IP network traffic flow data (source, destination, port, accept/reject status) for network monitoring and security audits.

Q23. What is an Elastic Network Interface (ENI)?

A virtual network card in a VPC that contains private IPs, MAC addresses, and attached Security Groups.

Q24. Why should databases (RDS) be in private subnets?

To prevent direct internet exposure, brute force attacks, and data breaches. Databases should only be reachable by authorized backend application servers.

Q25. Can a Subnet span across multiple Availability Zones?

No. A subnet is strictly confined to exactly ONE Availability Zone.

Q26. What is the Main Route Table?

The default route table automatically assigned to any subnet that is not explicitly associated with another custom route table.

Q27. How does an EC2 instance in a private subnet download updates?

Via a NAT Gateway located in a Public Subnet with a route 0.0.0.0/0 → nat-gateway-id in the private route table.

Q28. What is Security Group Referencing?

Setting the source of a Security Group rule to another Security Group's ID (e.g. sg-alb), allowing traffic only from instances carrying that specific security group.

Q29. How do you troubleshoot an EC2 instance that cannot connect to the internet?

Check: 1) Public IP exists, 2) Route table has 0.0.0.0/0 → IGW, 3) IGW is attached to VPC, 4) Security Group allows outbound traffic, 5) NACL allows outbound & ephemeral return traffic.

Q30. Explain a 3-Tier VPC Architecture.

Tier 1: Public Subnet with ALB for internet users; Tier 2: Private Subnet with App/Backend EC2s; Tier 3: Isolated Private Subnet for RDS databases.

THEORY 46. REAL-WORLD 3-TIER ENTERPRISE ARCHITECTURE

The 3-tier architecture is the global industry standard for enterprise cloud deployments, separating presentation, logic, and data layers across multiple Availability Zones.

REVISION 47. FINAL QUICK REVISION CHEATSHEET

  • VPC = Your logically isolated private cloud network in an AWS region.
  • CIDR = IP address range definition (e.g. 10.0.0.0/16 = 65,536 IPs).
  • Subnet = Smaller IP network slice locked to exactly one Availability Zone.
  • Public Subnet = Subnet with an explicit route 0.0.0.0/0 → Internet Gateway.
  • Private Subnet = Subnet with NO direct path to the Internet Gateway.
  • Internet Gateway = Connects public instances to the internet (2-way traffic).
  • NAT Gateway = Allows private instances outbound internet access without inbound access.
  • Route Table = The traffic GPS containing destination-to-target routing rules.
  • Security Group = Stateful virtual firewall at the instance/ENI level.
  • Network ACL = Stateless firewall with allow/deny rules at the subnet boundary.
  • Elastic IP = Fixed, static public IPv4 address that never changes.
  • VPC Peering = Direct private fiber connection linking two distinct VPCs.
  • VPC Endpoint = Private pathway to S3/DynamoDB without using internet or NAT.
  • VPC Flow Logs = Network traffic telemetry used for security audits and diagnostics.
