AWS Lambda — Hinglish Guide

AWS Lambda — Beginner Study Notes

Hinglish edition • padhai, revision, MERN developers, aur AWS interview preparation ke liye

1. AWS Lambda Introduction

Aasaan definition AWS Lambda AWS ki serverless compute service hai. Isme hume server create, maintain, patch ya continuously run karne ki zarurat nahi hoti. Hum apna code Lambda function ke form mein deploy karte hain aur AWS us code ko required time par run karta hai.

Lambda kya hai?

Ek service jahan hum code (“function”) upload karte hain, aur AWS use tab chalata hai jab koi cheez use trigger kare — HTTP request, file upload, schedule, etc.

Hum Lambda kyun use karte hain?

  • Server setup ya patch karne ki zarurat nahi.
  • Demand ke hisaab se automatically scale hota hai.
  • Mainly actual usage ka payment, idle time ka nahi.
  • Event-driven aur API workloads ke liye achha fit.

“Serverless” ka matlab kya hai? Kya isme servers hote hi nahi?

Important Serverless ka matlab ye nahi ki servers hote hi nahi. Servers abhi bhi exist karte hain, lekin AWS underlying infrastructure hamare liye manage karta hai.

Infrastructure kaun manage karta hai? Lambda kab execute hota hai?

AWS servers, OS patching aur scaling manage karta hai. Aapka code sirf tab execute hota hai jab function invoke (trigger) hota hai — server ki tarah hamesha nahi chalta rehta.

2. Simple Real-World Example: Image Upload

User | v S3 | v Lambda | v Process Image | v Save Result
  1. User S3 par image upload karta hai.
  2. S3 ek event generate karta hai.
  3. Lambda trigger hota hai.
  4. Lambda image download/read karta hai.
  5. Lambda image process karta hai (jaise resize).
  6. Lambda result store karta hai (jaise wapas S3 mein, ya metadata DynamoDB mein).

User image upload karta hai, S3 event fire karta hai, Lambda automatically chalta hai, image process hoti hai, aur result save ho jata hai — koi server hamesha chalu rakhne ki zarurat nahi.

3. MERN-style Project Example

Frontend: React • Backend logic: Node.js-style code • Database: MongoDB / DynamoDB • Serverless function: AWS Lambda

React | v API Gateway | v AWS Lambda | v DynamoDB | v Response | v React

Normal MERN mein Express server EC2 par hamesha chalta rehta hai. Serverless approach mein har API route ek chhota Lambda function ban sakta hai, jo sirf request aane par chalta hai.

4. EC2 vs Lambda

EC2: hum virtual server manage karte hain, wo continuously chalta hai, hum OS/config manage karte hain, hum instance size choose karte hain, hum allocated/running infrastructure ka payment karte hain.

Lambda: koi server management nahi, code invoke hone par chalta hai, AWS infrastructure manage karta hai, execution capacity automatically handle hoti hai, pricing current Lambda pricing model ke hisaab se usage par based hoti hai.

5. Lambda Function Kya Hai?

Definition Lambda function ek code ka piece hai jise AWS kisi event ya invocation ke response mein chalata hai.

Lambda function in cheezon se milkar bana hota hai:

  • Code — hamara logic
  • Runtime — language environment (Node.js, Python, etc.)
  • Handler — entry-point function
  • Configuration — memory, timeout, etc.
  • Permissions — execution role (IAM)
  • Environment variables — config values
  • Memory — allocated resources
  • Timeout — per invocation maximum run time

    return {
        statusCode: 200,
        body: JSON.stringify({

    };

9. Lambda Handler

Handler = Lambda function ka entry point — wo exact function jise AWS execution start karne ke liye call karta hai. Example: exports.handler.

Lambda configuration ki handler setting is format mein hoti hai:

filename.functionName

Agar file index.js hai aur exported function handler hai, to handler configuration hai:

index.handler

Ek aur example: agar file app.js hai aur exported function handler hai, to configuration app.handler hoga.

Handler setting AWS ko batati hai ki kaunsi file ke andar kaunsa function call karna hai. Format hamesha filename.functionName hota hai.

10. Event aur Context

exports.handler = async (event, context) => {
    console.log(event);
    console.log(context);

    return {
        statusCode: 200,
        body: "Hello"
    };
};
  • event — ismein wo jaankari hoti hai ki Lambda ko kisne trigger kiya (jaise API Gateway se aayi HTTP request ka body/headers, ya S3 file ki details).
  • context — ismein Lambda execution environment aur is invocation ki jaankari hoti hai (jaise kitna time bacha hai, request ID, function name).

event mein bataya jata hai ki trigger kis cheez ne kiya aur kya data bheja gaya. context mein invocation aur environment ki jaankari hoti hai, jaise kitna time bacha hai.

16. Lambda + DynamoDB CRUD

OperationRoute
CreatePOST /users
ReadGET /users/{id}
UpdatePUT /users/{id}
DeleteDELETE /users/{id}
// Create
exports.createUser = async (event) => {
    const body = JSON.parse(event.body);
    await dynamoDB.send(new PutCommand({
        TableName: "Users",
        Item: { userId: body.userId, name: body.name, email: body.email }
    }));
    return { statusCode: 201, body: JSON.stringify({ message: "Created" }) };
};

// Read
exports.getUser = async (event) => {
    const out = await dynamoDB.send(new GetCommand({
        TableName: "Users", Key: { userId: event.pathParameters.id }
    }));
    return { statusCode: 200, body: JSON.stringify(out.Item) };
};

Update aur Delete bhi isi pattern se hote hain, UpdateCommand aur DeleteCommand use karke (poori syntax ke liye DynamoDB notes dekho). Har route ke liye alag Lambda function banana ek common serverless pattern hai.

Har route ke liye alag chhota function likhna common practice hai. Isse code samajhna aur deploy karna aasaan rehta hai.

23. IAM Role aur Execution Role

Lambda ko AWS resources access karne ke liye permissions chahiye.

Lambda | v IAM Execution Role | v DynamoDB

Execution role AWS ko batati hai ki Lambda function kya access kar sakta hai.

DynamoDB ke liye example permissions:

dynamodb:GetItem
dynamodb:PutItem
dynamodb:UpdateItem
dynamodb:DeleteItem

Almost har function ko logging permissions bhi chahiye:

logs:CreateLogGroup
logs:CreateLogStream
logs:PutLogEvents
Least privilege Sirf wahi actions aur resources do jo function ko waqai chahiye. Production Lambda function ke liye AdministratorAccess recommend ya attach mat karo.

IAM User vs IAM Role vs Lambda Execution Role

  • IAM User: kisi person ya application ke liye long-term identity, usually static credentials ke saath.
  • IAM Role: permissions ka set jo koi trusted identity ya service temporarily assume kar sakti hai (long-term keys nahi).
  • Lambda Execution Role: wo specific IAM role jise Lambda function chalte time assume karta hai, jisse use us invocation ke liye temporary AWS permissions milti hain.

Lambda function chalte time apni execution role “assume” karta hai, aur usse temporary permissions milti hain. Hamesha least privilege follow karo.

26. Timeout aur Memory

Timeout

Har Lambda function ki ek maximum execution duration (timeout) hoti hai — ek invocation ke liye ye maximum time hai jitna wo chal sakta hai. Agar function configured timeout se zyada time le, to execution ruk jata hai.

Dhyan rakho Exact maximum duration ke liye current AWS Lambda documentation/console dekho, kisi purani value ko hard-code mat karo, kyunki limits badal sakti hain.

Memory

Memory configuration function ko milne wale resources ko affect karti hai, CPU allocation samet — zyada memory se zyada CPU bhi mil sakta hai. Chhote workload ke liye kam memory kaafi hai; heavy processing ke liye zyada memory chahiye ho sakti hai. Memory badhane se cost par asar padta hai, kyunki Lambda pricing configured resources aur execution duration se judi hoti hai.

Timeout se zyada time lage to Lambda ruk jata hai. Memory jitni zyada, utna CPU bhi mil sakta hai, lekin cost bhi badh sakti hai — workload ke hisaab se balance karo.

27. Cold Start aur Concurrency

Cold start

Cold start tab hota hai jab function chalane se pehle AWS ko naya execution environment initialize karna padta hai. Warm invocation existing environment reuse karta hai (fast); cold invocation ko naya environment chahiye (thoda zyada time le sakta hai).

Pehli request thodi slow ho sakti hai (cold start), lekin agar environment reuse ho jaye to baad ki requests fast hoti hain (warm).

Concurrency

Concurrency = ek saath process ho rahe Lambda invocations ki sankhya. 1 request → 1 execution; 100 simultaneous requests → potentially kai concurrent executions. Lambda AWS limits aur aapke account/function configuration ke hisaab se concurrent executions scale kar sakta hai.

Reserved concurrency

Kisi specific function ke liye concurrency limit reserve/set karta hai. Ye help karta hai: concurrency control karne mein, downstream services (jaise database) ko protect karne mein, aur ek function ko poori account ki concurrency use karne se rokne mein.

Provisioned concurrency

Execution environments ko pehle se initialize aur ready rakhta hai, taaki supported workloads ke liye cold-start latency kam ho (extra cost par).

Reserved concurrencyProvisioned concurrency
PurposeEk concurrency ceiling limit/guarantee karnaEnvironments ko pehle se garam rakh kar cold starts kam karna
Cost par asarApne aap koi extra cost nahiReady-rakhe gaye environments ke liye extra cost
Typical useDownstream DB ko protect karna, noisy function ko limit karnaLatency-sensitive APIs

Reserved concurrency limit lagata hai (kitne max invocations chalein), aur Provisioned concurrency environments ko pehle se garam rakhta hai taaki cold start kam ho.

28. Lambda Scaling aur Statelessness

Scaling

Traditional EC2: Traffic -> Manually/automatically servers add karna Lambda: Traffic -> AWS execution environments aur concurrency manage karta hai

Invocation demand badhne par Lambda automatically extra execution environments bana sakta hai, service/account limits ke andar.

Statelessness

Lambda functions ko generally stateless treat karna chahiye. Permanent application data ke liye local execution environment storage par depend mat karo. Lambda ka local /tmp storage temporary hai aur permanent database storage jaisa treat nahi karna chahiye.

Persistent data ke liye DynamoDB, S3, RDS, ya koi doosri persistent service use karo.

Lambda ko permanent storage mat samjho; important data hamesha DynamoDB/S3/RDS jaisi persistent service mein save karo.

Important Lambda ko VPC mein daalne se use automatically internet access nahi mil jata. Private subnets se outbound internet access ke liye zarurat padne par NAT Gateway jaisi appropriate networking chahiye ho sakti hai.

Error handling

exports.handler = async (event) => {

    try {

        // application logic

        return {
            statusCode: 200,
            body: JSON.stringify({
                message: "Success"
            })
        };

    } catch (error) {

        console.error(error);

        return {
            statusCode: 500,
            body: JSON.stringify({
                message: "Internal Server Error"
            })
        };
    }
};

try normal logic chalata hai; agar koi error throw ho, to catch use handle karta hai aur crash hone ke bajay ek proper error response return karta hai.

Retries

Lambda ka retry behavior invocation type aur event source par depend karta hai:

  • Synchronous invocation (jaise API Gateway se): caller ko result/error directly milta hai; Lambda khud automatically retry nahi karta.
  • Asynchronous invocation (jaise S3, SNS se): AWS Lambda ke asynchronous invocation behavior ke hisaab se failed invocations retry kar sakta hai.
  • Event-source mappings (jaise SQS, DynamoDB Streams): in services ka apna retry/visibility/dead-letter behavior hota hai.
Retry behavior har trigger ke liye same nahi hota — us specific service ki documentation check karo.

Dead Letter Queue (DLQ)

DLQ = Dead Letter Queue.

Lambda | v Processing fails | v Retry | v Phir bhi fail | v DLQ

DLQ support/configuration invocation type aur architecture par depend karta hai (jaise asynchronous invocations aur kuch event sources DLQ ya similar failure-destination configurations support karte hain).

Agar processing baar baar fail ho, to failed message/event ko DLQ mein bhej diya jata hai taaki wo lost na ho aur baad mein inspect kiya ja sake.

Versioning aur Aliases

Versions se function ke immutable snapshots publish kar sakte ho (jaise Version 1, Version 2, Version 3) — changes track karne aur zarurat par rollback karne ke liye useful.

Aliases specific versions ke naam wale pointers hote hain, jaise dev → version 2, prod → version 3. Isse production application ek stable version par point kar sakti hai, jab development naye version par chalta rahe.

Environments ke saath deployment

dev -> Lambda version staging -> Lambda version production -> Lambda version

Har environment (dev/staging/production) ke liye alag configuration rakhne se production data ya traffic par directly changes test karne se bacha ja sakta hai.

Versions se hum purane snapshots rakh sakte hain, aur aliases se ye control karte hain ki dev/staging/prod kaunsa version use kare.

32. Security, Cost aur Limitations

Security

  • IAM aur execution roles — least privilege
  • Config ke liye environment variables; sensitive secrets ke liye Secrets Manager
  • Encryption (at rest/in transit, jahan applicable ho)
  • Visibility ke liye CloudWatch Logs
  • Private resources access karte time VPC security groups
  • API authentication (jaise API Gateway authorizers se)
Important AWS access keys Lambda code mein directly mat daalo. AWS services access karne ke liye Lambda execution role prefer karo.

Cost

Lambda pricing generally in factors par based hoti hai: requests ki sankhya, duration, configured memory/resources, aur use ki gayi additional features/services. Lambda function ko “on” rakhne ke liye normally hume continuously chalne wale EC2 server ka payment nahi karna padta.

Important Lambda hamesha free nahi hota. AWS Free Tier eligibility aur limits badal sakti hain — current AWS pricing check karo.

Limitations

  • Maximum execution duration (timeout)
  • Memory limits
  • Package/deployment size limits
  • Concurrency limits
  • Cold starts
  • Stateless execution model
  • Har workload ke liye ideal nahi hai

Achha fit: APIs, event processing, automation, scheduled tasks, file processing, serverless applications.

Kam suitable ho sakta hai: lambe chalne wale processes, persistent processes wale workloads, kuch highly stateful applications.

Lambda short, event-driven kaamon ke liye badhiya hai. Lambe chalne wale ya bahut stateful processes ke liye EC2/ECS jaisa option better ho sakta hai.

34. Lambda vs Node.js Server, aur Common Mistakes

Lambda vs traditional Node.js server

Traditional Node.js: Client -> EC2 -> Node.js Server -> Database Serverless: Client -> API Gateway -> Lambda -> Database

Traditional Node server ek continuously running application process hai. Lambda invocations ke response mein functions chalata hai, requests ke beech mein koi process nahi chalta rehta.

Common Lambda mistakes

  1. Credentials hard-code karna
  2. Bina zarurat AdministratorAccess dena
  3. Timeout settings ignore karna
  4. Memory configuration ignore karna
  5. Unnecessary/repeated database connections banana
  6. Ye maan lena ki local (/tmp) storage permanent hai
  7. Errors handle na karna
  8. Logs monitor na karna
  9. Lambda ko lambe chalne wale workloads ke liye use karna
  10. Concurrency control na karna
  11. Latency-sensitive apps mein cold starts ignore karna
  12. Kharab IAM permissions (bahut broad ya bahut narrow)
  13. Secrets ko directly code mein daalna

Sabse common galtiyan: credentials hard-code karna, zyada IAM permissions dena, aur Lambda ko lambi-chalne-wali processes ke liye use karna.

35. Interview Questions & Answers

Q1. AWS Lambda kya hai?
Ek serverless compute service jo events ke response mein aapka code chalati hai, bina aapko servers manage karne ki zarurat ke.
Q2. Serverless kya hai?
Ek model jisme AWS underlying servers/infrastructure aapke liye manage karta hai.
Q3. Kya serverless ka matlab hai servers hote hi nahi?
Nahi. Servers abhi bhi exist karte hain; AWS unhe aapki jagah manage karta hai.
Q4. Lambda function kya hai?
Code ka ek piece jise AWS kisi event ya invocation ke response mein chalata hai.
Q5. Lambda handler kya hai?
Wo entry-point function jise AWS execution start karne ke liye call karta hai, jaise exports.handler.
Q6. Event kya hai?
Wo input data jo batata hai ki invocation ko kisne trigger kiya.
Q7. Context object kya hai?
Execution environment aur current invocation ki jaankari (jaise bacha hua time, request ID).
Q8. Lambda trigger kya hai?
Ek event source (S3, API Gateway, SQS, EventBridge, etc.) jo Lambda ko execute karwata hai.
Q9. Lambda API Gateway ke saath kaise kaam karta hai?
API Gateway ek HTTP endpoint deta hai, requests ko Lambda tak route karta hai, aur Lambda ka response client ko wapas deta hai.
Q10. Lambda DynamoDB ke saath kaise kaam karta hai?
Lambda AWS SDK use karke (IAM execution role ke saath) DynamoDB tables mein items read/write karta hai.
Q11. Lambda S3 ke saath kaise kaam karta hai?
S3 events (jaise object created) Lambda ko trigger kar sakte hain, taaki wo uploaded file process kare.
Q12. IAM execution role kya hai?
Wo IAM role jise Lambda function chalte samay assume karta hai, jisse use AWS resources access karne ki temporary permissions milti hain.
Q13. Lambda Layer kya hai?
Code/dependencies ka ek reusable package jo multiple Lambda functions mein share hota hai.
Q14. Cold start kya hai?
Wo delay jab AWS ko function chalane se pehle naya execution environment initialize karna padta hai.
Q15. Concurrency kya hai?
Ek saath chal rahi Lambda invocations ki sankhya.
Q16. Reserved concurrency kya hai?
Kisi specific function ke liye set kiya gaya concurrency limit/reservation.
Q17. Provisioned concurrency kya hai?
Pehle se initialize aur ready rakhe gaye execution environments, jo cold starts kam karne ke liye garam rakhe jate hain.
Q18. Lambda timeout kya hai?
Wo maximum time jitna ek invocation chal sakta hai, uske baad wo ruk jata hai.
Q19. Kya Lambda RDS access kar sakta hai?
Haan, aksar Lambda ko sahi VPC/subnets ke andar sahi security group rules ke saath chalakar, ideally connection pooling ya RDS Proxy ke saath.
Q20. Lambda Function URL kya hai?
Ek built-in HTTPS endpoint jo seedha ek Lambda function se juda hota hai, API Gateway setup karne se simpler.
Q21. Lambda vs EC2?
EC2 ek continuously chalne wala server hai jise hum manage karte hain; Lambda code sirf invoke hone par chalata hai aur AWS infrastructure manage karta hai.
Q22. Lambda vs ECS?
ECS containers chalata hai jo aap zyada directly manage karte ho (aksar lambe chalne wali services); Lambda kam operational overhead ke saath short, event-driven functions chalata hai.
Q23. Lambda ko kaise monitor karte hain?
CloudWatch metrics (invocations, errors, duration, throttles) aur CloudWatch Logs use karke.
Q24. Lambda ke logs kahan store hote hain?
Amazon CloudWatch Logs mein.
Q25. Lambda ko kaise secure karte hain?
Least-privilege IAM roles, hard-coded credentials nahi, secrets ke liye Secrets Manager, sahi VPC/security groups, aur zarurat par API authentication.
Q26. Secrets kahan store karte hain?
AWS Secrets Manager (ya isi jaisi secret-management service) use karke, plain code ya bahut sensitive values ke liye plain environment variables ke bajay.
Q27. Lambda ko S3 se kaise trigger karte hain?
S3 event notification (jaise object created) ko function invoke karne ke liye configure karke.
Q28. Lambda ko DynamoDB Streams se kaise trigger karte hain?
Table par stream enable karke aur stream se Lambda function tak ek event source mapping banakar.
Q29. Lambda kaise scale hota hai?
Invocation demand badhne par AWS automatically extra execution environments banata hai, service/account limits ke andar.
Q30. Kya Lambda hamesha free hai?
Nahi. Pricing requests, duration aur resources par depend karti hai; Free Tier terms aur limits badal sakti hain, isliye current AWS pricing check karo.
