1. AWS DynamoDB Introduction

AWS DynamoDB = Amazon DynamoDB

Aasaan definition DynamoDB AWS ka fully managed NoSQL database service hai. Isme hume database server install ya manage karne ki zarurat nahi hoti. AWS infrastructure ko manage karta hai aur hum mainly apne data aur application par focus karte hain.

Ye service fast aur predictable performance deti hai, aur traffic badhne par aasaani se scale ho jati hai.

DynamoDB kya hai?

Ek database service jahan hum data ko items ke roop mein tables ke andar store karte hain, aur AWS APIs ke through read/write karte hain. Koi database server banana ya chalana nahi padta.

NoSQL kya hai?

NoSQL databases mein data mainly SQL ki traditional relational tables (fixed rows-columns) ki tarah store nahi hota. Details section 4 mein hain.

“Fully managed” ka matlab kya hai?

Server, hardware, software patching, data ki replication aur infrastructure scaling AWS sambhalta hai. Hum apna data model, access patterns, permissions, security aur cost sambhalte hain.

Hum DynamoDB kyun use karte hain?

  • Key se lookup mein fast aur predictable performance.
  • Koi server install ya patch nahi karna.
  • Zyada traffic tak scale ho jata hai.
  • Flexible schema (alag items mein alag attributes ho sakte hain).
  • AWS services (IAM, Lambda, CloudWatch) ke saath achha integration.

DynamoDB kahan useful hai?

  • User profiles, shopping cart, orders history
  • Session data aur temporary data (TTL ke saath)
  • Gaming leaderboards / player data
  • IoT aur event data
  • Serverless applications (API Gateway + Lambda + DynamoDB)

Jahan data ko key se fast access karna ho (jaise userId se profile) aur traffic zyada ho sakta ho, wahan DynamoDB achha lagta hai.

2. DynamoDB vs RDS

DynamoDB: NoSQL, key-value/document database, serverless/fully managed experience, bahut fast access, automatic scaling options, flexible schema.

RDS: relational database, SQL, tables/rows/columns, MySQL/PostgreSQL/etc., relationships, SQL queries.

FeatureDynamoDBRDS
Database typeNoSQL (key-value / document)Relational (SQL)
Query styleAPI calls: GetItem, PutItem, Query, Scan (PartiQL bhi available hai)SQL queries (SELECT, JOIN, ...)
SchemaFlexible; sirf primary key fixed hoti haiHar table ke fixed columns
ScalingHorizontal scaling ke liye designed; on-demand aur provisioned optionsBada instance (vertical), storage growth, read replicas
RelationshipsJOIN nahi hota; data ko access patterns ke hisaab se design karte hainForeign keys aur JOINs
ConnectionAWS SDK/CLI, HTTPS aur IAM permissionsEndpoint + port (jaise 3306) + DB username/password
Typical use casesCart, sessions, profiles, IoT, serverless appsFinancial data, reporting, jahan joins aur complex SQL chahiye
Simple Hinglish mein DynamoDB mein SQL tables aur JOIN nahi hote; data key ke through access hota hai aur design access patterns ke hisaab se hota hai. RDS mein SQL, tables, rows, columns aur relationships hote hain. Dono alag problems ke liye bane hain, isliye koi ek doosre se universally better nahi hai.

4. NoSQL Kya Hai?

Definition NoSQL databases wo databases hain jo mainly SQL databases ki traditional relational table structure use nahi karte.

(“NoSQL” ko aksar “Not only SQL” bhi kehte hain.) DynamoDB key-value data aur document data support karta hai.

{
  "userId": "U101",
  "name": "Tarun",
  "age": 24,
  "skills": ["React", "Node.js", "AWS"]
}

NoSQL kyun useful ho sakta hai

  • Flexible data structure: items mein alag attributes, lists, nested maps ho sakte hain.
  • High scalability: data aur traffic ko kai machines mein baantne ke liye bana hai.
  • Fast access: key se tez lookup.
  • Large-scale applications: jab data aur traffic bahut zyada ho.

Iska matlab ye nahi ki har project ke liye NoSQL hi best hai; project ki zarurat dekhkar choose karo.

6. Primary Key, Partition Key aur Sort Key

Har DynamoDB table ke liye primary key zaroori hai. Ye har item ko unique identify karti hai. Iske do types hain:

  1. Simple primary key = sirf Partition key
  2. Composite primary key = Partition key + Sort key

Partition key

Partition key main key hoti hai jisse items identify hote hain aur internally distribute hote hain. Example: userId = U101.

Yaad rakho Partition key DynamoDB ko batata hai ki item ko kaise identify aur internally distribute karna hai.
Table: Users — Partition Key: userId
U101Tarun
U102Rahul
U103Riya

Composite primary key aur Sort key

Sort key Sort key composite primary key ka doosra hissa hai, jo related items ko organize karne aur ek saath query karne mein help karta hai.

Partition key = userId, Sort key = orderId. Dono ka combination unique hona chahiye.

Table: UsersOrders
userId (PK)orderId (SK)productprice
U101O1001Laptop50000
U101O1002Mouse1000
U102O1003Keyboard2000

Ye useful kyun hai? Same partition key wale items ek saath store hote hain aur sort key ke hisaab se arranged rehte hain. Isliye DynamoDB “U101 ke saare orders” ko Query se efficiently nikal leta hai, poori table check kiye bina.

Partition key se DynamoDB pata kar leta hai ki user ka data kahan hai. Sort key se us user ke orders ek order mein rehte hain.

9. CRUD Operations

LetterMatlabDynamoDB operationSimple Hinglish
CCreatePutItemNaya item likhna/create karna
RReadGetItemKey se item padhna
UUpdateUpdateItemItem ke attributes badalna
DDeleteDeleteItemItem delete karna

PutItem (create)

PutItem item create/write karta hai. Agar same primary key wala item pehle se ho, to wo replace ho jata hai (jab tak aap condition na lagao).

aws dynamodb put-item \
  --table-name Users \
  --item '{
    "userId": {"S": "U101"},
    "name": {"S": "Tarun"},
    "email": {"S": "tarun@example.com"}
  }'

S = String. (Aur common types: N = Number, BOOL = Boolean, L = List, M = Map.)

CLI ka JSON alag kyun hai? DynamoDB ka low-level API attribute types ko explicitly likhwata hai ({"S": "Tarun"}), isliye CLI syntax normal JSON se alag dikhta hai. Code mein Document Client use karoge to normal JSON jaisa "name": "Tarun" likh sakte ho (section 15).

GetItem (read)

aws dynamodb get-item \
  --table-name Users \
  --key '{
    "userId": {"S": "U101"}
  }'
  • --table-name Users — kaunsi table.
  • --key — jis item ko chahiye uski poori primary key (yahan sirf userId).

GetItem ko exact primary key chahiye; ye ek hi item wapas deta hai aur bahut fast hota hai.

UpdateItem

aws dynamodb update-item \
  --table-name Users \
  --key '{"userId":{"S":"U101"}}' \
  --update-expression "SET #n = :name" \
  --expression-attribute-names '{"#n":"name"}' \
  --expression-attribute-values '{":name":{"S":"Tarun Rajput"}}'
  • update-expression — kya badalna hai: SET #n = :name ka matlab “attribute #n ko value :name par set karo”.
  • expression-attribute-names — attribute ke naam ka nickname. #n ka matlab name. Ye isliye chahiye kyunki name DynamoDB ka reserved word hai.
  • expression-attribute-values — asli value. :name ka matlab "Tarun Rajput".

# se shuru hone wale placeholders attribute ke naam ke liye hote hain, aur : se shuru hone wale value ke liye. Isse reserved words ki problem nahi aati.

DeleteItem

aws dynamodb delete-item \
  --table-name Users \
  --key '{
    "userId": {"S": "U101"}
  }'

Ye us primary key wala item hata deta hai. Delete se pehle sure ho lo, warna baad mein backup/PITR se hi recover hoga.

10. Query vs Scan

QueryScan
Kaise kaam karta haiKey conditions use karta hai (partition key, optionally sort key)Poori table/index ke items examine karta hai
EfficiencyTargeted access ke liye generally zyada efficientZyada resources use kar sakta hai, khaaskar badi tables par
ExampleUser U101 ke saare orders nikaloPoori table check karo aur age = 24 wale users dhundo
Applications meinNormal access patterns ke liye preferredBadi scale wale application access patterns ke liye usually preferred nahi
# Query: user U101 ke saare orders (table: userId + orderId)
aws dynamodb query \
  --table-name UsersOrders \
  --key-condition-expression "userId = :u" \
  --expression-attribute-values '{":u":{"S":"U101"}}'
Hinglish mein Query = seedha us partition key wale items nikalna (jaise “U101 ke saare orders”). Scan = poori table check karna (jaise “kis user ki age 24 hai?”). Scan chhoti tables ya kabhi-kabhi ke admin kaam ke liye theek hai, lekin badi tables par baar baar Scan chalane se cost aur time dono badhte hain. Isliye Query ke hisaab se table design karo.

Note: Scan par lagaya gaya filter (jaise age = 24) items read hone ke baad apply hota hai, isliye jitne items examine hue unka read cost lagta hai.

11. DynamoDB Indexes (GSI aur LSI)

Index primary key ke alawa item dhundne ka ek aur tareeka deta hai. Simple bhasha mein: index ek extra “rasta” hai jisse hum kisi aur attribute se bhi efficiently search kar sakte hain.

GSI (Global Secondary Index)LSI (Local Secondary Index)
Partition keyBase table se alag ho sakti haiBase table jaisi hi
Sort keyAlag ho sakti hai (optional)Alag sort key
UseAlternative access patternsSame partition key ke andar alag sort order
Kab banate hainBaad mein bhi add kar sakte hainTable banate time hi banana padta hai

Simple example (LSI): UsersOrders table mein userId + orderId hai. orderDate sort key wala LSI lagane se ek user ke orders date ke hisaab se sorted mil sakte hain.

Real project mein GSI

Users table: partition key = userId. Maan lo hume user ko email se bhi dhundna hai (login ke liye).

Base table Users Primary key : userId GSI email-index GSI partition key : email

Ab userId se lookup table se hoga, aur email se lookup GSI se — do efficient access patterns.

Design tip Indexes application ke actual query patterns ke hisaab se design karo. Har index storage aur write cost badhata hai, isliye bina zarurat index mat banao.

12. Capacity Modes, RCU aur WCU

ModeMatlabSimple Hinglish
On-demandRequest usage ke hisaab se payment; DynamoDB capacity automatically manage karta hai.Jitni requests, utna payment. Capacity planning ki tension nahi.
ProvisionedHum read/write capacity settings batate hain aur capacity planning khud karte hain; scaling options (auto scaling) available hain.Hum khud read/write capacity set karte hain; traffic predictable ho to suitable.

RCU aur WCU

  • RCU = Read Capacity Unit
  • WCU = Write Capacity Unit

Concept simple hai: read operation read capacity use karta hai, aur write operation write capacity use karta hai. Actual consumption item size aur operation ki characteristics par depend karta hai (jaise consistency type, ya Query hai ya Scan). Bade items aur bade scans zyada capacity use karte hain.

Exact calculation ke liye AWS ka current documentation dekho; beginner ke liye concept samajhna kaafi hai.

13. DynamoDB Scaling aur Serverless Concept

DynamoDB horizontal scalability ke liye designed hai:

  • Bahut zyada traffic handle kar sakta hai
  • Infrastructure automatically manage karta hai
  • Scaling options support karta hai (on-demand, ya provisioned + auto scaling)
  • Achhe design ke saath bahut high request volumes handle kar sakta hai
Hinglish Traffic badhne par DynamoDB ko traditional server ki tarah manually CPU/RAM increase karne ki zarurat nahi hoti. DynamoDB service scaling ko manage karne ke liye designed hai.

15. DynamoDB Document Client (Aasaan Tareeka)

npm install @aws-sdk/client-dynamodb @aws-sdk/lib-dynamodb
const { DynamoDBClient } = require("@aws-sdk/client-dynamodb");
const {
  DynamoDBDocumentClient,
  PutCommand,
  GetCommand
} = require("@aws-sdk/lib-dynamodb");

const client = new DynamoDBClient({ region: process.env.AWS_REGION });
const docClient = DynamoDBDocumentClient.from(client);

async function demo() {
  // Create / write
  await docClient.send(new PutCommand({
    TableName: "Users",
    Item: { userId: "U101", name: "Tarun", age: 24 }
  }));

  // Read
  const result = await docClient.send(new GetCommand({
    TableName: "Users",
    Key: { userId: "U101" }
  }));

  console.log(result.Item);
}

demo();
Document Client aasaan kyun hai Document Client mein hum normal JavaScript values ("Tarun", 24) use karte hain, DynamoDB attribute types ({ S: "Tarun" }, { N: "24" }) manually likhne ki zarurat nahi padti. Zyada tar Node.js projects mein ye kaam aasaan bana deta hai.

16. Node.js + Express + DynamoDB API

React | v Express API | v DynamoDB
MethodRouteDynamoDB operation
POST/api/usersPutCommand
GET/api/users/:idGetCommand
PUT/api/users/:idUpdateCommand
DELETE/api/users/:idDeleteCommand
const express = require("express");
const { randomUUID } = require("crypto");
const { DynamoDBClient } = require("@aws-sdk/client-dynamodb");
const {
  DynamoDBDocumentClient, PutCommand, GetCommand, UpdateCommand, DeleteCommand
} = require("@aws-sdk/lib-dynamodb");

const app = express();
app.use(express.json());

const docClient = DynamoDBDocumentClient.from(
  new DynamoDBClient({ region: process.env.AWS_REGION })
);
const TABLE = "Users";

// POST /api/users
app.post("/api/users", async (req, res) => {
  const { name, email } = req.body;
  if (!name || !email) {
    return res.status(400).json({ error: "name and email are required" });
  }
  const user = { userId: randomUUID(), name, email };
  await docClient.send(new PutCommand({ TableName: TABLE, Item: user }));
  res.status(201).json(user);
});

// GET /api/users/:id
app.get("/api/users/:id", async (req, res) => {
  const out = await docClient.send(new GetCommand({
    TableName: TABLE, Key: { userId: req.params.id }
  }));
  if (!out.Item) return res.status(404).json({ error: "Not found" });
  res.json(out.Item);
});

// PUT /api/users/:id  (name update)
app.put("/api/users/:id", async (req, res) => {
  const out = await docClient.send(new UpdateCommand({
    TableName: TABLE,
    Key: { userId: req.params.id },
    UpdateExpression: "SET #n = :name",
    ExpressionAttributeNames: { "#n": "name" },
    ExpressionAttributeValues: { ":name": req.body.name },
    ReturnValues: "ALL_NEW"
  }));
  res.json(out.Attributes);
});

// DELETE /api/users/:id
app.delete("/api/users/:id", async (req, res) => {
  await docClient.send(new DeleteCommand({
    TableName: TABLE, Key: { userId: req.params.id }
  }));
  res.status(204).end();
});

app.listen(3000, () => console.log("API running on port 3000"));

Ye code learning ke liye simplified hai: real apps mein try/catch error handling, authentication aur zyada strict validation bhi chahiye. Ye update agar id exist na kare to item create kar dega; use rokna ho to condition expression add karo.

POST /api/users par kya hota hai?

Request body:
{
  "name": "Tarun",
  "email": "tarun@example.com"
}
  1. Backend request ko validate karta hai (name aur email hain ya nahi).
  2. Backend ek unique userId generate karta hai.
  3. Backend item ko DynamoDB mein write karta hai (PutCommand).
  4. Backend created user ke saath response bhejta hai.

EC2 | v IAM Role (instance se attached) | v DynamoDB permissions

dynamodb:GetItem

dynamodb:UpdateItem

Policy ka example idea (sirf ek table tak limited; region, account aur table name apne hisaab se badlo):

{

  "Statement": [{
    "Effect": "Allow",
    "Action": [

19. Kya DynamoDB Ko Port 3306 Chahiye?

NAHI. DynamoDB MySQL nahi hai. Normal DynamoDB API access ke liye Security Group mein koi MySQL-style port 3306 kholne ki zarurat nahi hoti. Application normally AWS service APIs ke through HTTPS par DynamoDB se baat karti hai.
RDS MySQLDynamoDB
Port = 3306AWS API over HTTPS
DB username/password se connectAWS credentials / IAM role se connect
Network access Security Group se controlAccess IAM policies se control
Hinglish mein RDS MySQL mein hum 3306 port aur security group rule use karte hain. DynamoDB mein aisa nahi hota: app AWS SDK ke through HTTPS API call karti hai, aur permission IAM se control hoti hai. Isliye DynamoDB ke liye 3306 kholne ki koi zarurat nahi.

20. AWS Ke Bahar Se Access, Windows aur Endpoint

DynamoDB ek AWS managed service hai jo AWS APIs ke through access hoti hai. Developer ka local computer ye use kar sakta hai:

  • AWS CLI
  • AWS SDK
  • AWS Console

Authentication/authorization AWS credentials (ya koi aur appropriate identity mechanism) se hoti hai, aur access IAM permissions par depend karta hai.

aws dynamodb list-tables --region eu-north-1

aws dynamodb scan --table-name Users --region eu-north-1

Scan sirf chhoti learning tables par chalao. Public RDS database ki tarah aap DynamoDB ko port 3306 kholkar internet par expose nahi karte.

Local Windows se access

  1. AWS CLI install karo, phir check karo: 
    aws --version
  2. Credentials configure karo: 
    aws configure
    Ye daalo: Access Key ID, Secret Access Key, Default region (jaise eu-north-1) aur Output format (jaise json).
  3. Test karo: 
    aws dynamodb list-tables --region eu-north-1
Keys ko sambhal kar rakho Long-term access keys ko dhyan se handle karo aur kabhi GitHub par commit mat karo. Least-privilege IAM users/roles use karo, aur jo keys ab kaam ki nahi unhe rotate ya delete kar do.

DynamoDB endpoint

DynamoDB RDS ki tarah kaam nahi karta, jahan aapko apne instance ka ek alag hostname (endpoint) milta hai. Iske bajay AWS SDK/CLI aapke chune hue region (jaise eu-north-1) ka AWS regional DynamoDB service endpoint use karta hai, aur ye automatically hota hai. Har table ka alag endpoint nahi hota.

RDS : Application -> RDS endpoint (host:3306) -> Database DynamoDB : Application -> AWS SDK / API (region) -> DynamoDB

RDS mein hum ek alag endpoint (hostname) se connect karte hain. DynamoDB mein bas region choose karte hain; SDK khud sahi regional service endpoint use kar leta hai.

21. DynamoDB Security

  • IAM: AWS mein kaun kya kar sakta hai ye control karta hai.
  • IAM Policies: JSON rules jo resources par actions allow/deny karte hain (jaise Users table par dynamodb:GetItem).
  • IAM Roles: EC2, Lambda jaise resources ke liye temporary permissions, bina long-term keys ke.
  • Encryption: encryption at rest AWS by default manage karta hai, aur customer-managed KMS keys ka option bhi hai. Data in transit HTTPS se safe rehta hai.
  • Least privilege: sirf zaroori actions aur sirf zaroori tables.
  • AWS credentials: secret rakho, hard-code mat karo, roles prefer karo.
  • CloudTrail: API activity record karta hai, taaki audit ho sake ki kisne kya kiya.
  • VPC endpoints (jahan appropriate ho): VPC ke andar ke resources ko DynamoDB tak public internet se guzre bina private access dete hain.

DynamoDB ki security mostly IAM se hoti hai: kaun access kar sakta hai aur kaunse actions kar sakta hai. Encryption default hota hai, aur CloudTrail se audit hota hai.

22. DynamoDB Backup

  • Point-in-time recovery (PITR): enable ho to recovery window ke andar kisi bhi chune hue time par table restore kar sakte hain.
  • On-demand backups: hum khud kisi moment par manually backup lete hain.
  • Restore: backup ya PITR point se hamesha nayi table banta hai.

Example: agar important data galti se delete ho jaye, to configured recovery options ke hisaab se backup/recovery features data wapas laane mein help kar sakte hain (jaise PITR pehle se enable hona chahiye).

23. DynamoDB TTL (Time To Live)

TTL = Time To Live. TTL ki help se items expiration time ke baad automatically remove ho jate hain.

{
  "otp": "123456",
  "expiresAt": 1750000000   // Unix time, seconds mein
}

Aap ek attribute (yahan expiresAt) ko TTL attribute chunte ho, jisme Unix epoch time (seconds mein) hota hai. Us time ke baad DynamoDB item ko background mein delete kar deta hai.

Kahan useful: OTP, temporary sessions, temporary cache-jaisa data, expiring records.

Note TTL deletion background process hai aur expiry ke exact second par hone ki guarantee nahi hoti. Agar app ko expired data kabhi use nahi karna, to code mein bhi expiry time check karo.

24. DynamoDB Streams

DynamoDB Streams items mein hone wale changes (create, update, delete) ko order mein capture karta hai.

User updated | v DynamoDB | v DynamoDB Stream | v Lambda | v Notification bhejo / event process karo

Jab table mein koi item add/update/delete hota hai, Stream us change ka record rakhta hai. Lambda us record ko padhkar kaam kar sakta hai, jaise notification bhejna ya kisi aur system ko update karna.

25. DynamoDB + Lambda (Serverless Architecture)

React | v API Gateway | v Lambda | v DynamoDB

Ise serverless architecture kehte hain kyunki hum koi server manage nahi karte: API Gateway HTTP handle karta hai, Lambda code on demand chalata hai, aur DynamoDB data store karta hai.

EC2 version se compare karo:

Serverless mein hum server manage nahi karte, sirf code aur data model dekhte hain. EC2 mein server hamara hota hai, isliye updates aur scaling hume dekhni padti hai.

28. Real E-commerce Example aur Design Thinking

Table: Orders • Partition key: userId • Sort key: orderId

userId (PK)orderId (SK)productpricestatus
U101O1001Laptop50000Delivered
U101O1002Mouse1000Shipped

U101 ke saare orders chahiye to partition key U101 par Query chalao.

aws dynamodb query \
  --table-name Orders \
  --key-condition-expression "userId = :u" \
  --expression-attribute-values '{":u":{"S":"U101"}}'

Ye efficient kyun hai? Same partition key wale saare items ek saath store hote hain, isliye DynamoDB seedha us user ke items tak jata hai, poori table nahi padhta.

DynamoDB tables access patterns ke hisaab se design karo

Traditional SQL mein developers aksar pehle normalized tables design karte hain. DynamoDB mein pehle ye poochho: “Meri application ko kaunse queries chahiye?”

Requirement: “Ek user ke saare orders nikalo.” Design: Partition key = userId, Sort key = orderId.

Hinglish mein SQL mein hum pehle tables design karte hain, phir queries likhte hain. DynamoDB mein ulta hota hai: pehle sochte hain ki app ko kaunse queries chahiye (access patterns), phir unke hisaab se partition key aur sort key choose karte hain.

29. Common DynamoDB Mistakes

  1. Har cheez ke liye Scan use karna — badi tables par slow aur costly; achhi keys ke saath Query prefer karo.
  2. Poor partition key design — jaise aisi key jahan zyadatar requests ek hi value par aayein (“hot” partition).
  3. Zyada IAM permissions dena — least privilege use karo; AdministratorAccess avoid karo.
  4. AWS credentials hard-code karna — roles / credential configuration use karo.
  5. Item size ignore karna — bade items zyada cost karte hain aur item size ki limit bhi hoti hai.
  6. Unnecessary indexes banana — har index cost badhata hai.
  7. Access patterns ke baare mein na sochna — design queries se shuru hota hai.
  8. Cost ignore karna — pricing, capacity mode, backups, streams check karo.
  9. DynamoDB ko relational SQL database ki tarah use karna — isme joins nahi hote; design alag tarah se karna padta hai.
  10. High-traffic access patterns ka plan na karna — key distribution aur capacity ke baare mein pehle se socho.

Sabse badi galti: DynamoDB ko MySQL ki tarah use karna. Access patterns pehle socho, Scan kam use karo, aur permissions tight rakho.

30. Cost, Monitoring aur Throttling

Cost

DynamoDB ki pricing in cheezon par depend kar sakti hai:

  • Read/write usage
  • Storage
  • On-demand ya provisioned capacity
  • Backups
  • Streams
  • Aur enabled features (indexes, global tables, etc.)
Cost warning DynamoDB hamesha free nahi hota. AWS Free Tier ki availability aur limits badal sakti hain, isliye current AWS pricing aur Free Tier terms verify karo, aur billing dashboard par nazar rakho.

Monitoring

Amazon CloudWatch DynamoDB ko monitor kar sakta hai. Common metrics:

MetricSimple matlab
Read capacity (consumed)Aapki app kitni read capacity use kar rahi hai.
Write capacity (consumed)Aapki app kitni write capacity use kar rahi hai.
Throttled requestsWo requests jo capacity exceed hone ki wajah se reject/delay hui.
Successful request latencySuccessful requests ko kitna time lagta hai.
Consumed capacityTotal capacity usage; cost aur limits plan karne mein help karta hai.

Throttling

Definition Throttling tab hoti hai jab requests relevant operation/partition ki available capacity se zyada ho jati hain.

Application design, capacity mode, partition-key distribution aur traffic patterns sab matter karte hain. Achhi key requests ko evenly failati hai; “hot” key total traffic kam dikhne par bhi throttling kara sakti hai. SDKs throttled requests ko automatically retry karte hain, lekin baar baar throttling ho to design ya capacity settings review karo.

31. DynamoDB Interview Questions & Answers

Q1. DynamoDB kya hai?
AWS ka fully managed NoSQL database service, jo fast aur predictable performance deta hai aur aasaani se scale hota hai.
Q2. DynamoDB SQL hai ya NoSQL?
NoSQL (key-value aur document). Ye relational database nahi hai.
Q3. DynamoDB table kya hai?
Items ka collection.
Q4. Item kya hai?
Table ka ek record, SQL ki row jaisa.
Q5. Attribute kya hai?
Item ke andar ka ek field, SQL ke column value jaisa.
Q6. Partition key kya hai?
Main key jo items ko identify aur internally distribute karti hai, jaise userId.
Q7. Sort key kya hai?
Composite key ka doosra hissa; same partition key ke andar items ko organize karti hai taaki unhe ek saath query kar sakein.
Q8. Composite primary key kya hai?
Partition key + sort key, jaise userId + orderId. Dono ka combination unique hona chahiye.
Q9. Query aur Scan mein kya difference hai?
Query key conditions use karta hai aur targeted access ke liye generally efficient hai. Scan poori table/index ke items examine karta hai aur badi tables par costly ho sakta hai.
Q10. GSI kya hai?
Global Secondary Index: alag partition key (aur optional sort key) wala index, alternative access patterns ke liye; baad mein add kar sakte hain.
Q11. LSI kya hai?
Local Secondary Index: table jaisi hi partition key lekin alag sort key; table banate time hi banana padta hai.
Q12. DynamoDB TTL kya hai?
Time To Live: TTL attribute (Unix seconds) mein diye expiry time ke baad items automatically remove ho jate hain.
Q13. DynamoDB Streams kya hai?
Ek feature jo item changes capture karta hai, taaki Lambda jaisi services un par react kar sakein.
Q14. RCU kya hai?
Read Capacity Unit: kitni read capacity use hui ye measure karta hai; item size aur read type par depend karta hai.
Q15. WCU kya hai?
Write Capacity Unit: kitni write capacity use hui ye measure karta hai; item size par depend karta hai.
Q16. On-demand capacity kya hai?
Per request payment; DynamoDB capacity automatically manage karta hai.
Q17. Provisioned capacity kya hai?
Hum read/write capacity set aur plan karte hain, auto scaling options ke saath.
Q18. EC2 DynamoDB ko kaise access karta hai?
App AWS SDK se HTTPS par baat karti hai, aur permission EC2 instance se attached IAM role se milti hai.
Q19. Kya DynamoDB ko port 3306 chahiye?
Nahi. Wo MySQL ka port hai. DynamoDB AWS APIs ke through HTTPS par access hota hai.
Q20. Local computer DynamoDB ko kaise access kar sakta hai?
AWS CLI, SDK ya Console se, aise AWS credentials ke saath jinke paas IAM permission ho.
Q21. DynamoDB aur RDS mein kya difference hai?
DynamoDB NoSQL hai, key-based, JOIN nahi, API aur IAM se access. RDS relational SQL hai, tables, joins, endpoint aur port ke saath.
Q22. DynamoDB aur MongoDB mein kya difference hai?
DynamoDB AWS-managed key-value/document service hai jo IAM se integrated hai; MongoDB apne ecosystem wala document database hai (Atlas uska managed service hai). Dono alag products hain aur dono ki apni strengths hain.
Q23. DynamoDB ko secure kaise karte hain?
IAM least-privilege policies aur roles, hard-coded credentials nahi, encryption (default, optionally KMS), CloudTrail auditing, aur jahan appropriate ho VPC endpoints.
Q24. Node.js ko DynamoDB se kaise connect karte hain?
AWS SDK v3 install karo (@aws-sdk/client-dynamodb, ya Document Client ke liye lib-dynamodb), region ke saath client banao, aur PutCommand/GetCommand jaisi commands send karo.
Q25. EC2 par hard-coded AWS credentials ke bajay IAM roles kyun?
Roles temporary, automatically rotate hone wale credentials dete hain, isliye server ya code mein long-term keys nahi rehti, aur permissions limited rakh sakte hain.
