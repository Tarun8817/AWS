THEORY 1. INTRODUCTION — What is Amazon ECS?

"Amazon ECS (Elastic Container Service) is a fully managed AWS container orchestration service used to run, manage, deploy, and scale Docker containers in the cloud."

If you already know how to build a Docker container on your laptop, ECS is the cloud platform that takes that container and runs it across multiple servers with automated health checks, self-healing restarts, zero-downtime deployments, and load balancing.

The Problem of Running Docker Manually vs Amazon ECS:

WITHOUT ECS (Manual Docker on EC2): Developer ──► SSH into EC2 ──► docker run ──► Container crashes at 2 AM? ❌ DOWN! Traffic increases 10x? ❌ SERVER CRASHES! Deploy new version? ❌ MANUAL RESTART & DOWNTIME! WITH AMAZON ECS: Docker Image ──► Amazon ECS ──► Auto-Starts Tasks ──► Container crashes? ✅ Auto-heals in seconds! Traffic spikes? ✅ Auto-scales to 10 tasks! Deploy new code? ✅ Zero-downtime rolling update!

THEORY 2. What is Container Orchestration?

When you have 1 container running locally, managing it is easy: docker run and docker stop. But what happens when your production application needs 10, 50, or 100 containers?

How ECS Solves Container Management at Scale:

  • Automatic Starting & Stopping: ECS places containers on optimal infrastructure based on CPU and memory needs.
  • Self-Healing (Auto-Restart): If an application crashes or runs out of memory, ECS immediately kills the bad container and spins up a healthy replacement.
  • Load Balancing: Distributes user traffic evenly across all running container instances.
  • Auto Scaling: Adds more containers during peak traffic hours and terminates them when traffic subsides to save money.
  • Zero-Downtime Rolling Deployments: Gradually swaps old containers with new container versions without dropping user connections.

THEORY 4. 24 IMPORTANT ECS TERMS (Master Dictionary)

Term What it is Why it is used Practical Example
1. ECS Elastic Container Service — AWS managed orchestration platform. Run and scale Docker apps without managing cluster master nodes. Running a microservices fleet on AWS.
2. Cluster A logical grouping of tasks or services. Isolates workloads (e.g. dev cluster vs prod cluster). production-cluster
3. Task Definition The blueprint specifying container configurations. Tells ECS what image, CPU, memory, and ports to run. Blueprint for Node.js API container.
4. Task A running container instance instantiated from a Task Definition. The actual compute process running your code. 1 active task handling web traffic.
5. Service Long-running supervisor that maintains task counts. Ensures high availability and connects tasks to Load Balancers. Keeping exactly 3 backend API tasks running.
6. Desired Count The target number of simultaneous tasks to maintain. Defines application capacity. Setting desired count = 4 during sale events.
7. ECR Elastic Container Registry — AWS private Docker image repository. Securely stores and scans Docker images inside AWS. Pushing my-node-app:latest to ECR.
8. AWS Fargate Serverless compute engine for containers. Runs containers without managing underlying EC2 virtual servers. Zero EC2 maintenance container hosting.
9. EC2 Launch Type Running ECS containers on EC2 virtual machines you manage. Maximum control over OS, GPU hardware, and custom networking. Machine learning workloads on GPU EC2s.
10. Execution Role IAM role used by the ECS agent / Fargate infrastructure. Pulls images from ECR and writes logs to CloudWatch. ecsTaskExecutionRole
11. Task Role IAM role assigned to your application code inside the container. Allows container code to call S3, DynamoDB, or Secrets Manager. Node.js code uploading user images to S3.
12. Launch Type The compute infrastructure type (FARGATE vs EC2). Determines who manages the underlying servers. Selecting Fargate for serverless scaling.
13. Capacity Provider Manages infrastructure scaling for tasks in a cluster. Automates Fargate, Fargate Spot, or EC2 Auto Scaling groups. Running 70% on Fargate Spot for cost savings.
14. Container Port The internal port exposed by the app inside the container. The port your code listens on. Express.js listening on port 3000.
15. Host Port The port on the physical host machine mapped to the container. Routes external traffic to the container. In awsvpc mode, Host Port = Container Port.
16. Port Mapping The bridge connecting Host Port to Container Port. Enables external traffic to reach the container. Mapping port 80 → 3000.
17. Health Check Periodic ping checking if the container responds with HTTP 200. Detects crashed or frozen application containers. ALB checking GET /health every 30s.
18. Load Balancer (ALB) Application Load Balancer distributing HTTP/HTTPS traffic. Single public DNS entry point routing across tasks. Users browsing https://api.mycompany.com.
19. Target Group A logical group of IP targets registered with the ALB. ALB forwards requests to tasks in this target group. Target group containing 3 Fargate IP addresses.
20. Service Discovery AWS Cloud Map private DNS resolution between microservices. Allows frontend containers to call backend.internal. Inter-microservice communication without public IPs.
21. CloudWatch Logs AWS log aggregation service capturing container stdout/stderr. Debugging crashes and viewing runtime console logs. Viewing console.log() statements in CloudWatch.
22. Container Registry Storage service for versioned Docker images. Central hub to pull and push container artifacts. Docker Hub or Amazon ECR.
23. Task Definition Revision Version number of a Task Definition (e.g. :1, :2). Tracks configuration changes and new image releases. Deploying ecs-demo-task:2 with new code.
24. awsvpc Networking ECS network mode assigning an ENI and private IP to every task. Full VPC security group isolation per container. Standard mandatory networking mode for Fargate.

THEORY 5, 6, 7 & 8. ECS COMPARISONS & WHAT IS AWS FARGATE?

5. ECS vs Docker:

Dimension Docker Amazon ECS
Scope Builds and runs individual containers on a single host. Orchestrates hundreds of containers across a cluster in the cloud.
Responsibility Packaging code, dependencies, and runtime. Auto-scaling, self-healing, load balancing, and deployments.

7 & 8. ECS Launch Types: EC2 vs AWS Fargate (Serverless)

Feature ECS on EC2 ECS Fargate (Serverless)
Server Management You manage OS updates, Docker daemon, and EC2 scaling. Zero server management (AWS manages underlying VMs).
Pricing Model Pay for EC2 instances running (even if idle). Pay per vCPU and GB memory per second consumed by tasks.
Setup Complexity Moderate to high. Minimal (Beginner friendly & industry standard).
Best Use Case GPU machine learning or custom kernel drivers. Web apps, microservices, APIs, and scheduled batch jobs.

PRACTICAL 11, 12 & 13. PRACTICAL 1, 2 & 3: BUILD & RUN NODE.JS DOCKER APP LOCALLY

Step 1: Create the Node.js Express Application

Create a project folder and create server.js:

JavaScript (server.js)
const express = require("express");
const app = express();
const PORT = process.env.PORT || 3000;

app.get("/", (req, res) => {
  res.send("<h1 style='color: #2451c4; font-family: sans-serif;'>🚀 Hello from Amazon ECS Fargate!</h1><p>Containerized Node.js Microservice is Live!</p>");
});

app.get("/health", (req, res) => {
  res.status(200).json({ status: "healthy", timestamp: new Date() });
});

app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});

Create package.json:

JSON (package.json)
{
  "name": "ecs-demo-app",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": {
    "start": "node server.js"
  },
  "dependencies": {
    "express": "^4.19.2"
  }
}

Create the Dockerfile:

Dockerfile
# 1. Base image with Node.js 20 LTS
FROM node:20-alpine

# 2. Set working directory inside container
WORKDIR /app

# 3. Copy package files first for efficient Docker layer caching
COPY package*.json ./

# 4. Install production dependencies
RUN npm install --only=production

# 5. Copy the remaining application source code
COPY . .

# 6. Expose container listening port
EXPOSE 3000

# 7. Start the application
CMD ["node", "server.js"]

PRACTICAL 14 TO 17. PRACTICAL 4 TO 7: PUSH DOCKER IMAGE TO AMAZON ECR

Step-by-Step ECR Setup & Push

  1. Open AWS Console → Search ECR (Elastic Container Registry).
  2. Click Create repository → Visibility: Private → Repository name: ecs-demo. Click Create repository.
  3. Authenticate your local Docker CLI with Amazon ECR:
    AWS CLI / PowerShell
    # Verify AWS identity
aws sts get-caller-identity

# Login to ECR (Replace YOUR_ACCOUNT_ID and YOUR_REGION)
# Windows PowerShell format:
(Get-ECRLoginCommand).Password | docker login --username AWS --password-stdin YOUR_ACCOUNT_ID.dkr.ecr.YOUR_REGION.amazonaws.com

# Linux/Mac/Git Bash format:
aws ecr get-login-password --region YOUR_REGION | docker login --username AWS --password-stdin YOUR_ACCOUNT_ID.dkr.ecr.YOUR_REGION.amazonaws.com
  4. Tag your local Docker image with the ECR repository URI:
    Terminal
    docker tag ecs-demo:latest YOUR_ACCOUNT_ID.dkr.ecr.YOUR_REGION.amazonaws.com/ecs-demo:latest
  5. Push the image to Amazon ECR:
    Terminal
    docker push YOUR_ACCOUNT_ID.dkr.ecr.YOUR_REGION.amazonaws.com/ecs-demo:latest
  6. In the AWS ECR Console, verify that ecs-demo displays image tag latest.

  3. Infrastructure requirements: Launch type: AWS Fargate.

PRACTICAL 28, 29 & 30. PRACTICAL 13: CONNECT APPLICATION LOAD BALANCER & HEALTH CHECKS

In production, users should never connect directly to individual task IP addresses. We place an Application Load Balancer (ALB) in front of the ECS Service on port 80/443.
Internet Users (Port 80/443) │ ▼ [ Application Load Balancer ] (DNS: my-alb-12345.region.elb.amazonaws.com) │ ▼ [ Target Group (IP type) ] ──► Periodic Health Check: GET /health (HTTP 200) │ ┌───────┴───────┐ ▼ ▼ [ Task 1 (Port 3000) ] [ Task 2 (Port 3000) ]

Step-by-Step ALB Integration:

  1. In EC2 Console → Load Balancers → Click Create load balancer → Application Load Balancer.
  2. Name: ecs-alb, Scheme: Internet-facing, select your VPC and at least 2 public Availability Zones.
  3. Security Group: Create alb-sg allowing Inbound HTTP Port 80 from 0.0.0.0/0.
  4. Create Target Group: Target type: IP addresses • Protocol: HTTP • Port: 3000 • Health check path: /health.
  5. Attach ALB to ECS Service: In ECS Service configuration → Load balancing → select ecs-alb → container port 3000.
  6. Open the ALB DNS Name in your browser: http://ecs-alb-xxxx.amazonaws.com.

THEORY 31 TO 35. AUTO SCALING, ROLLING UPDATES & BLUE/GREEN DEPLOYMENTS

31. ECS Service Auto Scaling:

ECS Service Auto Scaling uses CloudWatch alarms to dynamically adjust the desired task count based on actual load:

  • Target Tracking Scaling: Keep average CPU utilization at 60%. If CPU reaches 80%, ECS automatically launches 2 additional tasks.
  • Scale-In Protection: Gracefully terminates excess tasks when traffic subsides.

33 & 35. Rolling Update vs Blue/Green Deployment:

Strategy How it Works Downtime Rollback Speed
Rolling Deployment (Default) Gradually launches new V2 tasks while slowly terminating old V1 tasks. Zero downtime Moderate (must spin old tasks back up).
Blue/Green (AWS CodeDeploy) Provisions an entire green replacement fleet, verifies health, then shifts ALB traffic instantly. Zero downtime Instant (shift traffic back to Blue fleet).

TROUBLESHOOTING 54 & 55. 20 COMMON ECS ERRORS & HOW TO FIX THEM

Error / Symptom Root Cause How to Fix
1. CannotPullContainerError Wrong ECR image URI or execution role lacks ECR pull permissions. Verify image URI spelling; ensure ecsTaskExecutionRole has AmazonECSTaskExecutionRolePolicy.
2. Task Stops Immediately (Exit Code 1) Application code crashed on startup (missing env var or syntax error). Check CloudWatch log streams under /ecs/<task-family> for the Node.js stack trace.
3. Out of Memory (Exit Code 137) Container exceeded the allocated memory limit (e.g. 512 MB). Increase task memory in Task Definition (e.g. from 512 MB to 1024 MB).
4. Task Stuck in PENDING No available subnets with public IPs or insufficient cluster resources. Verify task is launched in subnets with an active Internet Gateway or NAT Gateway route.
5. ALB Target Unhealthy (HTTP 502/504) Health check path failed or container not listening on expected port. Ensure container listens on port 3000 and GET /health returns HTTP 200.
6. AccessDenied to S3/DynamoDB Task Role missing required IAM permissions. Attach IAM policy to the Task Role (not the Execution Role).
7. Security Group Blocking Traffic ECS task security group does not allow traffic from ALB security group. In ECS Security Group, allow Port 3000 inbound referencing sg-alb as the source.

THEORY 56 & 57. ECS PRICING & PROPER LAB CLEANUP ORDER

💰 Clean Up Lab Resources to Avoid Unwanted AWS Charges:

Always delete training resources in this exact sequential order after completing your exercises:

  1. 1. Update ECS Service: Set Desired Tasks = 0, then delete the ECS Service.
  2. 2. Delete Application Load Balancer: Delete the ALB to stop hourly balancer charges.
  3. 3. Delete Target Group: Remove the associated target group.
  4. 4. Delete ECS Cluster: Delete ecs-demo-cluster.
  5. 5. Delete ECR Repository: Delete ecs-demo repository and its stored images.
  6. 6. Delete CloudWatch Log Group: Delete /ecs/ecs-demo-task.

THEORY 58 & 59. 19 PRODUCTION BEST PRACTICES & SECURITY

  • 1. Use Versioned Image Tags: Avoid deploying :latest in production; use Git commit SHAs (e.g. :v1.2.0-abc1234).
  • 2. Decouple IAM Roles: Use Execution Role for infrastructure setup and Task Role for application-level AWS SDK calls.
  • 3. Secure Secrets: Load database credentials from AWS Secrets Manager directly in the Task Definition.
  • 4. Deploy in Private Subnets: Place Fargate tasks in private subnets behind an internet-facing ALB.
  • 5. Enable CloudWatch Container Insights: Monitor task-level CPU, memory, and network throughput telemetry.
  • 6. Small Multi-Stage Docker Builds: Use lightweight base images (e.g. node:20-alpine) to accelerate image pulls and minimize attack surfaces.

INTERVIEW 60. TOP 40+ AWS ECS INTERVIEW QUESTIONS & ANSWERS

Q1. What is Amazon ECS?

A fully managed AWS container orchestration service used to run, scale, and manage Docker containers securely in the cloud.

Q2. What is AWS Fargate?

A serverless compute engine for containers that allows you to run ECS tasks without provisioning or managing underlying EC2 instances.

Q3. What is an ECS Task Definition?

A JSON blueprint specifying container configuration, image URI, CPU, memory, port mappings, and environment variables.

Q4. What is the difference between a Task and a Service?

A Task is a single running container instance; a Service maintains a specified desired count of tasks, handles replacements, and integrates with Load Balancers.

Q5. What is Amazon ECR?

Elastic Container Registry — a fully managed AWS Docker registry used to securely store, scan, and manage container images.

Q6. Task Execution Role vs Task Role?

Execution Role is used by the ECS agent to pull images from ECR and send logs to CloudWatch. Task Role is used by the application code to call AWS APIs like S3 and DynamoDB.

Q7. What is the default networking mode for Fargate?

awsvpc, which assigns a dedicated Elastic Network Interface (ENI) and private IP address to every task.

Q8. What happens when an ECS Task crashes?

The ECS Service automatically detects the unhealthy state, terminates the bad task, and immediately launches a new task to maintain the desired count.

Q9. What does Exit Code 137 mean in ECS?

Out of Memory (OOM) error. The container exceeded the allocated RAM defined in the Task Definition and was killed by the OS kernel.

Q10. What is Fargate Spot?

Spare AWS compute capacity offered at up to 70% discount for fault-tolerant and interruptible container workloads.
