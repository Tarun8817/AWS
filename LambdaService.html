1. AWS Lambda Introduction

Definition AWS Lambda is a serverless compute service that lets you run code without managing servers.
Hinglish AWS Lambda AWS ki serverless compute service hai. Isme hume server create, maintain, patch ya continuously run karne ki zarurat nahi hoti. Hum apna code Lambda function ke form mein deploy karte hain aur AWS us code ko required time par run karta hai.

What is Lambda?

A service where you upload code (a “function”) and AWS runs it whenever something triggers it — an HTTP request, a file upload, a schedule, etc.

Why do we use Lambda?

  • No server to set up or patch.
  • Automatically scales with demand.
  • Pay mainly for actual usage, not idle time.
  • Fits event-driven and API workloads well.

What does “serverless” mean? Does it mean no servers?

Important Serverless does NOT mean there are no servers. Servers still exist, but AWS manages the underlying infrastructure for us.

Hinglish: Serverless ka matlab servers gayab nahi hue; servers hain, bas unhe AWS manage karta hai, hume nahi.

Who manages the infrastructure? When does Lambda execute?

AWS manages the servers, OS patching and scaling. Your code executes only when the function is invoked (triggered) — not continuously like a server.

2. Simple Real-World Example: Image Upload

User | v S3 | v Lambda | v Process Image | v Save Result
  1. User uploads an image to S3.
  2. S3 generates an event.
  3. Lambda is triggered.
  4. Lambda downloads/reads the image.
  5. Lambda processes the image (e.g. resize).
  6. Lambda stores the result (e.g. back to S3, or metadata to DynamoDB).

Hinglish: User image upload karta hai, S3 event fire karta hai, Lambda automatically chalta hai, image process hoti hai, aur result save ho jata hai — koi server hamesha chalu rakhne ki zarurat nahi.

3. MERN-style Project Example

Frontend: React • Backend logic: Node.js-style code • Database: MongoDB / DynamoDB • Serverless function: AWS Lambda

React | v API Gateway | v AWS Lambda | v DynamoDB | v Response | v React

A MERN developer can use Lambda instead of keeping an Express backend running continuously on an EC2 server. Existing Express applications can be adapted to run inside Lambda (with an adapter library), but Lambda functions are often designed around individual API/event handlers rather than one always-running app.

Hinglish: Normal MERN mein Express server EC2 par hamesha chalta rehta hai. Serverless approach mein har API route ek chhota Lambda function ban sakta hai, jo sirf request aane par chalta hai.

4. EC2 vs Lambda

EC2: you manage a virtual server, it runs continuously, you manage OS/config, you choose instance size, you pay for allocated/running infrastructure.

Lambda: no server management, code runs when invoked, AWS manages infrastructure, execution capacity is handled automatically, pricing follows the current Lambda pricing model based on usage.

FeatureEC2Lambda
Server managementYou manage the OS/serverFully managed by AWS
ScalingYou configure (or use Auto Scaling groups)Handled automatically per invocation demand
ExecutionContinuous processRuns only when invoked
BillingFor running instance time/sizeMainly for requests + duration (see current pricing)
OS managementYour responsibilityNot applicable / managed by AWS
Use casesLong-running apps, custom server needsAPIs, events, automation, scheduled tasks
Max execution durationNo inherent limit (it’s a server)Limited per invocation (check current AWS docs)
DeploymentConfigure/patch server yourselfUpload code/zip/container image
Hinglish EC2 mein server hamesha chalta hai aur hum use manage karte hain. Lambda mein server dikhta nahi, code sirf zarurat par chalta hai aur AWS scaling sambhalta hai. Koi bhi ek doosre se hamesha better nahi hai; use case dekh kar choose karo.

5. What is a Lambda Function?

Definition A Lambda function is a piece of code that AWS runs in response to an event or invocation.

A Lambda function is made up of:

  • Code — your logic
  • Runtime — the language environment (Node.js, Python, etc.)
  • Handler — the entry-point function
  • Configuration — memory, timeout, etc.
  • Permissions — the execution role (IAM)
  • Environment variables — config values
  • Memory — allocated resources
  • Timeout — maximum run time per invocation

6. Supported Runtimes

  • Node.js
  • Python
  • Java
  • .NET
  • Go
  • Ruby
Note AWS Lambda runtime availability (and exact supported versions) changes over time, so check the current AWS-supported runtime list before creating a function.

This note focuses mainly on Node.js, since the learner is a MERN developer.

7. How to Create Your First Lambda Function

  1. Login to the AWS Console.
  2. Search for Lambda.
  3. Open AWS Lambda.
  4. Click Create function.
  5. Select Author from scratch.
  6. Function name: helloLambda
  7. Runtime: Node.js (use whichever Node.js version the Console currently supports).
  8. Architecture: keep the default.
  9. Permissions: AWS can create a basic execution role for you (this gives the function permission to write logs, and more permissions can be added later).
  10. Click Create function.

Hinglish: Console ki screens badal sakti hain, lekin flow same rehta hai: naam do, runtime chuno, aur execution role banne do. Baad mein role mein zaroorat ke hisaab se permissions add kar sakte ho.

8. First Lambda Code

exports.handler = async (event) => {
    return {
        statusCode: 200,
        body: JSON.stringify({
            message: "Hello from AWS Lambda"
        })
    };
};
PartMeaning
exports.handlerExports the function so AWS can find and call it (the entry point).
asyncMarks the function as asynchronous, so you can use await inside it.
eventThe input data describing what triggered this invocation.
returnSends the result back to whoever/whatever invoked the function.
statusCodeThe HTTP-style status code of the response (200 = success).
bodyThe response content, usually sent as a string.
JSON.stringifyConverts a JavaScript object into a JSON string for the response body.

The handler is the function AWS invokes. Hinglish: Jab bhi Lambda trigger hota hai, AWS isi handler function ko call karta hai.

9. Lambda Handler

Handler = entry point of the Lambda function — the exact function AWS calls to start execution. Example: exports.handler.

The handler setting in Lambda configuration follows the format:

filename.functionName

If the file is index.js and the exported function is handler, the handler configuration is:

index.handler

Another example: if the file is app.js and the exported function is handler, the configuration is app.handler.

Hinglish: Handler setting AWS ko batati hai ki kaunsi file ke andar kaunsa function call karna hai. Format hamesha filename.functionName hota hai.

10. Event and Context

exports.handler = async (event, context) => {
    console.log(event);
    console.log(context);

    return {
        statusCode: 200,
        body: "Hello"
    };
};
  • event — contains information about what triggered the Lambda (e.g. the HTTP request body/headers from API Gateway, or details about the S3 file that was uploaded).
  • context — contains information about the Lambda execution environment and this invocation (e.g. how much time is left, request ID, function name).

Hinglish: event mein bataya jata hai ki trigger kis cheez ne kiya aur kya data bheja gaya. context mein invocation aur environment ki jaankari hoti hai, jaise kitna time bacha hai.

13. Lambda + API Gateway

User | v API Gateway | v Lambda | v DynamoDB

API Gateway provides an HTTP/HTTPS API endpoint. Lambda processes the request. DynamoDB stores data.

MethodRoute
GET/users
POST/users
GET/users/{id}
DELETE/users/{id}

Request flow: Client calls the API Gateway URL → API Gateway routes the request to the matching Lambda → Lambda runs its logic (often reading/writing DynamoDB) → Lambda returns a response → API Gateway sends it back to the client.

Hinglish: API Gateway ek entry door hai; wahi request ko sahi Lambda tak pahunchati hai. Lambda kaam karke response deta hai, jo wapas client tak jata hai.

15. Lambda + DynamoDB (Setup)

Lambda | v AWS SDK | v DynamoDB
npm install @aws-sdk/client-dynamodb
npm install @aws-sdk/lib-dynamodb
const {
    DynamoDBClient
} = require("@aws-sdk/client-dynamodb");

const {
    DynamoDBDocumentClient,
    PutCommand
} = require("@aws-sdk/lib-dynamodb");

const client = new DynamoDBClient({
    region: process.env.AWS_REGION
});

const dynamoDB = DynamoDBDocumentClient.from(client);
  • DynamoDBClient — the low-level client that talks to DynamoDB.
  • DynamoDBDocumentClient — a wrapper that lets you use plain JavaScript objects instead of DynamoDB’s typed attribute format.
  • region: process.env.AWS_REGION — which AWS region to use, read from an environment variable.
  • DynamoDBDocumentClient.from(client) — builds the easier-to-use document client on top of the base client.

Hinglish: Lambda mein bhi normal Node.js code jaisa hi AWS SDK use hota hai. Document client se JSON values seedhe use kar sakte hain, DynamoDB type (S/N) likhne ki zarurat nahi.

16. Lambda + DynamoDB CRUD

OperationRoute
CreatePOST /users
ReadGET /users/{id}
UpdatePUT /users/{id}
DeleteDELETE /users/{id}
// Create
exports.createUser = async (event) => {
    const body = JSON.parse(event.body);
    await dynamoDB.send(new PutCommand({
        TableName: "Users",
        Item: { userId: body.userId, name: body.name, email: body.email }
    }));
    return { statusCode: 201, body: JSON.stringify({ message: "Created" }) };
};

// Read
exports.getUser = async (event) => {
    const out = await dynamoDB.send(new GetCommand({
        TableName: "Users", Key: { userId: event.pathParameters.id }
    }));
    return { statusCode: 200, body: JSON.stringify(out.Item) };
};

Update and Delete follow the same pattern using UpdateCommand and DeleteCommand (see the DynamoDB notes for the full syntax). Each Lambda function here handles one route — a common serverless pattern.

Hinglish: Har route ke liye alag chhota function likhna common practice hai. Isse code samajhna aur deploy karna aasaan rehta hai.

20. Lambda + SQS

Producer | v SQS Queue | v Lambda | v Process Message

Example: an order service creates an order → a message goes into SQS → Lambda processes the message.

Why queues are useful:

  • Decoupling (producer and processor don’t need to know about each other directly)
  • Asynchronous processing
  • Handling traffic spikes
  • Retry behavior for failed messages

Hinglish: Queue use karne se producer aur processor alag-alag speed par kaam kar sakte hain, aur traffic spike mein bhi messages safely wait karte hain.

Hinglish: EventBridge ek scheduler ki tarah kaam karta hai; ye rules ke hisaab se (jaise “roz raat 2 baje”) Lambda ko trigger karta hai.

23. IAM Role and Execution Role

Lambda needs permissions to access AWS resources.

Lambda | v IAM Execution Role | v DynamoDB

The execution role tells AWS what the Lambda function is allowed to access.

Example permissions for DynamoDB:

dynamodb:GetItem
dynamodb:PutItem
dynamodb:UpdateItem
dynamodb:DeleteItem

Also, almost every function needs logging permissions:

logs:CreateLogGroup
logs:CreateLogStream
logs:PutLogEvents
Least privilege Give only the actions and resources the function actually needs. Do NOT recommend or attach AdministratorAccess for a production Lambda function.

IAM User vs IAM Role vs Lambda Execution Role

  • IAM User: a long-term identity for a person or application, usually with static credentials.
  • IAM Role: a set of permissions that can be temporarily assumed by a trusted identity or service (no long-term keys).
  • Lambda Execution Role: the specific IAM role a Lambda function assumes when it runs, giving it temporary AWS permissions for that invocation.

Hinglish: Lambda function chalte time apni execution role “assume” karta hai, aur usse temporary permissions milti hain. Hamesha least privilege follow karo.

25. Lambda Layers

Function A | v Layer Function B | v Layer

Hinglish: Agar ek hi library ya utility code kai functions mein chahiye, to use ek Layer mein daal do, taaki har function mein alag se copy na karni pade.

26. Timeout and Memory

Timeout

Every Lambda function has a maximum execution duration (timeout) — the maximum time it is allowed to run for one invocation. If the function takes longer than the configured timeout, the execution stops.

Note Use the current AWS Lambda documentation/console for the exact maximum duration rather than hard-coding an outdated value, since limits can change.

Memory

Memory configuration affects the resources available to the function, including CPU allocation — more memory can also provide more CPU. A small workload may need lower memory; heavy processing may need higher memory. Increasing memory can affect cost, since Lambda pricing is tied to configured resources and execution duration.

Hinglish: Timeout se zyada time lage to Lambda ruk jata hai. Memory jitni zyada, utna CPU bhi mil sakta hai, lekin cost bhi badh sakti hai — workload ke hisaab se balance karo.

27. Cold Start and Concurrency

Cold start

Cold start happens when AWS needs to initialize a new execution environment before running a function. A warm invocation reuses an existing environment (faster); a cold invocation needs a new one (can take slightly longer).

Hinglish: Pehli request thodi slow ho sakti hai (cold start), lekin agar environment reuse ho jaye to baad ki requests fast hoti hain (warm).

Concurrency

Concurrency = number of Lambda invocations being processed at the same time. 1 request → 1 execution; 100 simultaneous requests → potentially many concurrent executions. Lambda can scale concurrent executions according to AWS limits and your account/function configuration.

Reserved concurrency

Reserves/sets a concurrency limit for a specific function. Helps to: control concurrency, protect downstream services (like a database), and prevent one function from consuming all available concurrency in the account.

Provisioned concurrency

Keeps execution environments initialized and ready in advance, to reduce cold-start latency for supported workloads (at extra cost).

Reserved concurrencyProvisioned concurrency
PurposeLimit/guarantee a concurrency ceilingReduce cold starts by pre-warming environments
Effect on costNo extra cost by itselfExtra cost for kept-ready environments
Typical useProtect a downstream DB, cap a noisy functionLatency-sensitive APIs

Hinglish: Reserved concurrency limit lagata hai (kitne max invocations chalein), aur Provisioned concurrency environments ko pehle se garam rakhta hai taaki cold start kam ho.

28. Lambda Scaling and Statelessness

Scaling

Traditional EC2: Traffic -> Manually/automatically add servers Lambda: Traffic -> AWS manages execution environments and concurrency

Lambda can automatically create additional execution environments as invocation demand increases, subject to service/account limits.

Statelessness

Lambda functions should generally be treated as stateless. Do not depend on local execution environment storage for permanent application data. Lambda’s local /tmp storage is temporary and should not be treated as permanent database storage.

For persistent data, use DynamoDB, S3, RDS, or another persistent service.

Hinglish: Lambda ko permanent storage mat samjho; important data hamesha DynamoDB/S3/RDS jaisi persistent service mein save karo.

29. Lambda + Database, VPC, and Function URL

Lambda + Database options

Option 1: Lambda -> DynamoDB Option 2: Lambda -> RDS Option 3: Lambda -> MongoDB Atlas

Relational database connections need careful connection management because Lambda can scale to many concurrent execution environments, each potentially opening its own DB connection. Consider connection pooling and services such as RDS Proxy where appropriate.

Lambda + RDS

API Gateway | v Lambda | v RDS MySQL

If RDS is private, Lambda may need to run inside the appropriate VPC/subnets with the right security configuration.

Lambda Security Group | v RDS Security Group | v TCP 3306
Important Do not expose RDS publicly just because Lambda needs access. Configure networking (VPC/security groups) instead.

Lambda VPC

Lambda can be configured to access resources inside a VPC (like a private RDS instance) by attaching it to specific subnets and security groups.

Important Putting Lambda in a VPC does not automatically give it internet access. Outbound internet access from private subnets may require appropriate networking, such as a NAT Gateway, where needed.

Lambda Function URL

Definition A Lambda Function URL provides an HTTPS endpoint directly associated with a Lambda function.
User | v HTTPS | v Lambda Function URL | v Lambda
API GatewayFunction URL
SetupMore configuration, more featuresSimple, quick setup
RoutingFull routing, multiple methods/resourcesOne URL tied to one function
Auth/authorization optionsRicher options (API keys, authorizers, etc.)Simpler options
Best forFull APIs with many routesA single simple HTTP-triggered function
Note Function URL and API Gateway are not exactly the same, and neither is always better — choose based on how much API functionality you need.

Hinglish: Function URL simple, seedha HTTPS endpoint deta hai. API Gateway zyada features (routing, auth options) deta hai lekin setup thoda zyada hota hai.

30. Logs, Monitoring, Error Handling, Retries, DLQ

Logs

AWS Lambda integrates with Amazon CloudWatch Logs. Anything you console.log(...) is sent there.

console.log("User created");
Lambda | v CloudWatch Logs

To view logs: Open Lambda → open the function → go to Monitor → open CloudWatch logs → open the log group → open a log stream.

Monitoring

MetricSimple meaning
InvocationsHow many times the function was called.
ErrorsHow many invocations resulted in an error.
DurationHow long each invocation takes.
ThrottlesInvocations rejected because concurrency limits were hit.
Concurrent executionsHow many invocations are running at once.
Iterator age (where relevant)For stream-based sources, how far behind processing is.

Error handling

exports.handler = async (event) => {

    try {

        // application logic

        return {
            statusCode: 200,
            body: JSON.stringify({
                message: "Success"
            })
        };

    } catch (error) {

        console.error(error);

        return {
            statusCode: 500,
            body: JSON.stringify({
                message: "Internal Server Error"
            })
        };
    }
};

try runs the normal logic; if anything throws an error, catch handles it gracefully and returns a proper error response instead of crashing unexpectedly.

Retries

Lambda retry behavior depends on the invocation type and event source:

  • Synchronous invocation (e.g. via API Gateway): the caller receives the result/error directly; Lambda itself does not automatically retry.
  • Asynchronous invocation (e.g. via S3, SNS): AWS can retry failed invocations according to Lambda’s asynchronous invocation behavior.
  • Event-source mappings (e.g. SQS, DynamoDB Streams): these services have their own retry/visibility/dead-letter behavior.
Retry behavior is not identical for every trigger — check the specific service’s documentation.

Dead Letter Queue (DLQ)

DLQ = Dead Letter Queue.

Lambda | v Processing fails | v Retry | v Still fails | v DLQ

DLQ support/configuration depends on the invocation type and architecture (for example, asynchronous invocations and certain event sources support DLQ or similar failure-destination configurations).

Hinglish: Agar processing baar baar fail ho, to failed message/event ko DLQ mein bhej diya jata hai taaki wo lost na ho aur baad mein inspect kiya ja sake.

Versioning and Aliases

Versions let you publish immutable snapshots of a function (e.g. Version 1, Version 2, Version 3) — useful for tracking changes and rolling back if needed.

Aliases are named pointers to specific versions, e.g. dev → version 2, prod → version 3. This lets a production application point to a specific, stable version while development continues on a newer one.

Deployment with environments

dev -> Lambda version staging -> Lambda version production -> Lambda version

Separate configuration per environment (dev/staging/production) helps avoid testing changes directly against production data or traffic.

Hinglish: Versions se hum purane snapshots rakh sakte hain, aur aliases se ye control karte hain ki dev/staging/prod kaunsa version use kare.

32. Security, Cost and Limitations

Security

  • IAM & execution roles — least privilege
  • Environment variables for config; Secrets Manager for sensitive secrets
  • Encryption (at rest/in transit, where applicable)
  • CloudWatch Logs for visibility
  • VPC security groups when accessing private resources
  • API authentication (e.g. via API Gateway authorizers)
Important Do not put AWS access keys directly in Lambda code. Prefer the Lambda execution role for accessing AWS services.

Cost

Lambda pricing is generally based on factors such as: number of requests, duration, configured memory/resources, and additional features/services used. You do not normally pay for a continuously running EC2 server just to keep a Lambda function “on.”

Important Lambda is not always free. AWS Free Tier eligibility and limits can change — check current AWS pricing.

Limitations

  • Maximum execution duration (timeout)
  • Memory limits
  • Package/deployment size limits
  • Concurrency limits
  • Cold starts
  • Stateless execution model
  • Not ideal for every workload

Good fit: APIs, event processing, automation, scheduled tasks, file processing, serverless applications.

May be less suitable: long-running processes, workloads requiring persistent processes, certain highly stateful applications.

Hinglish: Lambda short, event-driven kaamon ke liye badhiya hai. Lambe chalne wale ya bahut stateful processes ke liye EC2/ECS jaisa option better ho sakta hai.

34. Lambda vs Node.js Server, and Common Mistakes

Lambda vs a traditional Node.js server

Traditional Node.js: Client -> EC2 -> Node.js Server -> Database Serverless: Client -> API Gateway -> Lambda -> Database

A traditional Node server is a continuously running application process. Lambda runs functions in response to invocations, with no process running between requests.

Common Lambda mistakes

  1. Hard-coding credentials
  2. Giving AdministratorAccess unnecessarily
  3. Ignoring timeout settings
  4. Ignoring memory configuration
  5. Making unnecessary/repeated database connections
  6. Assuming local (/tmp) storage is permanent
  7. Not handling errors
  8. Not monitoring logs
  9. Using Lambda for long-running workloads
  10. Not controlling concurrency
  11. Ignoring cold starts for latency-sensitive apps
  12. Poor IAM permissions (too broad or too narrow)
  13. Putting secrets directly in code

Hinglish: Sabse common galtiyan: credentials hard-code karna, zyada IAM permissions dena, aur Lambda ko lambi-chalne-wali processes ke liye use karna.

35. Interview Questions & Answers

Q1. What is AWS Lambda?
A serverless compute service that runs your code in response to events, without you managing servers.
Q2. What is serverless?
A model where AWS manages the underlying servers/infrastructure for you.
Q3. Does serverless mean there are no servers?
No. Servers still exist; AWS manages them instead of you.
Q4. What is a Lambda function?
A piece of code AWS runs in response to an event or invocation.
Q5. What is a Lambda handler?
The entry-point function AWS calls to start execution, e.g. exports.handler.
Q6. What is an event?
The input data describing what triggered the invocation.
Q7. What is the context object?
Information about the execution environment and the current invocation (e.g. remaining time, request ID).
Q8. What is a Lambda trigger?
An event source (S3, API Gateway, SQS, EventBridge, etc.) that causes Lambda to execute.
Q9. How does Lambda work with API Gateway?
API Gateway exposes an HTTP endpoint, routes requests to Lambda, and returns Lambda’s response to the client.
Q10. How does Lambda work with DynamoDB?
Lambda uses the AWS SDK (with an IAM execution role) to read/write items in DynamoDB tables.
Q11. How does Lambda work with S3?
S3 events (like object created) can trigger Lambda to process the uploaded file.
Q12. What is an IAM execution role?
The IAM role a Lambda function assumes when running, granting it temporary permissions to access AWS resources.
Q13. What is a Lambda Layer?
A reusable package of code/dependencies shared across multiple Lambda functions.
Q14. What is a cold start?
The delay when AWS must initialize a new execution environment before running a function.
Q15. What is concurrency?
The number of Lambda invocations running at the same time.
Q16. What is reserved concurrency?
A set concurrency limit/reservation for a specific function.
Q17. What is provisioned concurrency?
Pre-initialized, ready execution environments kept warm to reduce cold starts.
Q18. What is Lambda timeout?
The maximum time a single invocation is allowed to run before it is stopped.
Q19. Can Lambda access RDS?
Yes, often by running Lambda inside the appropriate VPC/subnets with correct security group rules, ideally with connection pooling or RDS Proxy.
Q20. What is a Lambda Function URL?
A built-in HTTPS endpoint directly tied to one Lambda function, simpler than setting up API Gateway.
Q21. Lambda vs EC2?
EC2 is a continuously running server you manage; Lambda runs code only on invocation and AWS manages the infrastructure.
Q22. Lambda vs ECS?
ECS runs containers you manage more directly (often longer-running services); Lambda runs short, event-driven functions with less operational overhead.
Q23. How do you monitor Lambda?
Using CloudWatch metrics (invocations, errors, duration, throttles) and CloudWatch Logs.
Q24. Where are Lambda logs stored?
In Amazon CloudWatch Logs.
Q25. How do you secure Lambda?
Least-privilege IAM roles, no hard-coded credentials, Secrets Manager for secrets, proper VPC/security groups, and API authentication where needed.
Q26. How do you store secrets?
Using AWS Secrets Manager (or a similar secret-management service) instead of plain code or, for highly sensitive values, plain environment variables.
Q27. How can Lambda be triggered by S3?
By configuring an S3 event notification (e.g. object created) to invoke the function.
Q28. How can Lambda be triggered by DynamoDB Streams?
By enabling a stream on the table and creating an event source mapping from the stream to the Lambda function.
Q29. How does Lambda scale?
AWS automatically creates additional execution environments as invocation demand increases, within service/account limits.
Q30. Is Lambda always free?
No. Pricing depends on requests, duration and resources; Free Tier terms and limits can change, so check current AWS pricing.
